The official SDKs wrap the public `/v1` endpoints and help with validation and webhook parsing. Authentication is always your `ps_` API key.

## Node.js / TypeScript

Package: [`@pilot-status/sdk`](https://www.npmjs.com/package/@pilot-status/sdk)

```bash
npm i @pilot-status/sdk
```

```typescript
import { PilotStatusClient } from "@pilot-status/sdk";

const client = new PilotStatusClient({
  apiKey: process.env.PILOT_STATUS_API_KEY!,
});

const accepted = await client.messages.send({
  templateId: "onboarding-test",
  destinationNumber: "+5511999999999",
  variables: { name: "John" },
});

const message = await client.messages.get(accepted.id);
```

### Retry-safe sends (`idempotencyKey`)

`messages.send()` takes an optional second argument, `{ idempotencyKey }`, sent as the [`Idempotency-Key`](/api/messages/send#idempotency) header — never in the body. Retrying with the **same key and the same input** within 24 hours returns the first accepted response instead of sending again; the same key with a different input fails with `409 IDEMPOTENCY_KEY_REUSED`, and while the first call is still running with `409 IDEMPOTENCY_KEY_IN_USE`. The SDK never retries this POST on its own.

```typescript
const accepted = await client.messages.send(
  {
    templateId: "order-confirmed",
    destinationNumber: "+5511999999999",
    variables: { order_id: "48213" },
  },
  { idempotencyKey: "order-48213-+5511999999999" },
);
```

Derive the key from your own data (order id \+ recipient) or generate a UUID and store it before the first attempt — a key created anew on each attempt protects nothing.

Webhook parsing:

```typescript
import { parseCustomerWebhook } from "@pilot-status/sdk";

const event = parseCustomerWebhook(payload);
```

### Webhook events the SDK does not know

The platform adds events, and a webhook subscribed to `"*"` receives a new one the day it ships — before you upgrade. Starting with **0.12.0**, `parseCustomerWebhook` does not throw on an event name it does not know: it returns `{ type: "unknown", event, data, raw }` (`UnknownCustomerWebhookEvent`) — `event` and `data` as received, `raw` the whole body, nothing validated. Acknowledge it with a `2xx` and ignore it.

```typescript
import { isUnknownCustomerWebhookEvent, parseCustomerWebhook } from "@pilot-status/sdk";

const event = parseCustomerWebhook(payload);
if (isUnknownCustomerWebhookEvent(event)) return new Response("ok");

switch (event.event) {
  // fully narrowed, as before
}
```

<Warning>
  **TypeScript migration (one line).** The unknown case's `event` is a plain `string`, so narrowing on `event.event` alone no longer compiles: rule the unknown case out first with `isUnknownCustomerWebhookEvent`, as above. To keep the old behaviour and the old return type, pass `{ unknownEvents: "throw" }`: `parseCustomerWebhook(payload, { unknownEvents: "throw" })`.
</Warning>

It still throws on a body that is not an object with a string `event`, and on a **known** event whose fields break its contract. `isCustomerWebhookEvent` stays strict: `false` for an unknown event name.

### Ads, Lead Ads Pages and ad referrals (0.16.0)

From **0.16.0** the Node SDK covers [ad referrals](/api/referrals), [ads](/api/ads) and [Lead Ads Pages](/api/lead-pages):

```typescript
const refs = await client.referrals.list();           // GET /v1/referrals
const perAd = await client.ads.summary();             // GET /v1/ads/summary
const accounts = await client.ads.listAccounts();     // GET /v1/ads/accounts
const pages = await client.leadPages.list();          // GET /v1/lead-pages
```

`client.referrals` has `list()` and `summary()`; `client.ads` has `listAccounts()`, `linkAccount()`, `unlinkAccount()` and `summary()`; `client.leadPages` has `list()`, `link()`, `update()`, `unlink()`, `resync()`, `listForms()` and `updateForm()`. `leadPages.unlink()` erases every lead captured through the Page.

**`seatLimit` is now `number | null`** in `WorkspaceDetail` and `WorkspaceMemberList`: workspace members are unlimited on every plan, and the API always returns `null`. If your TypeScript does arithmetic with `seatLimit`, handle `null`. `seatsUsed` is informational only.

## Python

Package: [`pilot-status`](https://pypi.org/project/pilot-status/)

```bash
pip install pilot-status
```

```python
import os
from pilot_status import PilotStatusClient

client = PilotStatusClient(api_key=os.environ["PILOT_STATUS_API_KEY"])

accepted = client.messages.send({
    "templateId": "onboarding-test",
    "destinationNumber": "+5511999999999",
    "variables": {"name": "John"},
})

message = client.messages.get(accepted["id"])
```

For a retry-safe send, pass `idempotency_key` — sent as the [`Idempotency-Key`](/api/messages/send#idempotency) header, with the same semantics as in the Node SDK:

```python
accepted = client.messages.send(
    {
        "templateId": "order-confirmed",
        "destinationNumber": "+5511999999999",
        "variables": {"order_id": "48213"},
    },
    idempotency_key="order-48213-+5511999999999",
)
```

Webhook parsing — from **1.10.0**, an event name the SDK does not know comes back as a dict `{"type": "unknown", "event", "data", "raw"}` instead of raising; tell it apart with `is_unknown_customer_webhook_event` and answer it with a `2xx`:

```python
from pilot_status import is_unknown_customer_webhook_event, parse_customer_webhook

event = parse_customer_webhook(payload)
if is_unknown_customer_webhook_event(event):
    return  # a newer event: acknowledge it, never fail on it
```

`WebhookParseError` is still raised for a body that is not an object with a string `event` and for a **known** event with invalid fields. Pass `unknown_events="raise"` to keep the old behaviour; `is_customer_webhook_event` stays strict. `flow.response_received`, which the Python parser does not model, now comes back as unknown instead of raising.

From **1.14.0** the Python SDK has the same resources — `client.referrals`, `client.ads` and `client.lead_pages` (`list`, `link`, `update`, `unlink`, `resync`, `list_forms`, `update_form`); the `TypedDict`s use the camelCase wire names. It also gains `whatsapp_number_id`: an account-wide key can now target one number, as the Node SDK already did, by sending the `x-whatsapp-number-id` header:

```python
client = PilotStatusClient(api_key=os.environ["PILOT_STATUS_API_KEY"], whatsapp_number_id="num_01HZX...")

# or, from an existing client, a copy bound to another number
leads = client.with_number("num_01HZY...").leads.list()
```

Before 1.14.0, an account-wide key could not reach the number-scoped endpoints (referrals, leads, history) from Python.

## n8n (native integration)

Official community node: `n8n-nodes-pilot-status`.

Install from the n8n UI: **Settings → Community Nodes → Install → `n8n-nodes-pilot-status`**. Authentication uses a Pilot Status API key.

From **2.8.0** the node adds the resources **Referral** (Get Many, Summary), **Ads Summary** (Get), **Ad Account** (Get Many, Link, Unlink), **Lead Page** (Get Many, Link, Update, Unlink, Resync) and **Lead Form** (Get Many, Update). **Lead Page → Unlink** is destructive: it erases every lead captured through the Page and its form configurations.

In **Message → Send**, the optional **Idempotency Key** field is sent as the [`Idempotency-Key`](/api/messages/send#idempotency) header. Use an expression that stays the **same** when n8n retries the item (for example an id from your input data, such as `{{ $json.orderId }}-{{ $json.phone }}`): a retried execution then returns the first response instead of sending the message twice.

<Note>
  For inbound events, add the **Pilot Status Trigger** node to your workflow, copy its webhook URL, and paste it as a new webhook on the **Webhooks** page in the Pilot Status dashboard. Every subscribed event then starts your workflow. With **All Events** selected, the Trigger passes any event through with the body untouched — including events newer than your node version; with a specific event selected, anything else is answered `200 Ignored event`.
</Note>

## Best practices

- Keep the API key on the backend only — never in browser code.
- For `429`/`5xx` responses, retry with exponential backoff (the SDKs help, but the retry policy is up to your system).
- When retrying a send, reuse the same `Idempotency-Key` so a message that was already accepted is not sent twice.
