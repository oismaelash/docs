Pilot Status ships an official **Model Context Protocol (MCP)** server that exposes the public `/v1` API as MCP tools. AI agents and LLM clients can use it to send messages, query conversations, manage numbers, templates, webhooks, groups, and voice calls — directly from the model context.

## Hosted connector

The server speaks the **streamable HTTP** transport and runs as a hosted connector at:

```text
https://mcp.pilotstatus.com.br/mcp
```

Add it as a **Custom Connector** in claude.ai (Settings → Connectors → Add custom connector). claude.ai runs the OAuth 2.1 login (Pilot Status SSO) — no API key is shared with the client. During the consent step you approve access for the **whole tenant** or grant only **specific numbers**; a per-number grant restricts every tool to those numbers. Only the workspace **Owner** or an **Admin** can grant the whole tenant: for an Agent or Analyst the consent screen shows that option disabled and explains why. See [Secrets and API keys over OAuth](#secrets-and-api-keys-over-oauth) for what the app can do with keys and secrets.

Any MCP client that supports custom OAuth connectors can connect the same way. Clients configured by file can instead send a `ps_*` key in the `x-api-key` header:

```json
{
  "mcpServers": {
    "pilot-status": {
      "type": "http",
      "url": "https://mcp.pilotstatus.com.br/mcp",
      "headers": { "x-api-key": "ps_your_key_here" }
    }
  }
}
```

<Tip>
Start here: `/mcp` is the default, and your client shows each call for you to approve. For agents that build reports, loop over many items or run on a tight context, use **`https://mcp.pilotstatus.com.br/code`** instead of `/mcp` (not alongside it): the agent gets 2 tools (`describe` and `execute`) instead of 151 and writes a TypeScript script that calls `await ps.<tool>(args)`. Same credentials. [MCP Code Mode](/integrations/mcp-code-mode)
</Tip>

## Connect your client

Two ways in, whatever the client: **OAuth** (the client opens a Pilot Status login and consent page; no key is copied anywhere) or an **API key** in the `x-api-key` header. Use `/code` instead of `/mcp` in any URL below to get [Code Mode](/integrations/mcp-code-mode).

| Client | How |
| --- | --- |
| **claude.ai** and **Claude Desktop** | Settings → Connectors → **Add custom connector**, URL `https://mcp.pilotstatus.com.br/mcp`, no client id or secret. Connect, log in to Pilot Status and choose the access on the consent screen. Connectors added on claude.ai also show up in Claude Desktop. |
| **Claude Code** | OAuth: `claude mcp add --transport http pilot-status https://mcp.pilotstatus.com.br/mcp`, then run `/mcp` in Claude Code and pick **Authenticate**. API key: add `--header "x-api-key: ps_your_key_here"` to the same command. |
| **ChatGPT** | Where your plan allows custom connectors (developer mode), create a connector with the URL `https://mcp.pilotstatus.com.br/mcp` and **OAuth** authentication. ChatGPT registers itself, so leave client id and secret empty. |
| **Cursor** | API key in `~/.cursor/mcp.json` (or `.cursor/mcp.json` in the project): `{ "mcpServers": { "pilot-status": { "url": "https://mcp.pilotstatus.com.br/mcp", "headers": { "x-api-key": "ps_your_key_here" } } } }`. Or OAuth: leave out `headers` (`{ "mcpServers": { "pilot-status": { "url": "https://mcp.pilotstatus.com.br/mcp" } } }`), then click **Connect** next to the server in **Settings → MCP**; Cursor opens the Pilot Status login and consent page and returns through its `cursor://` callback. |
| **VS Code** (Copilot agent mode) | API key in `.vscode/mcp.json`: `{ "servers": { "pilot-status": { "type": "http", "url": "https://mcp.pilotstatus.com.br/mcp", "headers": { "x-api-key": "ps_your_key_here" } } } }`. |
| **Any other MCP client** | Streamable HTTP at the URL above. A client that supports OAuth with dynamic client registration connects with no setup (callbacks: `https://`, `http://` on loopback, or a native app scheme — see below); otherwise send `x-api-key`. |

Which key to send in `x-api-key`: a **number key** (`ps_number_…`) acts on one number; a **workspace key** (`ps_workspace_…`) acts on the whole workspace, so pass `whatsappNumberId` to number-scoped tools; an **account key** (`ps_account_…`) also needs `x-workspace-id` ([below](#with-an-account-key)). [API key types](/api/key-types)

### What the OAuth login does

- **Which workspace.** The connection acts on one workspace: the consent screen shows its name at the top ("Access will be bound to this workspace"). If you belong to more than one, switch workspace right there before authorizing. If the workspace changes in another tab before you click **Authorize**, the authorization is refused and the screen asks you to reload, so the token is never bound to a workspace you did not see. For two workspaces, add two connections.
- **What it can reach.** On the consent screen you pick **Entire account** (workspace Owner or Admin only) or **specific numbers** (any role, limited to the numbers you can access yourself). A per-number grant restricts every tool to those numbers and blocks account-level tools such as `billing_checkout`, `api_keys_*` and `numbers_create`. Consent is asked on **every** authorization, even with an active session.
- **Your role still applies.** The token never does more than your workspace role allows, and owner-only tools check the role again on every call.
- **Session length.** The access token lasts 1 hour and the client refreshes it on its own; the refresh token lasts 30 days and is replaced on each use. After 30 days without use, or after an ownership transfer, connect again. The access token is not a snapshot: every request re-checks your **current** membership (cached for at most 30 seconds). A role or number change applies on the next tool call, and removal from the workspace ends the connection at once (`401`, the client asks you to connect again).
- **Revoking.** Remove the connector in your client. Keys and secrets the app already obtained stay valid: see [Secrets and API keys over OAuth](#secrets-and-api-keys-over-oauth).

For client developers: the MCP server publishes `/.well-known/oauth-protected-resource` (RFC 9728) and answers an unauthenticated request with `401` and a `WWW-Authenticate` challenge. When the API rejects the OAuth token of a request (expired, revoked), the whole response is `401` with `WWW-Authenticate: Bearer error="invalid_token", …, resource_metadata="…"`, so the client refreshes the token or logs in again; with an API key the rejection stays a tool error. The authorization server, `https://pilotstatus.com.br`, publishes `/.well-known/oauth-authorization-server`: dynamic client registration at `/api/oauth/register` (public clients, `token_endpoint_auth_method: none`), authorization code with **PKCE S256** only, and refresh tokens. Redirect URIs may be `https://`; `http://` on a loopback host (`localhost`, `127.0.0.1`, `[::1]`, any port); or, for native apps (RFC 8252), a private-use scheme that is reverse-DNS (`com.example.app:/callback`) or one of `cursor`, `vscode`, `vscode-insiders`, `windsurf`. Schemes such as `javascript:`, `data:` and `file:`, fragments and user credentials are refused. PKCE stays mandatory for every client. The transport is stateless: JSON-RPC goes in a `POST`; `GET` and `DELETE` answer `405`.

## Authentication

| Method | How |
| --- | --- |
| OAuth 2.1 | `Authorization: Bearer <token>` — handled by the client after the login ([Connect your client](#connect-your-client)) |
| API key | `x-api-key` header with a `ps_*` key |
| Account key | `x-api-key` header with a `ps_account_*` key, plus `x-workspace-id` naming the workspace to act on |

Every tool except `docs_search` takes an extra argument, **`whatsappNumberId`**: the number to act on, from `numbers_list`. With an OAuth token or a workspace key, number-scoped tools (messages, conversations, groups, templates, webhooks, calls, Chatwoot…) **need it** — the server sends it to the API as the `x-whatsapp-number-id` header. With a number key it is ignored: the key already names its number. Account-level tools (`api_keys_list`, `billing_checkout`, `branding_*`, `workspace_*`, phone lines…) need an OAuth token or a workspace key; a number key gets `403`.

### With an account key

An [account key](/api/key-types#account-keys) (`ps_account_…`, created in **Profile → API**) belongs to a user and reaches every workspace they are an active member of, so the connection must say which one to act on: add an `x-workspace-id` header with a workspace id from `workspaces_list`. The server forwards it on every call, on `/mcp` and on [`/code`](/integrations/mcp-code-mode). Inside that workspace the key acts with the user's current role.

```json
{
  "mcpServers": {
    "pilot-status": {
      "type": "http",
      "url": "https://mcp.pilotstatus.com.br/mcp",
      "headers": { "x-api-key": "ps_account_your_key_here", "x-workspace-id": "your_workspace_id" }
    }
  }
}
```

- **Without `x-workspace-id`**, only the `workspaces_*` tools and `docs_search` work (`docs_search` calls no `/v1` endpoint, so it needs no workspace). Every other tool answers `WORKSPACE_ID_REQUIRED` without calling the API, with a message explaining where to set the id.
- **To switch workspaces**, change the header and reconnect, or configure one connection per workspace. A workspace's own `ps_workspace_` key needs no header.
- With an OAuth token the header is ignored: the token already names its workspace.

## Self-hosted

The server is published as `@pilot-status/mcp-server` on npm (command `pilot-status-mcp`, Node.js 20 or later). It speaks **streamable HTTP only** — there is no stdio mode — and listens on `http://localhost:8787/mcp` (`PORT` and `HOST` change it):

```bash
PILOT_STATUS_API_KEY=ps_your_key_here npx -y @pilot-status/mcp-server
```

Then point your client at the local URL, as in [Connect your client](#connect-your-client):

```json
{
  "mcpServers": {
    "pilot-status": { "type": "http", "url": "http://localhost:8787/mcp" }
  }
}
```

The key can come from the process (`PILOT_STATUS_API_KEY`) or from each request's `x-api-key` header, which wins over the variable. It calls `https://pilotstatus.com.br` (`PILOT_STATUS_API_URL` changes it) and serves the same 151 tools as the hosted connector; Code Mode (`/code`) is not available self-hosted. A self-hosted server also reads `PILOT_STATUS_API_KEY` from its environment and, for an account key, `PILOT_STATUS_WORKSPACE_ID`. That variable applies only to the key set in `PILOT_STATUS_API_KEY`, never to a key a connection sends in its own `x-api-key` header: send `x-workspace-id` with that one instead.

Notes:

- `templates_create`/`templates_update` require the `examples` object (one real sample per variable; missing → `400 TEMPLATE_EXAMPLES_REQUIRED`) and accept media headers by **URL only** — base64 is REST-only.
- `templates_insights` (read-only) returns Meta's analytics for one template via `GET /v1/templates/{id}/insights`: args `id` and optional `days` (`7`, `30` or `90`; default `30`). It returns sent/delivered/read `totals`, `readRate` (`null` when nothing was delivered), button `clicks` and a `daily` series, plus the template's name, status, category, language and `qualityScore`. Only Meta templates have insights: a non-Meta template fails with `409 TEMPLATE_NOT_ON_META`, and WhatsApp Business App / coexistence accounts fail with `422 TEMPLATE_INSIGHTS_UNAVAILABLE_SMB` (Meta provides no insights there — do not retry). The first call may enable template insights on the WABA at Meta. Number-scoped API key required.
- `templates_update` returns `409 TEMPLATE_NOT_EDITABLE` when Meta does not allow editing the template in its current state (only rejected templates can be edited); the stored template is left unchanged. Create a new template with the change, or send the document at send time. [Edit](/api/templates#edit)
- `templates_submit` submits a template to Meta for approval (`POST /v1/templates/{id}/submit`, arg `id`) and `templates_sync` pulls the WABA's catalogue from Meta (`POST /v1/templates/sync`, no args, returns `{ created, updated }`; `429 TEMPLATE_SYNC_IN_PROGRESS` while another sync of the number runs). Both need a Meta Cloud API number (`422 TEMPLATE_REQUIRES_META_NUMBER` otherwise) and a number-scoped credential. [Submit to Meta](/api/templates#submit-to-meta)
- `templates_delete` is destructive and asks for confirmation with a token: see [Confirmation for destructive tools](#confirmation-for-destructive-tools). Meta deletes by name, so every language version of that name on the WABA goes.
- `messages_send` supports the three send modes: `templateId`, `text`, or direct media (`media` \+ `mediaType`; use `mediaType: "voice"` for a voice note on any number — `"audio"` arrives as an audio file on official numbers and as a voice note on unofficial ones).
- `messages_send` with `mediaType: "audio"` or `"voice"` takes `media` **only as a public http(s) URL** to a real audio file. A base64 data URI for audio or voice — or any `data:audio/*` media, whatever the `mediaType` — is refused with `400 MCP_AUDIO_URL_REQUIRED` before anything is sent: no message is created. Image and document data URIs are still accepted, for a file the user actually attached. The rule is MCP-only — it applies to `/mcp`, [Code Mode](/integrations/mcp-code-mode) and the in-app AI agent; the [REST API](/api/messages/send) still accepts audio as a data URI. It exists because models invent base64 audio: those bytes are not a playable file and the send failed later with [`MEDIA_TRANSCODE_FAILED`](/api/messages/log-error-codes#media-preparation-on-official-numbers).
- `messages_send` takes `markRead: false` to reply on an official (Meta) number without the typing indicator and without marking the conversation read — for an agent whose replies a person should still find unread. The number-wide default is `markReadOnSend` on `numbers_settings_update` / `numbers_create`. `messages_typing` on a Meta number marks the conversation read, so such an agent must not call it. [Read receipt and typing](/api/messages/send#read-receipt-and-typing)
- `messages_send` takes an optional `idempotencyKey` (up to 255 characters), sent as the `Idempotency-Key` header. Within 24 hours, calling it again with the same key and the same arguments returns the first accepted response without sending again — so an agent that retries after a timeout does not message the contact twice. The same key with different arguments is `409 IDEMPOTENCY_KEY_REUSED`; while the first call is still running, `409 IDEMPOTENCY_KEY_IN_USE`. Derive the key from what makes the send unique (e.g. order id \+ recipient). [Idempotency](/api/messages/send#idempotency)
- `messages_unread_counts` (read-only) returns the unread inbound count **per number** in one call via `GET /v1/messages/unread/counts` — use it instead of calling `messages_unread` once per number. Omit `whatsappNumberIds` for every number the credential can see; each `total` equals `messages_unread`'s `total` for that number. Returns `{ byNumber: [{ whatsappNumberId, number, displayName, total }], total }`.
- Inbound media: on META numbers feed `media.id` to `media_get`; on unofficial (Pilot Status web) numbers use `media.url` directly.
- `numbers_delete` is a 30-day soft delete, undone with `numbers_restore`. `numbers_purge` deletes a number permanently and irreversibly; with an OAuth token only the workspace OWNER may call it.
- `numbers_pay` pays the pending extra-number charge of one number and resumes sending from it (`POST /v1/numbers/{id}/pay`) — with funds available it charges on the spot. It needs a tenant-scoped key with `billing:manage`; with an OAuth token only the workspace OWNER has it.
- `leads_list` and `leads_get` read the leads captured from Meta Lead Ads Instant Forms (Facebook/Instagram) on the Facebook Pages linked to the key's WhatsApp number, and need a number-scoped key. `leads_get` takes the Pilot Status lead `id` from `leads_list`, not Meta's `leadgenId`. `consentGiven` has three states: `true` (ticked the WhatsApp consent checkbox), `false` (left it unticked) and `null` (unknown — never a refusal nor consent). A redacted lead (`redacted: true`, e.g. a RELAY_ONLY number) still counts, with `fullName`, `email` and `phone` null. Both wrap the REST endpoints documented in [`GET /v1/leads`](/api/leads).
- Meta ads and Lead Ads configuration: `ads_accounts_*`, `lead_pages_*` and `lead_forms_*` need the `integrations:manage` permission (workspace ADMIN or OWNER), reads included; `ads_summary` needs `analytics:read`, which every role holds, and carries no conversation content. There is no login step: access comes from partner sharing — the advertiser adds the Pilot Status business portfolio (`partnerBusinessId`) as a partner in Meta Business Manager. `ads_accounts_*` take an account-wide credential; the Lead Ads tools and `ads_summary` see the whole workspace with an account-wide credential and only the bound number with a number-scoped one. `lead_pages_unlink` ERASES every lead captured through the link and its form configurations (irreversible). With `autoSendEnabled: true`, `lead_forms_update` makes the platform message every new lead automatically, without a human. `ads_summary` returns `conversations` (distinct conversations) and `messages` separately, plus `leadCount` per ad, capped at 200 ads (`truncated`). They wrap the REST endpoints documented in [Ads](/api/ads) and [Lead Ads Pages](/api/lead-pages).
- `webhooks_create` and `webhooks_update`: `"*"` subscribes to every event except `lead.received`, which is opt-in — list it by name (for example `["*", "lead.received"]`). See [`lead.received`](/api/webhooks/events#lead-payload).
- `webhooks_create` returns the signing `secret` in clear **once**, on creation; no read returns it again. `webhooks_rotate_secret` mints a new one (also the way to sign a webhook created before 2026-09-15): it is returned once, and the previous secret stops verifying immediately, with no overlap window — store it before anything else. See [Verify the signature](/api/webhooks/configure#verify-the-signature).
- `webhooks_reactivate` resumes a webhook the automatic pause stopped and releases the held events; calling it on a webhook that is already delivering is a no-op.
- Phone-line tools take a tenant-scoped credential only. The `phone_lines_verification_*` tools are OWNER only (`phone_lines:purchase`); `phone_lines_verification_start` requires an `idempotencyKey` (sent as the `Idempotency-Key` header). `phone_lines_activation_audio` returns the recording's metadata and download URL, never the audio itself.
- `phone_lines_webhooks_*` manage the [phone-line webhooks](/api/phone-lines/webhooks), a registry of their own that receives only `phone_line.*` events (the number webhooks of `webhooks_*` never receive them). Tenant-scoped credential only; `phone_lines:webhooks` (workspace ADMIN or OWNER). `phone_lines_webhooks_list` also returns `events`, the catalogue of subscribable events: `events` takes a non-empty list of them, or `["*"]` for every phone-line event. `phone_lines_webhooks_create` returns the `plwh_` signing secret **once** — store it right away: it cannot be read again and there is no rotation. With an OAuth connection every creation is recorded in the audit log ([see below](#secrets-and-api-keys-over-oauth)). It is not idempotent: each call creates another webhook. `phone_lines_webhooks_update` with `active: false` pauses a webhook; `phone_lines_webhooks_delete` removes it and its delivery history permanently. `phone_lines_webhooks_deliveries_list` never carries the payload; `phone_lines_webhooks_deliveries_get` returns it as signed, and on `phone_line.code_received` it contains the activation code.
- `billing_checkout` takes an optional `method`: `card` (default) returns a hosted checkout `url`; `pix` (BRL workspaces only, otherwise `400 PIX_NOT_ELIGIBLE`) returns `orderId` and `pix { transactionId, copyPaste, qrCode, expiresAt }` for the user to pay in their bank app. `successUrl`/`cancelUrl` only apply to card checkouts (`400 FIELD_NOT_APPLICABLE` with `pix`). Nothing is charged until a human pays. `billing_topups_get` reads the top-up order by that `orderId` — `status` `pending`, `paid` (wallet credited), `expired` or `failed` — without calling the payment provider. The Stripe Elements endpoints (`/v1/billing/card/setup-intent*`, `/v1/billing/payment-intents*`) have no tool: their `clientSecret` is only usable by Stripe.js in a browser. See [Wallet and card via API](/api/wallet-and-card).
- `workspace_webhooks_*` manage the [workspace webhooks](/api/workspace-webhooks) (`/v1/workspace/webhooks*`): the same registry as `phone_lines_webhooks_*` (same rows, `plwh_` secret, signature and deliveries), with a wider event set — every `phone_line.*` event plus `wallet.topup_paid` (a wallet top-up was credited). `"*"` still means every phone-line event only: `wallet.topup_paid` is opt-in, list it by name (for example `["*", "wallet.topup_paid"]`). Tenant-scoped credential only; `phone_lines:webhooks` (workspace ADMIN or OWNER). `workspace_webhooks_create` returns the signing secret **once**, like `phone_lines_webhooks_create` (with an OAuth connection, recorded in the audit log).
- `workspace_update` (arg `name`, 1–60 characters, trimmed) renames the workspace; `workspace_settings_get` (no args) reads its currency, time zone, language, billing mode and the price of a new phone line; `workspace_settings_update` (args `mainTimezone?` — an IANA zone — and `mainLanguage?` — `pt`, `en` or `es`) changes only those two fields: the currency is changed by the owner in the dashboard, and the billing mode by the platform. They take a tenant-scoped credential; with an OAuth token, `workspace_update` and `workspace_settings_update` need ADMIN or OWNER, and `workspace_settings_get` any role. See [Workspace API](/api/workspace#rename-the-workspace).
- **`workspace_archive`, `workspace_transfer_ownership` and `workspace_members_remove` are destructive and confirmation-gated**, like `templates_delete`. The first call (no `confirm_token`) changes nothing: it reads `GET /v1/workspace` and `GET /v1/workspace/members` and returns a `preview` — the workspace and every member who loses access (archive); the new owner and the current one (transfer); the member's e-mail, role, numbers and what they lose (remove) — plus a single-use `confirm_token` valid for 5 minutes. Show the preview to the user; only a second call with the **same arguments** and that token runs [`POST /v1/workspace/archive`](/api/workspace#archive-the-workspace), [`POST /v1/workspace/transfer-ownership`](/api/workspace#transfer-ownership) or [`DELETE /v1/workspace/members/{id}`](/api/workspace#removing-a-member-who-created-api-keys). Different arguments are `CONFIRM_TOKEN_MISMATCH`, a reused token `CONFIRM_TOKEN_USED`, an expired one `CONFIRM_TOKEN_EXPIRED`. If the server cannot check that the token is single-use, the call is refused with `503 CONFIRM_TOKEN_STORE_UNAVAILABLE` and nothing runs — retry it.
  - All three are **owner only** and need the owner's OAuth/MCP token (archive and transfer also accept their account key). A workspace or number `ps_` key gets `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE` (archive, transfer) or `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS` (remove).
  - `workspace_archive` takes `confirmName`, the workspace name typed exactly (case-sensitive); a mismatch is refused at the preview with `400 CONFIRMATION_MISMATCH` and no token. Archiving locks everyone out, the caller included, and there is no unarchive endpoint.
  - `workspace_transfer_ownership` takes the new owner's `email` (a member who accepted the invite; `NOT_A_MEMBER`, `TARGET_NOT_ACTIVE` and `ALREADY_OWNER` are refused at the preview). You become ADMIN and both users' OAuth refresh tokens are revoked, so this connection acts as ADMIN from the next call and must consent again when its access token expires.
  - `workspace_members_remove` takes `id` and, after a `409 MEMBER_HAS_API_KEYS`, `apiKeyAction` (`revoke` or `keep`): that 409 spends the token and removes nothing, so request a new preview with the decision.
  - The in-app AI agent does not offer archive or transfer.
- `workspaces_*` take an **account key** only (`ps_account_…`, created in Profile → API, sent as `x-api-key`): an OAuth/connector token, a workspace key or a number key gets `403 ACCOUNT_KEY_REQUIRED`. `workspaces_list` lists the workspaces the key's user is an active member of, with their role; `workspaces_create` creates one owned by that user and returns its primary workspace key **once** (`409 WORKSPACE_LIMIT_REACHED` at the user's ceiling); its optional `shareCard: true` links the new workspace to the user's reserve card, and absent or `false` leaves it not shared. `workspaces_shared_card_link` and `workspaces_shared_card_unlink` (argument `workspaceId`) call `PUT` and `DELETE /v1/workspaces/{workspaceId}/shared-card`: they need the user to be OWNER of that workspace, change who pays its renewals and ask for confirmation. `workspaces_api_keys_list` (masked), `workspaces_api_keys_create` (a named `ps_workspace_` key, returned once; `409 WORKSPACE_KEY_LIMIT_REACHED`) and `workspaces_api_keys_revoke` (`409 PRIMARY_KEY_NOT_REVOCABLE` for the primary key) need the user's live role ADMIN or OWNER in that workspace, otherwise `403 WORKSPACE_MEMBERSHIP_REQUIRED` or `PERMISSION_DENIED`. The in-app AI agent does not offer them. They need no `x-workspace-id`, and neither does `docs_search`; every other tool used with an account key does (see [With an account key](#with-an-account-key)). See [Create workspaces](/api/workspaces).
- `docs_search` takes a `query` — a question, keywords or an error code, in Portuguese or English — and an optional `limit` (3–5, default 5), and returns `{ query, results, source }`: the 3–5 most relevant pages of this documentation, each with `title`, `url` and `description` (not the page content). It reads the public docs index (`llms.txt` and its pt-BR sub-index; the Playground pages are left out), calls no `/v1` endpoint and needs no permission, key scope or `whatsappNumberId`, so any role can use it and the in-app agent runs it without asking for confirmation. `source` is `live`, or `fallback` when the index could not be fetched and a built-in copy answered; the index is cached for 6 hours. Use it when the user asks how to do something on Pilot Status, or when another tool returns an error code — search the code (e.g. `MEDIA_TRANSCODE_FAILED` leads to [Log Error Codes](/api/messages/log-error-codes)).
- `templates_delete` takes an optional `force_local_delete`: when Meta refuses the deletion (`409 META_TEMPLATE_DELETE_REFUSED`, nothing deleted), it deletes only the Pilot Status copy and leaves the template on Meta. Use it only after the user saw that 409 and asked for a local-only delete.
- Three tools refuse to run without the boolean **`confirm: true`** (no token, one call): `flows_publish` (publishing a Flow cannot be undone; otherwise `400 FLOW_PUBLISH_REQUIRES_CONFIRMATION`), `flows_endpoint_key_rotate` when the number already has a key registered at Meta (replacing it breaks every `data_exchange` Flow of the number; otherwise `400 FLOW_ENDPOINT_KEY_REQUIRES_CONFIRMATION`) and `subscription_extra_numbers_add` when the purchase converts a FREE plan to On Demand. Send it only after the user said yes.
- Member management needs an **OAuth token** — there is no user behind a `ps_` key, so a key gets `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`: `workspace_members_invite` and `workspace_members_resend` (ADMIN or OWNER; an ADMIN can assign only AGENT or ANALYST), `workspace_members_set_numbers` (ADMIN or OWNER), `workspace_members_update` and `workspace_members_remove` (OWNER only). `workspace_members_list` (ADMIN or OWNER) also works with a workspace key. Nobody becomes OWNER through these tools: that is `workspace_transfer_ownership`.
- `billing_checkout` is account-level: it needs the workspace OWNER and an **Entire account** grant (a per-number OAuth grant cannot use it).
- Token-based routes (remote-pairing public endpoints, embed session minting) are excluded from the tool list because they use a different auth flow.

## Secrets and API keys over OAuth

With the OAuth connector, the app can do what the dashboard does — including revealing and creating API keys and secrets — under these safeguards:

1. **API keys: workspace Owner only, checked on every call.** Revealing or creating a `ps_` API key works only while the connected user is the workspace **Owner**. The role is read from the workspace on each call, not from the token or from the consent: if the owner hands the workspace over or is removed, the very next call is refused.
2. **Signing secrets: same rule as the dashboard.** Webhook signing secrets (including `plwh_`), the Flow endpoint secret and the Meta verify token go to whoever the dashboard allows — workspace **Admin** or **Owner**.
3. **Audit log, for all of them.** Every reveal or creation of a key or secret made through OAuth is recorded: who (user), which app (OAuth client), which workspace, what (action and target), when and from which IP. The value itself is never recorded.
4. **Warning on the consent screen.** An owner is told the app will be able to view secrets and create API keys; an admin, that it will be able to view secrets (API keys stay owner-only).

| Tool | What it reveals or creates | Who, over OAuth |
| --- | --- | --- |
| `api_keys_list` | The number keys, in clear | Owner only; otherwise `403 OAUTH_SECRET_REQUIRES_OWNER` |
| `api_keys_regenerate_number` | A new number key (`ps_number_…`) | Owner only; otherwise `403 OAUTH_SECRET_REQUIRES_OWNER` |
| `webhooks_create`, `webhooks_rotate_secret` | A webhook signing secret | Admin or Owner (`webhooks:manage`) |
| `workspace_webhooks_create`, `phone_lines_webhooks_create` | A `plwh_` signing secret | Admin or Owner (`phone_lines:webhooks`) |

`POST /v1/api-keys/regenerate` (the workspace's primary key) follows the API-key rule; `PUT`/`PATCH /v1/flows/{id}/endpoint` (the Flow endpoint secret) and `POST /v1/numbers/meta` (the Meta verify token) follow the dashboard's rule. If the audit record cannot be written, the act does not go through unrecorded: a reveal or rotation is refused with `500 OAUTH_SECRET_AUDIT_UNAVAILABLE`, and a creation still succeeds but returns `secret: null` with `secretWithheld: true` (rotate to get a new one).

<Warning>
  A key or secret obtained through the connector **stays valid after you revoke the connector**: revoking it ends the app's access, not what it obtained. To cut those, regenerate the keys on the [API Keys](/dashboard/api-keys) screen and rotate the secrets. Keys created through OAuth are recorded as created by you, so removing you from the workspace offers to revoke them.
</Warning>

A classic `ps_` key (`x-api-key`) is not affected by these rules. Creating workspaces and named workspace keys (`workspaces_*`) still needs an account key.

## Confirmation for destructive tools

Some tools change things that cannot be undone. They run in **two calls**, and the second one needs a token from the first:

1. **Call the tool without `confirm_token`.** Nothing changes. The answer is `status: "CONFIRMATION_REQUIRED"`, a `preview` of exactly what would happen and a `confirm_token` valid for **5 minutes**.
2. **Show the preview to the person and wait for an explicit yes.** Then call the tool again with the **same arguments** plus `confirm_token`. Only this call runs the action.

```json First call: preview, nothing deleted
{
  "status": "CONFIRMATION_REQUIRED",
  "preview": {
    "dry_run": true,
    "action": "DELETE_ON_META_AND_LOCAL",
    "template": { "id": "tpl_01HZX...", "name": "promo", "meta_language": "pt_BR", "meta_status": "APPROVED" },
    "waba": { "id": "1581714517011340", "name": "Acme" },
    "via_number": { "id": "wn_01HZX...", "number": "+5511999990000" }
  },
  "confirm_token": "pct1.eyJ0Ijo...",
  "expires_at": "2026-11-10T14:05:00.000Z",
  "next_step": "Nothing was changed. Show this preview to the user. …"
}
```

- The token is single-use and bound to the tool, its arguments and your connection (credential, workspace and number). Another tool, other arguments, another key or another number cannot use it.
- Refusals: `CONFIRM_TOKEN_EXPIRED` (ask for a new preview), `CONFIRM_TOKEN_MISMATCH` (repeat the exact arguments of the preview), `CONFIRM_TOKEN_USED` (it already ran — do not repeat it), `CONFIRM_TOKEN_INVALID` (get a new preview).
- Tools with confirmation today: `templates_delete`, `workspace_archive`, `workspace_transfer_ownership` and `workspace_members_remove`. The REST API needs no token: call `DELETE /v1/templates/{id}?dry_run=true` to get the same preview of a template delete.
- In [Code Mode](/integrations/mcp-code-mode) the same two calls apply. In the in-app AI agent the preview runs on its own and the agent asks you to confirm the second call.

## Common errors

- `401` — missing or invalid API key, or an expired OAuth session: the client is asked to log in again ([Connect your client](#connect-your-client)).
- `403` — a number key on an account-level tool, a tool outside a per-number grant, or a role that may not call the tool. With an OAuth token or a workspace key, a number-scoped tool called without `whatsappNumberId` is also refused.
- `WORKSPACE_ID_REQUIRED` — an account key without `x-workspace-id` ([With an account key](#with-an-account-key)).
- `503 SHUTTING_DOWN` — the replica that took the request is restarting; retry it.
- `400` — invalid tool arguments (validated against the underlying API schema).
- `400 MCP_AUDIO_URL_REQUIRED` — `messages_send` got a data URI (base64) for `mediaType` `audio`/`voice`, or a `data:audio/*` media. Send the audio as a public http(s) URL. The message is bilingual (`English | Português`) and nothing was sent.
