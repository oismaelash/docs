Os SDKs oficiais encapsulam os endpoints públicos `/v1` e ajudam com validação e parsing de webhooks. A autenticação é sempre sua chave de API `ps_`.

## Node.js / TypeScript

Pacote: [`@pilot-status/sdk`](https://www.npmjs.com/package/@pilot-status/sdk)

```bash
npm i @pilot-status/sdk
```

```typescript
import { PilotStatusClient } from "@pilot-status/sdk";

const client = new PilotStatusClient({
  apiKey: process.env.PILOT_STATUS_API_KEY!,
});

const accepted = await client.messages.send({
  templateId: "onboarding-test",
  destinationNumber: "+5511999999999",
  variables: { name: "John" },
});

const message = await client.messages.get(accepted.id);
```

### Envio seguro para nova tentativa (`idempotencyKey`)

`messages.send()` aceita um segundo argumento opcional, `{ idempotencyKey }`, enviado no header [`Idempotency-Key`](/pt-BR/api/messages/send#idempotência) — nunca no corpo. Tentar de novo com a **mesma chave e a mesma entrada** dentro de 24 horas devolve a primeira resposta aceita em vez de enviar de novo; a mesma chave com uma entrada diferente falha com `409 IDEMPOTENCY_KEY_REUSED`, e, enquanto a primeira chamada ainda está em andamento, com `409 IDEMPOTENCY_KEY_IN_USE`. O SDK nunca repete este POST por conta própria.

```typescript
const accepted = await client.messages.send(
  {
    templateId: "pedido-confirmado",
    destinationNumber: "+5511999999999",
    variables: { order_id: "48213" },
  },
  { idempotencyKey: "pedido-48213-+5511999999999" },
);
```

Derive a chave dos seus próprios dados (id do pedido \+ destinatário) ou gere um UUID e guarde-o antes da primeira tentativa — uma chave criada de novo a cada tentativa não protege nada.

Parsing de webhook:

```typescript
import { parseCustomerWebhook } from "@pilot-status/sdk";

const event = parseCustomerWebhook(payload);
```

### Eventos de webhook que o SDK não conhece

A plataforma acrescenta eventos, e um webhook assinado em `"*"` recebe um evento novo no dia em que ele sai — antes de você atualizar. A partir da **0.12.0**, `parseCustomerWebhook` não lança erro para um nome de evento que não conhece: devolve `{ type: "unknown", event, data, raw }` (`UnknownCustomerWebhookEvent`) — `event` e `data` como chegaram, `raw` o corpo inteiro, nada validado. Responda com `2xx` e ignore.

```typescript
import { isUnknownCustomerWebhookEvent, parseCustomerWebhook } from "@pilot-status/sdk";

const event = parseCustomerWebhook(payload);
if (isUnknownCustomerWebhookEvent(event)) return new Response("ok");

switch (event.event) {
  // estreitado por completo, como antes
}
```

<Warning>
  **Migração em TypeScript (uma linha).** O `event` do caso desconhecido é uma `string` comum, então estreitar só por `event.event` deixa de compilar: descarte o caso desconhecido antes com `isUnknownCustomerWebhookEvent`, como acima. Para manter o comportamento e o tipo de retorno antigos, passe `{ unknownEvents: "throw" }`: `parseCustomerWebhook(payload, { unknownEvents: "throw" })`.
</Warning>

Continua lançando erro para um corpo que não é um objeto com `event` em texto e para um evento **conhecido** com campos que quebram o contrato. `isCustomerWebhookEvent` continua estrito: `false` para um nome de evento desconhecido.

### Anúncios, Páginas do Lead Ads e origens de anúncio (0.16.0)

A partir da **0.16.0**, o SDK Node cobre as [origens de anúncio](/pt-BR/api/referrals), os [anúncios](/pt-BR/api/ads) e as [Páginas do Lead Ads](/pt-BR/api/lead-pages):

```typescript
const refs = await client.referrals.list();           // GET /v1/referrals
const perAd = await client.ads.summary();             // GET /v1/ads/summary
const accounts = await client.ads.listAccounts();     // GET /v1/ads/accounts
const pages = await client.leadPages.list();          // GET /v1/lead-pages
```

`client.referrals` tem `list()` e `summary()`; `client.ads` tem `listAccounts()`, `linkAccount()`, `unlinkAccount()` e `summary()`; `client.leadPages` tem `list()`, `link()`, `update()`, `unlink()`, `resync()`, `listForms()` e `updateForm()`. `leadPages.unlink()` apaga todo lead captado pela Página.

**`seatLimit` agora é `number | null`** em `WorkspaceDetail` e `WorkspaceMemberList`: os membros do workspace são ilimitados em todos os planos, e a API devolve sempre `null`. Se o seu TypeScript faz conta com `seatLimit`, trate o `null`. `seatsUsed` é só informativo.

### Webhooks das linhas (0.18.0)

A partir da **0.18.0**, `client.phoneLines.webhooks` gerencia os [webhooks das linhas](/pt-BR/api/phone-lines/webhooks) — um cadastro separado dos webhooks de número (`client.webhooks`), que recebe só eventos `phone_line.*`. Exige uma chave da conta inteira (escopo de tenant) de um **Proprietário ou Administrador** (`phone_lines:webhooks`). Cada método devolve o corpo da resposta como veio:

```typescript
const { webhook } = await client.phoneLines.webhooks.create({
  url: "https://hooks.example.com/lines",                         // https e público
  events: ["phone_line.code_received", "phone_line.code_failed"], // ou ["*"]
  name: "Códigos de ativação",                                    // opcional
});
// webhook.secret ("plwh_...") só vem aqui — guarde agora

const { webhooks, events } = await client.phoneLines.webhooks.list();   // nunca o segredo
await client.phoneLines.webhooks.update(webhook.id, { active: false }); // pausar
const { deliveries } = await client.phoneLines.webhooks.listDeliveries(webhook.id, { limit: 20 });
const { delivery } = await client.phoneLines.webhooks.getDelivery(webhook.id, deliveries[0].id);
await client.phoneLines.webhooks.delete(webhook.id);                    // { ok: true }
```

Os métodos são `list()`, `get(id)`, `create()`, `update(id, input)`, `delete(id)`, `listDeliveries(id, { limit })` (1–200, padrão 50, mais recentes primeiro, sem o payload) e `getDelivery(id, deliveryId)`. `create()` não é idempotente: duas chamadas criam dois webhooks com dois segredos, e o SDK nunca o repete sozinho. `delivery.payload` é a string JSON exata que foi assinada, para você conferir com `verifyWebhookSignature` e o segredo `plwh_`. O payload de um `phone_line.code_received` contém o código de ativação: trate-o como credencial.

## Python

Pacote: [`pilot-status`](https://pypi.org/project/pilot-status/)

```bash
pip install pilot-status
```

```python
import os
from pilot_status import PilotStatusClient

client = PilotStatusClient(api_key=os.environ["PILOT_STATUS_API_KEY"])

accepted = client.messages.send({
    "templateId": "onboarding-test",
    "destinationNumber": "+5511999999999",
    "variables": {"name": "John"},
})

message = client.messages.get(accepted["id"])
```

Para um envio seguro para nova tentativa, passe `idempotency_key` — enviado no header [`Idempotency-Key`](/pt-BR/api/messages/send#idempotência), com a mesma semântica do SDK de Node:

```python
accepted = client.messages.send(
    {
        "templateId": "pedido-confirmado",
        "destinationNumber": "+5511999999999",
        "variables": {"order_id": "48213"},
    },
    idempotency_key="pedido-48213-+5511999999999",
)
```

Parsing de webhook — a partir da **1.10.0**, um nome de evento que o SDK não conhece volta como um dict `{"type": "unknown", "event", "data", "raw"}` em vez de lançar erro; identifique-o com `is_unknown_customer_webhook_event` e responda com `2xx`:

```python
from pilot_status import is_unknown_customer_webhook_event, parse_customer_webhook

event = parse_customer_webhook(payload)
if is_unknown_customer_webhook_event(event):
    return  # evento mais novo que o SDK: confirme, nunca falhe
```

`WebhookParseError` continua sendo lançado para um corpo que não é um objeto com `event` em texto e para um evento **conhecido** com campos inválidos. Passe `unknown_events="raise"` para manter o comportamento antigo; `is_customer_webhook_event` continua estrito. O `flow.response_received`, que o parser Python não modela, agora volta como desconhecido em vez de lançar erro.

A partir da **1.14.0**, o SDK Python tem os mesmos recursos — `client.referrals`, `client.ads` e `client.lead_pages` (`list`, `link`, `update`, `unlink`, `resync`, `list_forms`, `update_form`); os `TypedDict` usam os nomes do wire em camelCase. Ele também ganha `whatsapp_number_id`: uma chave da conta inteira agora pode mirar um número, como o SDK Node já fazia, enviando o header `x-whatsapp-number-id`:

```python
client = PilotStatusClient(api_key=os.environ["PILOT_STATUS_API_KEY"], whatsapp_number_id="num_01HZX...")

# ou, a partir de um cliente existente, uma cópia vinculada a outro número
leads = client.with_number("num_01HZY...").leads.list()
```

Antes da 1.14.0, uma chave da conta inteira não alcançava pelo Python os endpoints que atuam num número (origens de anúncio, leads, histórico).

A partir da **1.16.0**, `client.phone_lines.webhooks` gerencia os [webhooks das linhas](/pt-BR/api/phone-lines/webhooks), com as mesmas regras do SDK Node: `list()`, `get(webhook_id)`, `create(url=..., events=[...], name=None)`, `update(webhook_id, name=..., url=..., events=..., active=...)` (só os argumentos passados são enviados), `delete(webhook_id)`, `list_deliveries(webhook_id, limit=None)` e `get_delivery(webhook_id, delivery_id)`. As respostas são os corpos da API como dicts com as chaves em camelCase.

```python
created = client.phone_lines.webhooks.create(
    url="https://hooks.example.com/lines",
    events=["phone_line.code_received"],
)
secret = created["webhook"]["secret"]  # "plwh_..." — só vem aqui

client.phone_lines.webhooks.update(created["webhook"]["id"], active=False)
```

Também a partir da **1.16.0**, `verify_webhook_signature(raw_body, signature_header, secret)` confere o cabeçalho `x-pilot-status-signature` — a contraparte Python do `verifyWebhookSignature`. É o mesmo HMAC-SHA256 (hex, sobre o corpo cru) para os [webhooks de número](/pt-BR/api/webhooks/configure#verifique-a-assinatura) e os [webhooks das linhas](/pt-BR/api/phone-lines/webhooks#verificar-a-assinatura) (segredo `plwh_`). A comparação é em tempo constante e a função devolve `False` — nunca lança exceção — para cabeçalho ausente ou malformado, segredo vazio ou corpo adulterado. Passe o corpo **exatamente como chegou** (`bytes`, ou `str` codificada em UTF-8), nunca o JSON re-serializado:

```python
from pilot_status import WEBHOOK_SIGNATURE_HEADER, verify_webhook_signature

raw = request.get_data()      # Flask; FastAPI: raw = await request.body()
if not verify_webhook_signature(raw, request.headers.get(WEBHOOK_SIGNATURE_HEADER), secret):
    abort(401)
event = parse_customer_webhook(json.loads(raw))
```

## n8n (integração nativa)

Node oficial da comunidade: `n8n-nodes-pilot-status`.

Instale pela interface do n8n: **Settings → Community Nodes → Install → `n8n-nodes-pilot-status`**. A autenticação usa uma chave de API do Pilot Status.

A partir da **2.8.0**, o node ganha os recursos **Referral** (Get Many, Summary), **Ads Summary** (Get), **Ad Account** (Get Many, Link, Unlink), **Lead Page** (Get Many, Link, Update, Unlink, Resync) e **Lead Form** (Get Many, Update). **Lead Page → Unlink** é destrutivo: apaga todo lead captado pela Página e as configurações de formulário dela.

A partir da **2.10.0**, o recurso **Phone Line Webhook** (Create, Delete, Get, Get Many, Update, Get Deliveries, Get Delivery) gerencia os [webhooks das linhas](/pt-BR/api/phone-lines/webhooks) com uma chave da conta inteira de um Proprietário ou Administrador. **Create** devolve o segredo de assinatura `plwh_` uma única vez — guarde-o na mesma execução.

Em **Message → Send**, o campo opcional **Idempotency Key** é enviado no header [`Idempotency-Key`](/pt-BR/api/messages/send#idempotência). Use uma expressão que continue a **mesma** quando o n8n repetir o item (por exemplo, um id dos seus dados de entrada, como `{{ $json.orderId }}-{{ $json.phone }}`): uma execução repetida então devolve a primeira resposta em vez de enviar a mensagem duas vezes.

<Note>
  Para eventos de entrada, adicione o node **Pilot Status Trigger** ao seu fluxo de trabalho, copie sua URL de webhook e cole como um novo webhook na página **Webhooks** no painel do Pilot Status. Cada evento assinado então inicia seu fluxo de trabalho. Com **All Events** selecionado, o Trigger repassa qualquer evento com o corpo intacto — inclusive eventos mais novos que a versão do seu node; com um evento específico selecionado, os demais recebem `200 Ignored event`.
</Note>

## Boas práticas

- Mantenha a chave de API apenas no backend — nunca em código de navegador.
- Para respostas `429`/`5xx`, tente novamente com backoff exponencial (os SDKs ajudam, mas a política de retentativa fica a cargo do seu sistema).
- Ao repetir um envio, reutilize a mesma `Idempotency-Key` para que uma mensagem já aceita não seja enviada duas vezes.
