A Pilot Status oferece um servidor oficial de **Model Context Protocol (MCP)** que expõe a API pública `/v1` como ferramentas MCP. Agentes de IA e clientes LLM podem usá-lo para enviar mensagens, consultar conversas, gerenciar números, templates, webhooks, grupos e chamadas de voz — diretamente do contexto do modelo.

## Conector hospedado

O servidor usa o transporte **streamable HTTP** e roda como um conector hospedado em:

```text
https://mcp.pilotstatus.com.br/mcp
```

Adicione-o como um **Conector Personalizado** no claude.ai (Configurações → Conectores → Adicionar conector personalizado). O claude.ai executa o login OAuth 2.1 (SSO da Pilot Status) — nenhuma chave de API é compartilhada com o cliente. Durante a etapa de consentimento você aprova o acesso ao **tenant inteiro** ou concede apenas **números específicos**; uma concessão por número restringe cada ferramenta a esses números. Só o **proprietário** ou um **administrador** do workspace pode conceder o tenant inteiro: para um agente ou analista, a tela de consentimento mostra essa opção desabilitada e explica o motivo. Veja em [Segredos e chaves de API por OAuth](#segredos-e-chaves-de-api-por-oauth) o que o aplicativo pode fazer com chaves e segredos.

Qualquer cliente MCP que suporte conectores OAuth personalizados pode conectar da mesma forma. Clientes configurados por arquivo podem, em vez disso, enviar uma chave `ps_*` no header `x-api-key`:

```json
{
  "mcpServers": {
    "pilot-status": {
      "type": "http",
      "url": "https://mcp.pilotstatus.com.br/mcp",
      "headers": { "x-api-key": "ps_your_key_here" }
    }
  }
}
```

<Tip>
Comece por aqui: o `/mcp` é o padrão, e o seu cliente mostra cada chamada para você aprovar. Para agentes que montam relatórios, percorrem muitos itens ou rodam com contexto apertado, use **`https://mcp.pilotstatus.com.br/code`** no lugar do `/mcp` (não junto com ele): o agente recebe 2 ferramentas (`describe` e `execute`) em vez de 148 e escreve um script TypeScript que chama `await ps.<ferramenta>(args)`. Mesmas credenciais. [Modo de código do MCP](/pt-BR/integrations/mcp-code-mode)
</Tip>

## Conectar o seu cliente

Há duas formas de entrar, qualquer que seja o cliente: **OAuth** (o cliente abre uma página de login e consentimento da Pilot Status; nenhuma chave é copiada) ou uma **chave de API** no header `x-api-key`. Troque `/mcp` por `/code` em qualquer URL abaixo para usar o [modo de código](/pt-BR/integrations/mcp-code-mode).

| Cliente | Como |
| --- | --- |
| **claude.ai** e **Claude Desktop** | Configurações → Conectores → **Adicionar conector personalizado**, URL `https://mcp.pilotstatus.com.br/mcp`, sem client id nem secret. Conecte, entre na Pilot Status e escolha o acesso na tela de consentimento. Os conectores adicionados no claude.ai também aparecem no Claude Desktop. |
| **Claude Code** | OAuth: `claude mcp add --transport http pilot-status https://mcp.pilotstatus.com.br/mcp`, depois rode `/mcp` no Claude Code e escolha **Authenticate**. Chave de API: acrescente `--header "x-api-key: ps_sua_chave_aqui"` ao mesmo comando. |
| **ChatGPT** | Onde o seu plano permite conectores personalizados (modo desenvolvedor), crie um conector com a URL `https://mcp.pilotstatus.com.br/mcp` e autenticação **OAuth**. O ChatGPT se registra sozinho, então deixe client id e secret em branco. |
| **Cursor** | Chave de API em `~/.cursor/mcp.json` (ou `.cursor/mcp.json` no projeto): `{ "mcpServers": { "pilot-status": { "url": "https://mcp.pilotstatus.com.br/mcp", "headers": { "x-api-key": "ps_sua_chave_aqui" } } } }`. O OAuth não funciona no Cursor: o retorno do login dele é um endereço `cursor://`, e o servidor de autorização da Pilot Status só aceita retornos `https://` e `http://localhost`. |
| **VS Code** (modo agente do Copilot) | Chave de API em `.vscode/mcp.json`: `{ "servers": { "pilot-status": { "type": "http", "url": "https://mcp.pilotstatus.com.br/mcp", "headers": { "x-api-key": "ps_sua_chave_aqui" } } } }`. |
| **Qualquer outro cliente MCP** | Streamable HTTP na URL acima. Um cliente com OAuth, registro dinâmico de cliente e retorno `https://` ou `http://localhost` conecta sem configuração; senão, envie `x-api-key`. |

Qual chave enviar em `x-api-key`: uma **chave de número** (`ps_number_…`) age em um número; uma **chave de workspace** (`ps_workspace_…`) age no workspace inteiro, então passe `whatsappNumberId` nas ferramentas de número; uma **chave de conta** (`ps_account_…`) também precisa de `x-workspace-id` ([abaixo](#com-uma-chave-de-conta)). [Tipos de chave de API](/pt-BR/api/key-types)

### O que o login OAuth faz

- **Qual workspace.** A conexão age no workspace que está **selecionado na sua sessão da Pilot Status** no momento da autorização. A tela de consentimento não pergunta o workspace: troque de workspace no painel antes e depois conecte. Para dois workspaces, adicione duas conexões.
- **O que ela alcança.** Na tela de consentimento você escolhe **Toda a conta** (só proprietário ou administrador do workspace) ou **números específicos** (qualquer papel, limitado aos números a que você mesmo tem acesso). Uma concessão por número restringe todas as ferramentas a esses números e bloqueia ferramentas da conta, como `billing_checkout`, `api_keys_*` e `numbers_create`. O consentimento é pedido em **toda** autorização, mesmo com sessão ativa.
- **O seu papel continua valendo.** O token nunca faz mais do que o seu papel no workspace permite, e as ferramentas exclusivas do proprietário conferem o papel de novo a cada chamada.
- **Duração.** O token de acesso dura 1 hora e o cliente o renova sozinho; o token de renovação dura 30 dias e é trocado a cada uso. Depois de 30 dias sem uso, ou de uma transferência de posse, conecte de novo.
- **Revogar.** Remova o conector no seu cliente. Chaves e segredos que o aplicativo já obteve continuam válidos: veja [Segredos e chaves de API por OAuth](#segredos-e-chaves-de-api-por-oauth).

Para quem desenvolve clientes: o servidor MCP publica `/.well-known/oauth-protected-resource` (RFC 9728) e responde a uma requisição sem credencial com `401` e um desafio `WWW-Authenticate`. O servidor de autorização, `https://pilotstatus.com.br`, publica `/.well-known/oauth-authorization-server`: registro dinâmico de cliente em `/api/oauth/register` (clientes públicos, `token_endpoint_auth_method: none`), código de autorização só com **PKCE S256** e tokens de renovação. As URIs de redirecionamento precisam ser `https://`, ou `http://` em `localhost` / `127.0.0.1`. O transporte não guarda sessão: o JSON-RPC vai num `POST`; `GET` e `DELETE` respondem `405`.

## Autenticação

| Método | Como |
| --- | --- |
| OAuth 2.1 | `Authorization: Bearer <token>` — tratado pelo cliente depois do login ([Conectar o seu cliente](#conectar-o-seu-cliente)) |
| Chave de API | header `x-api-key` com uma chave `ps_*` |
| Chave de conta | header `x-api-key` com uma chave `ps_account_*`, mais `x-workspace-id` indicando o workspace em que agir |

Toda ferramenta, exceto a `docs_search`, recebe um argumento a mais, **`whatsappNumberId`**: o número em que agir, obtido em `numbers_list`. Com um token OAuth ou uma chave de workspace, as ferramentas de número (mensagens, conversas, grupos, templates, webhooks, chamadas, Chatwoot…) **precisam dele** — o servidor o envia à API no header `x-whatsapp-number-id`. Com uma chave de número ele é ignorado: a chave já indica o número. As ferramentas da conta (`api_keys_list`, `billing_checkout`, `branding_*`, `workspace_*`, linhas telefônicas…) precisam de um token OAuth ou de uma chave de workspace; uma chave de número recebe `403`.

### Com uma chave de conta

Uma [chave de conta](/pt-BR/api/key-types#chaves-de-conta) (`ps_account_…`, criada em **Perfil → API**) pertence a um usuário e alcança todos os workspaces em que ele é membro ativo, então a conexão precisa dizer em qual agir: adicione um header `x-workspace-id` com o id de um workspace obtido em `workspaces_list`. O servidor o encaminha em toda chamada, no `/mcp` e no [`/code`](/pt-BR/integrations/mcp-code-mode). Dentro desse workspace, a chave age com o papel atual do usuário.

```json
{
  "mcpServers": {
    "pilot-status": {
      "type": "http",
      "url": "https://mcp.pilotstatus.com.br/mcp",
      "headers": { "x-api-key": "ps_account_sua_chave_aqui", "x-workspace-id": "id_do_seu_workspace" }
    }
  }
}
```

- **Sem `x-workspace-id`**, só as ferramentas `workspaces_*` e a `docs_search` funcionam (a `docs_search` não chama nenhum endpoint `/v1`, então não precisa de workspace). Todas as outras respondem `WORKSPACE_ID_REQUIRED` sem chamar a API, com uma mensagem que explica onde colocar o id.
- **Para trocar de workspace**, mude o header e reconecte, ou configure uma conexão por workspace. A chave `ps_workspace_` do próprio workspace dispensa o header.
- Com um token OAuth o header é ignorado: o token já indica o workspace.

## Auto-hospedado

O servidor é publicado como `@pilot-status/mcp-server` no npm (comando `pilot-status-mcp`, Node.js 20 ou mais recente). Ele fala **só streamable HTTP** — não há modo stdio — e escuta em `http://localhost:8787/mcp` (`PORT` e `HOST` mudam isso):

```bash
PILOT_STATUS_API_KEY=ps_sua_chave_aqui npx -y @pilot-status/mcp-server
```

Depois aponte o seu cliente para a URL local, como em [Conectar o seu cliente](#conectar-o-seu-cliente):

```json
{
  "mcpServers": {
    "pilot-status": { "type": "http", "url": "http://localhost:8787/mcp" }
  }
}
```

A chave pode vir do processo (`PILOT_STATUS_API_KEY`) ou do header `x-api-key` de cada requisição, que prevalece sobre a variável. Ele chama `https://pilotstatus.com.br` (`PILOT_STATUS_API_URL` muda isso) e serve as mesmas 148 ferramentas do conector hospedado; o modo de código (`/code`) não está disponível auto-hospedado. Um servidor auto-hospedado também lê `PILOT_STATUS_API_KEY` do ambiente e, para uma chave de conta, `PILOT_STATUS_WORKSPACE_ID`. Essa variável vale só para a chave definida em `PILOT_STATUS_API_KEY`, nunca para uma chave que a conexão envia no próprio header `x-api-key`: com essa, envie `x-workspace-id`.

Notas:

- `templates_create`/`templates_update` exigem o objeto `examples` (uma amostra real por variável; ausente → `400 TEMPLATE_EXAMPLES_REQUIRED`) e aceitam headers de mídia **apenas por URL** — base64 é exclusivo do REST.
- `templates_insights` (só leitura) devolve as métricas da Meta de um template via `GET /v1/templates/{id}/insights`: argumentos `id` e, opcional, `days` (`7`, `30` ou `90`; padrão `30`). Retorna os `totals` de enviadas/entregues/lidas, `readRate` (`null` quando nada foi entregue), os `clicks` por botão e a série `daily`, além do nome, status, categoria, idioma e `qualityScore` do template. Só templates da Meta têm insights: um template que não é da Meta falha com `409 TEMPLATE_NOT_ON_META`, e contas do WhatsApp Business App / coexistência falham com `422 TEMPLATE_INSIGHTS_UNAVAILABLE_SMB` (a Meta não fornece insights nesses casos — não tente de novo). A primeira chamada pode ativar os insights de templates da WABA na Meta. Exige chave de API com escopo de número.
- `templates_update` retorna `409 TEMPLATE_NOT_EDITABLE` quando a Meta não permite editar o template no estado atual (só templates rejeitados podem ser editados); o template guardado fica inalterado. Crie um novo template com a alteração ou envie o documento no momento do envio. [Editar](/pt-BR/api/templates#editar)
- `templates_submit` envia um template para aprovação da Meta (`POST /v1/templates/{id}/submit`, argumento `id`) e `templates_sync` traz o catálogo da WABA da Meta (`POST /v1/templates/sync`, sem argumentos, retorna `{ created, updated }`; `429 TEMPLATE_SYNC_IN_PROGRESS` enquanto outra sincronia do número roda). Os dois precisam de um número da Meta Cloud API (senão `422 TEMPLATE_REQUIRES_META_NUMBER`) e de uma credencial com escopo de número. [Enviar para a Meta](/pt-BR/api/templates#enviar-para-a-meta)
- `templates_delete` é destrutiva e pede confirmação com token: veja [Confirmação para ferramentas destrutivas](#confirmação-para-ferramentas-destrutivas). A Meta apaga pelo nome, então todas as versões de idioma desse nome na WABA são apagadas.
- `messages_send` suporta os três modos de envio: `templateId`, `text` ou mídia direta (`media` \+ `mediaType`; use `mediaType: "voice"` para nota de voz em qualquer número — `"audio"` chega como arquivo de áudio em números oficiais e como nota de voz em números não oficiais).
- `messages_send` com `mediaType: "audio"` ou `"voice"` aceita `media` **só como URL http(s) pública** de um arquivo de áudio real. Um data URI em base64 para áudio ou voz — ou qualquer mídia `data:audio/*`, seja qual for o `mediaType` — é recusado com `400 MCP_AUDIO_URL_REQUIRED` antes de qualquer envio: nenhuma mensagem é criada. Data URIs de imagem e documento continuam aceitos, para um arquivo que o usuário de fato anexou. A regra vale só no MCP — no `/mcp`, no [Code Mode](/pt-BR/integrations/mcp-code-mode) e no agente de IA do app; a [API REST](/pt-BR/api/messages/send) continua aceitando áudio como data URI. Ela existe porque modelos inventam base64 de áudio: esses bytes não são um arquivo reproduzível, e o envio falhava depois com [`MEDIA_TRANSCODE_FAILED`](/pt-BR/api/messages/log-error-codes#preparação-de-mídia-em-números-oficiais).
- `messages_send` aceita `markRead: false` para responder em número oficial (Meta) sem o indicador "digitando" e sem marcar a conversa como lida — para um agente cujas respostas uma pessoa ainda precisa encontrar não lidas. O padrão do número é o `markReadOnSend` em `numbers_settings_update` / `numbers_create`. `messages_typing` em número Meta marca a conversa como lida, então esse agente não deve chamá-lo. [Confirmação de leitura e digitando](/pt-BR/api/messages/send#confirmação-de-leitura-e-digitando)
- `messages_send` aceita um `idempotencyKey` opcional (até 255 caracteres), enviado no header `Idempotency-Key`. Durante 24 horas, chamá-la de novo com a mesma chave e os mesmos argumentos devolve a primeira resposta aceita sem enviar de novo — assim, um agente que tenta de novo depois de um timeout não manda a mensagem duas vezes ao contato. A mesma chave com argumentos diferentes dá `409 IDEMPOTENCY_KEY_REUSED`; enquanto a primeira chamada ainda está em andamento, `409 IDEMPOTENCY_KEY_IN_USE`. Derive a chave do que torna o envio único (ex.: id do pedido \+ destinatário). [Idempotência](/pt-BR/api/messages/send#idempotência)
- `messages_unread_counts` (só leitura) devolve a contagem de mensagens recebidas não lidas **por número** numa só chamada via `GET /v1/messages/unread/counts` — use-a em vez de chamar `messages_unread` uma vez por número. Omita `whatsappNumberIds` para todos os números que a credencial enxerga; cada `total` é igual ao `total` de `messages_unread` para aquele número. Devolve `{ byNumber: [{ whatsappNumberId, number, displayName, total }], total }`.
- Mídia recebida: em números META, passe `media.id` para `media_get`; em números não oficiais (Pilot Status web), use `media.url` diretamente.
- `numbers_delete` é um soft delete de 30 dias, desfeito com `numbers_restore`. `numbers_purge` exclui um número de forma permanente e irreversível; com token OAuth, só o OWNER do workspace pode chamá-la.
- `numbers_pay` paga a cobrança pendente do número extra de um número e libera o envio por ele (`POST /v1/numbers/{id}/pay`) — havendo saldo ou cartão, cobra na hora. Exige uma chave com escopo de tenant com `billing:manage`; com token OAuth, só o OWNER do workspace tem essa permissão.
- `leads_list` e `leads_get` leem os leads captados dos Formulários Instantâneos do Meta Lead Ads (Facebook/Instagram) nas Páginas do Facebook vinculadas ao número de WhatsApp da chave, e exigem uma chave com escopo de número. `leads_get` recebe o `id` do lead na Pilot Status, devolvido por `leads_list`, e não o `leadgenId` da Meta. `consentGiven` tem três estados: `true` (marcou a caixa de consentimento do WhatsApp), `false` (deixou desmarcada) e `null` (desconhecido — nunca é recusa nem consentimento). Um lead ocultado (`redacted: true`, por exemplo num número RELAY_ONLY) continua contando, com `fullName`, `email` e `phone` nulos. As duas usam os endpoints REST documentados em [`GET /v1/leads`](/pt-BR/api/leads).
- Configuração de anúncios e do Lead Ads da Meta: `ads_accounts_*`, `lead_pages_*` e `lead_forms_*` exigem a permissão `integrations:manage` (ADMIN ou OWNER do workspace), leituras incluídas; `ads_summary` exige `analytics:read`, que todo papel tem, e não traz conteúdo de conversa. Não há etapa de login: o acesso vem do compartilhamento de parceiro — o anunciante adiciona o portfólio empresarial da Pilot Status (`partnerBusinessId`) como parceiro no Meta Business Manager. `ads_accounts_*` recebem uma credencial da conta inteira; as ferramentas do Lead Ads e `ads_summary` veem o workspace todo com uma credencial da conta inteira e só o número vinculado com uma chave com escopo de número. `lead_pages_unlink` APAGA todo lead captado pelo vínculo e as configurações de formulário dele (irreversível). Com `autoSendEnabled: true`, `lead_forms_update` faz a plataforma mandar mensagem automaticamente a todo lead novo, sem um humano. `ads_summary` devolve `conversations` (conversas distintas) e `messages` separadamente, mais `leadCount` por anúncio, com limite de 200 anúncios (`truncated`). Elas usam os endpoints REST documentados em [Anúncios](/pt-BR/api/ads) e [Páginas do Lead Ads](/pt-BR/api/lead-pages).
- `webhooks_create` e `webhooks_update`: `"*"` assina todos os eventos, menos `lead.received`, que é opcional — liste-o pelo nome (por exemplo `["*", "lead.received"]`). Veja [`lead.received`](/pt-BR/api/webhooks/events#payload-de-lead).
- `webhooks_create` devolve o `secret` de assinatura em claro **uma única vez**, na criação; nenhuma leitura o devolve de novo. `webhooks_rotate_secret` gera um novo (também é o jeito de assinar um webhook criado antes de 2026-09-15): ele vem uma única vez, e o anterior para de valer na hora, sem janela de transição — guarde-o antes de qualquer outra coisa. Veja [Verificar a assinatura](/pt-BR/api/webhooks/configure#verifique-a-assinatura).
- `webhooks_reactivate` retoma um webhook parado pela pausa automática e libera os eventos retidos; chamar num webhook que já está entregando não faz nada.
- As ferramentas de linhas telefônicas aceitam só credencial com escopo de tenant. As ferramentas `phone_lines_verification_*` são exclusivas do OWNER (`phone_lines:purchase`); `phone_lines_verification_start` exige um `idempotencyKey` (enviado no header `Idempotency-Key`). `phone_lines_activation_audio` devolve os metadados e a URL de download da gravação, nunca o áudio em si.
- As ferramentas `phone_lines_webhooks_*` gerenciam os [webhooks das linhas](/pt-BR/api/phone-lines/webhooks), um cadastro próprio que recebe só eventos `phone_line.*` (os webhooks de número de `webhooks_*` nunca os recebem). Só credencial com escopo de tenant; `phone_lines:webhooks` (ADMIN ou OWNER do workspace). `phone_lines_webhooks_list` devolve também `events`, o catálogo de eventos assináveis: `events` recebe uma lista não vazia deles, ou `["*"]` para todos os eventos das linhas. `phone_lines_webhooks_create` devolve o segredo de assinatura `plwh_` **uma única vez** — guarde-o na hora: ele não pode ser lido de novo e não há rotação. Numa conexão OAuth, cada criação fica registrada na auditoria ([veja abaixo](#segredos-e-chaves-de-api-por-oauth)). Não é idempotente: cada chamada cria outro webhook. `phone_lines_webhooks_update` com `active: false` pausa um webhook; `phone_lines_webhooks_delete` o remove, com o histórico de entregas, de forma permanente. `phone_lines_webhooks_deliveries_list` nunca traz o payload; `phone_lines_webhooks_deliveries_get` o devolve como foi assinado, e num `phone_line.code_received` ele contém o código de ativação.
- `billing_checkout` aceita um `method` opcional: `card` (padrão) devolve uma `url` de checkout hospedado; `pix` (só workspaces em BRL; senão `400 PIX_NOT_ELIGIBLE`) devolve `orderId` e `pix { transactionId, copyPaste, qrCode, expiresAt }` para o usuário pagar no app do banco. `successUrl`/`cancelUrl` valem só para cartão (`400 FIELD_NOT_APPLICABLE` com `pix`). Nada é cobrado até uma pessoa pagar. `billing_topups_get` lê o pedido de recarga por esse `orderId` — `status` `pending`, `paid` (carteira creditada), `expired` ou `failed` — sem chamar o provedor de pagamento. Os endpoints de Stripe Elements (`/v1/billing/card/setup-intent*`, `/v1/billing/payment-intents*`) não têm ferramenta: o `clientSecret` deles só serve ao Stripe.js no navegador. Veja [Carteira e cartão pela API](/pt-BR/api/wallet-and-card).
- As ferramentas `workspace_webhooks_*` gerenciam os [webhooks do workspace](/pt-BR/api/workspace-webhooks) (`/v1/workspace/webhooks*`): o mesmo cadastro de `phone_lines_webhooks_*` (mesmas linhas, segredo `plwh_`, assinatura e entregas), com mais eventos — todos os `phone_line.*` e mais `wallet.topup_paid` (uma recarga da carteira foi creditada). `"*"` continua significando só os eventos das linhas: `wallet.topup_paid` é opcional, liste-o pelo nome (por exemplo `["*", "wallet.topup_paid"]`). Só credencial com escopo de tenant; `phone_lines:webhooks` (ADMIN ou OWNER do workspace). `workspace_webhooks_create` devolve o segredo de assinatura **uma vez**, como `phone_lines_webhooks_create` (numa conexão OAuth, registrado na auditoria).
- `workspace_update` (arg `name`, de 1 a 60 caracteres, sem espaços nas pontas) renomeia o workspace; `workspace_settings_get` (sem args) lê a moeda, o fuso horário, o idioma, o modo de cobrança e o preço de uma linha telefônica nova; `workspace_settings_update` (args `mainTimezone?` — um fuso IANA — e `mainLanguage?` — `pt`, `en` ou `es`) muda só esses dois campos: a moeda é alterada pelo proprietário no painel, e o modo de cobrança pela plataforma. Exigem credencial com escopo de tenant; com token OAuth, `workspace_update` e `workspace_settings_update` exigem ADMIN ou OWNER, e `workspace_settings_get` qualquer papel. Veja a [API de Workspace](/pt-BR/api/workspace#renomear-o-workspace).
- **`workspace_archive`, `workspace_transfer_ownership` e `workspace_members_remove` são destrutivas e exigem confirmação**, como `templates_delete`. A primeira chamada (sem `confirm_token`) não muda nada: lê `GET /v1/workspace` e `GET /v1/workspace/members` e devolve uma `preview` — o workspace e cada membro que perde o acesso (arquivar); o novo proprietário e o atual (transferir); o e-mail, o papel, os números do membro e o que ele perde (remover) — mais um `confirm_token` de uso único, válido por 5 minutos. Mostre a prévia ao usuário; só uma segunda chamada com os **mesmos argumentos** e esse token executa [`POST /v1/workspace/archive`](/pt-BR/api/workspace#arquivar-o-workspace), [`POST /v1/workspace/transfer-ownership`](/pt-BR/api/workspace#transferir-a-posse) ou [`DELETE /v1/workspace/members/{id}`](/pt-BR/api/workspace#remover-membro-que-criou-chaves-de-api). Argumentos diferentes dão `CONFIRM_TOKEN_MISMATCH`, um token reutilizado `CONFIRM_TOKEN_USED`, um expirado `CONFIRM_TOKEN_EXPIRED`. Se o servidor não consegue verificar que o token é de uso único, a chamada é recusada com `503 CONFIRM_TOKEN_STORE_UNAVAILABLE` e nada é executado — tente de novo.
  - As três são **só do proprietário** e exigem o token OAuth/MCP dele (arquivar e transferir também aceitam a chave de conta dele). Uma chave `ps_` de workspace ou de número recebe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE` (arquivar, transferir) ou `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS` (remover).
  - `workspace_archive` recebe `confirmName`, o nome do workspace digitado exatamente (diferencia maiúsculas); um nome diferente é recusado já na prévia com `400 CONFIRMATION_MISMATCH`, sem token. Arquivar tranca todo mundo do lado de fora, inclusive quem chamou, e não existe endpoint para desarquivar.
  - `workspace_transfer_ownership` recebe o `email` do novo proprietário (um membro que aceitou o convite; `NOT_A_MEMBER`, `TARGET_NOT_ACTIVE` e `ALREADY_OWNER` são recusados já na prévia). Você vira ADMIN e os refresh tokens OAuth dos dois usuários são revogados, então esta conexão precisa consentir de novo quando o access token expirar.
  - `workspace_members_remove` recebe `id` e, depois de um `409 MEMBER_HAS_API_KEYS`, `apiKeyAction` (`revoke` ou `keep`): esse 409 gasta o token e não remove ninguém, então peça uma prévia nova com a decisão.
  - O agente de IA do painel não oferece arquivar nem transferir.
- As ferramentas `workspaces_*` aceitam **só chave de conta** (`ps_account_…`, criada em Perfil → API, enviada no `x-api-key`): um token OAuth/de conector, uma chave de workspace ou de número recebe `403 ACCOUNT_KEY_REQUIRED`. `workspaces_list` lista os workspaces em que o usuário da chave é membro ativo, com o papel dele; `workspaces_create` cria um workspace do qual esse usuário é dono e devolve a chave principal **uma vez** (`409 WORKSPACE_LIMIT_REACHED` no teto do usuário); o argumento opcional `shareCard: true` vincula o novo workspace ao cartão de reserva do usuário, e ausente ou `false` o deixa sem compartilhar. `workspaces_shared_card_link` e `workspaces_shared_card_unlink` (argumento `workspaceId`) chamam o `PUT` e o `DELETE /v1/workspaces/{workspaceId}/shared-card`: exigem que o usuário seja OWNER daquele workspace, mudam quem paga as renovações dele e pedem confirmação. `workspaces_api_keys_list` (mascaradas), `workspaces_api_keys_create` (uma chave `ps_workspace_` com nome, devolvida uma vez; `409 WORKSPACE_KEY_LIMIT_REACHED`) e `workspaces_api_keys_revoke` (`409 PRIMARY_KEY_NOT_REVOCABLE` para a chave principal) exigem que o papel atual do usuário naquele workspace seja ADMIN ou OWNER; senão, `403 WORKSPACE_MEMBERSHIP_REQUIRED` ou `PERMISSION_DENIED`. O agente de IA do app não as oferece. Elas dispensam o `x-workspace-id`, assim como a `docs_search`; todas as outras ferramentas usadas com chave de conta exigem (veja [Com uma chave de conta](#com-uma-chave-de-conta)). Veja [Criar workspaces](/pt-BR/api/workspaces).
- `docs_search` recebe uma `query` — uma pergunta, palavras-chave ou um código de erro, em português ou inglês — e um `limit` opcional (3–5, padrão 5), e devolve `{ query, results, source }`: as 3–5 páginas mais relevantes desta documentação, cada uma com `title`, `url` e `description` (não o conteúdo da página). Ela lê o índice público da documentação (`llms.txt` e o sub-índice em pt-BR; as páginas do Playground ficam de fora), não chama nenhum endpoint `/v1` e não exige permissão, escopo de chave nem `whatsappNumberId` — por isso qualquer papel pode usá-la, e o agente do app a executa sem pedir confirmação. `source` é `live`, ou `fallback` quando o índice não pôde ser baixado e uma cópia embutida respondeu; o índice fica em cache por 6 horas. Use-a quando o usuário perguntar como fazer algo na Pilot Status, ou quando outra ferramenta devolver um código de erro — busque o código (ex.: `MEDIA_TRANSCODE_FAILED` leva a [Códigos de Erro do Log](/pt-BR/api/messages/log-error-codes)).
- `templates_delete` aceita um `force_local_delete` opcional: quando a Meta recusa a exclusão (`409 META_TEMPLATE_DELETE_REFUSED`, nada apagado), ele apaga só a cópia da Pilot Status e deixa o template na Meta. Use só depois que o usuário viu esse 409 e pediu a exclusão apenas local.
- Três ferramentas se recusam a rodar sem o booleano **`confirm: true`** (sem token, numa chamada só): `flows_publish` (publicar um Flow não tem volta; sem ele, `400 FLOW_PUBLISH_REQUIRES_CONFIRMATION`), `flows_endpoint_key_rotate` quando o número já tem uma chave registrada na Meta (substituí-la quebra todos os Flows `data_exchange` do número; sem ele, `400 FLOW_ENDPOINT_KEY_REQUIRES_CONFIRMATION`) e `subscription_extra_numbers_add` quando a compra converte um plano FREE em On Demand. Envie só depois que o usuário disser sim.
- A gestão de membros exige um **token OAuth** — não há usuário por trás de uma chave `ps_`, então a chave recebe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`: `workspace_members_invite` e `workspace_members_resend` (ADMIN ou OWNER; um ADMIN só atribui AGENT ou ANALYST), `workspace_members_set_numbers` (ADMIN ou OWNER), `workspace_members_update` e `workspace_members_remove` (só OWNER). A `workspace_members_list` (ADMIN ou OWNER) também funciona com chave de workspace. Ninguém vira OWNER por essas ferramentas: isso é a `workspace_transfer_ownership`.
- `billing_checkout` é da conta: exige o OWNER do workspace e uma concessão de **Toda a conta** (uma concessão OAuth por número não a usa).
- Rotas baseadas em token (endpoints públicos de remote-pairing, emissão de sessão de embed) são excluídas da lista de ferramentas porque usam um fluxo de autenticação diferente.

## Segredos e chaves de API por OAuth

Com o conector OAuth, o aplicativo pode fazer o que o painel faz — inclusive revelar e criar chaves de API e segredos — com estas salvaguardas:

1. **Chaves de API: só o proprietário do workspace, conferido a cada chamada.** Revelar ou criar uma chave de API `ps_` só funciona enquanto o usuário conectado for o **proprietário** do workspace. O papel é lido do workspace em cada chamada, e não do token nem do consentimento: se o proprietário transferir o workspace ou for removido, a chamada seguinte já é recusada.
2. **Segredos de assinatura: a mesma regra do painel.** Os segredos de assinatura de webhook (inclusive `plwh_`), o segredo do endpoint do Flow e o token de verificação da Meta vão para quem o painel permite — **administrador** ou **proprietário** do workspace.
3. **Registro de auditoria, para todos eles.** Toda revelação ou criação de chave ou segredo feita por OAuth fica registrada: quem (usuário), qual aplicativo (cliente OAuth), qual workspace, o quê (ação e alvo), quando e de qual IP. O valor nunca é registrado.
4. **Aviso na tela de consentimento.** O proprietário é avisado de que o aplicativo poderá ver segredos e criar chaves de API; o administrador, de que poderá ver segredos (chaves de API continuam só do proprietário).

| Ferramenta | O que revela ou cria | Quem, por OAuth |
| --- | --- | --- |
| `api_keys_list` | As chaves dos números, em claro | Só o proprietário; senão `403 OAUTH_SECRET_REQUIRES_OWNER` |
| `api_keys_regenerate_number` | Uma nova chave de número (`ps_number_…`) | Só o proprietário; senão `403 OAUTH_SECRET_REQUIRES_OWNER` |
| `webhooks_create`, `webhooks_rotate_secret` | Um segredo de assinatura de webhook | Administrador ou proprietário (`webhooks:manage`) |
| `workspace_webhooks_create`, `phone_lines_webhooks_create` | Um segredo de assinatura `plwh_` | Administrador ou proprietário (`phone_lines:webhooks`) |

`POST /v1/api-keys/regenerate` (a chave principal do workspace) segue a regra das chaves de API; `PUT`/`PATCH /v1/flows/{id}/endpoint` (o segredo do endpoint do Flow) e `POST /v1/numbers/meta` (o token de verificação da Meta) seguem a regra do painel. Se o registro de auditoria não puder ser gravado, o ato não passa sem registro: uma revelação ou rotação é recusada com `500 OAUTH_SECRET_AUDIT_UNAVAILABLE`, e uma criação ainda acontece, mas devolve `secret: null` com `secretWithheld: true` (rotacione para obter um novo).

<Warning>
  Uma chave ou um segredo obtido pelo conector **continua válido depois que você revoga o conector**: revogar encerra o acesso do aplicativo, não o que ele obteve. Para cortá-los, regenere as chaves na tela de [Chaves de API](/pt-BR/dashboard/api-keys) e rotacione os segredos. As chaves criadas por OAuth ficam registradas como criadas por você, então remover você do workspace oferece revogá-las.
</Warning>

Uma chave `ps_` clássica (`x-api-key`) não é afetada por essas regras. Criar workspaces e chaves de workspace nomeadas (`workspaces_*`) continua exigindo uma chave de conta.

## Confirmação para ferramentas destrutivas

Algumas ferramentas mudam coisas que não têm volta. Elas rodam em **duas chamadas**, e a segunda precisa de um token da primeira:

1. **Chame a ferramenta sem `confirm_token`.** Nada muda. A resposta é `status: "CONFIRMATION_REQUIRED"`, uma `preview` do que exatamente aconteceria e um `confirm_token` válido por **5 minutos**.
2. **Mostre a prévia à pessoa e espere um sim explícito.** Depois chame a ferramenta de novo com os **mesmos argumentos** e o `confirm_token`. Só esta chamada executa a ação.

```json Primeira chamada: prévia, nada apagado
{
  "status": "CONFIRMATION_REQUIRED",
  "preview": {
    "dry_run": true,
    "action": "DELETE_ON_META_AND_LOCAL",
    "template": { "id": "tpl_01HZX...", "name": "promo", "meta_language": "pt_BR", "meta_status": "APPROVED" },
    "waba": { "id": "1581714517011340", "name": "Acme" },
    "via_number": { "id": "wn_01HZX...", "number": "+5511999990000" }
  },
  "confirm_token": "pct1.eyJ0Ijo...",
  "expires_at": "2026-11-10T14:05:00.000Z",
  "next_step": "Nothing was changed. Show this preview to the user. …"
}
```

- O token é de uso único e fica preso à ferramenta, aos argumentos e à sua conexão (credencial, workspace e número). Outra ferramenta, outros argumentos, outra chave ou outro número não conseguem usá-lo.
- Recusas: `CONFIRM_TOKEN_EXPIRED` (peça uma nova prévia), `CONFIRM_TOKEN_MISMATCH` (repita exatamente os argumentos da prévia), `CONFIRM_TOKEN_USED` (a ação já rodou — não repita), `CONFIRM_TOKEN_INVALID` (peça uma nova prévia).
- Ferramentas com confirmação hoje: `templates_delete`, `workspace_archive`, `workspace_transfer_ownership` e `workspace_members_remove`. A API REST não precisa de token: chame `DELETE /v1/templates/{id}?dry_run=true` para ter a mesma prévia da exclusão de um template.
- No [Code Mode](/pt-BR/integrations/mcp-code-mode) valem as mesmas duas chamadas. No agente de IA do app, a prévia roda sozinha e o agente pede a sua confirmação para a segunda chamada.

## Erros comuns

- `401` — chave de API ausente ou inválida, ou sessão OAuth expirada: o cliente pede um novo login ([Conectar o seu cliente](#conectar-o-seu-cliente)).
- `403` — chave de número numa ferramenta da conta, ferramenta fora de uma concessão por número, ou papel que não pode chamar a ferramenta. Com um token OAuth ou uma chave de workspace, uma ferramenta de número chamada sem `whatsappNumberId` também é recusada.
- `WORKSPACE_ID_REQUIRED` — chave de conta sem `x-workspace-id` ([Com uma chave de conta](#com-uma-chave-de-conta)).
- `503 SHUTTING_DOWN` — a réplica que recebeu a requisição está reiniciando; tente de novo.
- `400` — argumentos de ferramenta inválidos (validados contra o schema da API subjacente).
- `400 MCP_AUDIO_URL_REQUIRED` — o `messages_send` recebeu um data URI (base64) com `mediaType` `audio`/`voice`, ou uma mídia `data:audio/*`. Envie o áudio como URL http(s) pública. A mensagem é bilíngue (`English | Português`) e nada foi enviado.
