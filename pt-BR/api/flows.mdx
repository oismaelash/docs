Todo endpoint abaixo autentica com uma **chave de API com escopo de número** (`x-api-key`) cujo número seja **Meta (API Oficial)**. A WABA é DERIVADA desse número — não existe parâmetro para nomear uma, de propósito.

| Permissão | Cobre |
| --- | --- |
| `flows:read` | Listar Flows e ler as respostas dos formulários |
| `flows:manage` | Toda escrita — criar, atualizar, subir JSON, publicar, depreciar, apagar — **e toda a superfície `data_exchange` (a chave do endpoint e o endpoint do Flow), leituras incluídas** |

<Warning>
  **Ler a chave do endpoint ou o endpoint do Flow exige `flows:manage`, não `flows:read`**, mesmo os dois sendo `GET`. As respostas carregam `endpointUrl` / `endpointUri` / `metaEndpointUri`, e o token dentro dessas URLs é uma **credencial**: a Meta se autentica no endpoint DECIFRANDO, e a pública correspondente é pública por construção. Quem tiver as duas consegue forjar uma requisição que o Pilot Status decifra e repassa ao seu webhook **com a nossa assinatura**. Credencial só de leitura continua sendo credencial — e é também por isso que o valor nunca aparece no `GET /v1/flows`.
</Warning>

<Note>
  `flows:read` é um slug próprio e **não** é `templates:read`. A listagem de templates devolve texto que o seu workspace escreveu; a resposta de um Flow devolve o que um **cliente** digitou num formulário — um nome, um telefone, às vezes um documento. As duas coisas são gateadas separadamente de propósito.
</Note>

## Listar Flows

```bash
curl "https://pilotstatus.com.br/v1/flows?page=1&pageSize=30" \
  -H "x-api-key: ps_sua_chave_aqui"
```

```json
{
  "flows": [
    {
      "id": "flw_local_1",
      "metaFlowId": "1122334455",
      "name": "Agendamento",
      "metaStatus": "PUBLISHED",
      "categories": ["APPOINTMENT_BOOKING"],
      "jsonVersion": "7.1",
      "healthStatus": "AVAILABLE",
      "clonedFromFlowId": null,
      "supersededByFlowId": null,
      "createdAt": "2026-08-30T12:00:00.000Z",
      "updatedAt": "2026-09-01T09:12:00.000Z"
    }
  ],
  "total": 1, "page": 1, "pageSize": 30
}
```

<Note>
  `id` é o **id local** e é o único id que você manda de volta para nós. `metaFlowId` é o da Meta e é somente leitura — vem `null` enquanto o Flow existe aqui e ainda não chegou à Meta.
</Note>

## Criar ou clonar

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows" \
  -H "x-api-key: ps_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Agendamento v2",
    "categories": ["APPOINTMENT_BOOKING"],
    "cloneFromFlowId": "flw_local_1"
  }'
```

Devolve `201` com o Flow novo em `DRAFT`. Omita `cloneFromFlowId` para começar do zero.

<Warning>
  `cloneFromFlowId` é o **id local** do Flow de origem — o campo `id`, não o `metaFlowId`. Clonar é a única forma de mudar um Flow que já foi publicado.
</Warning>

## Renomear e recategorizar

```bash
curl -X PATCH "https://pilotstatus.com.br/v1/flows/flw_local_1" \
  -H "x-api-key: ps_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Agendamento (matriz)", "categories": ["APPOINTMENT_BOOKING"] }'
```

Aceita **apenas** `name` e `categories`. Nunca publica e nunca deprecia — essas têm endpoint próprio, para um engano num formulário não alcançar uma operação irreversível.

## Subir o Flow JSON

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows/flw_local_1/json" \
  -H "x-api-key: ps_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{ "flowJson": "{\"version\":\"7.1\",\"screens\":[...]}" }'
```

Um `200` significa que o documento compilou, e aí `validationErrors` vem sempre vazio:

```json
{ "validationErrors": [] }
```

Documento que a Meta recusa volta como **`422` `FLOW_JSON_INVALID`**, com a lista dela anexada:

```json
{
  "error": "A Meta recusou este Flow JSON. Veja validationErrors.",
  "errorEN": "Meta rejected this Flow JSON. See validationErrors.",
  "code": "FLOW_JSON_INVALID",
  "validationErrors": [ { "error": "...", "line_start": 12, "message": "..." } ]
}
```

<Warning>
  **Isto NÃO é como a API da Meta se comporta, de propósito — e a diferença é o ponto.**

  A Meta responde `200` com os problemas listados _dentro_ do payload. Ou seja: lá, sucesso aparente sobre documento inválido é o caso normal, e um cliente que olha só o status publica um Flow que nunca compilou.

  Esta rota lê a LISTA em vez do status da Graph, e responde `422` sempre que ela não está vazia. Um `200` nosso significa, então, o que um `200` deve significar. Leia `validationErrors` no `422` — é a resposta da Meta, verbatim.

  `flowJson` é uma **string**, nunca um objeto aninhado: a Meta compila os bytes exatos, e re-serializar reordenaria em silêncio o que você escreveu.
</Warning>

<Note>
  Cada item de `validationErrors` é da Meta, verbatim — `error`, `error_type`, `message` e `pointers` nomeando os componentes recusados. Um que você vai encontrar se um Flow coleta arquivos é o `COMPONENT_TYPE_MAX_NUMBER_PER_SCREEN`: no máximo um `PhotoPicker` **ou** `DocumentPicker` por tela. Veja [Flows](/pt-BR/concepts/flows) com ele citado por inteiro. O SDK de Node lê o array com `flowJsonValidationErrors(err)`.
</Note>

## Publicar

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows/flw_local_1/publish" \
  -H "x-api-key: ps_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{ "confirm": true }'
```

<Warning>
  **Irreversível na Meta.** Um Flow publicado nunca mais pode ser editado nem despublicado — só clonado num novo. `"confirm": true` é obrigatório; sem ele a requisição é recusada com `400`.
</Warning>

## Depreciar

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows/flw_local_1/deprecate" \
  -H "x-api-key: ps_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{ "supersededByFlowId": "flw_local_2" }'
```

Aposenta o Flow sem apagar, e sem apagar as respostas já enviadas. `supersededByFlowId` é opcional — mas, se você mandar, tem de nomear um Flow real seu: string vazia é recusada em vez de ignorada em silêncio, porque cadeia de versões rompida é invisível depois.

## Apagar

```bash
curl -X DELETE "https://pilotstatus.com.br/v1/flows/flw_local_1" \
  -H "x-api-key: ps_sua_chave_aqui"
```

Só um `DRAFT` pode ser apagado. Qualquer outro estado devolve `409`.

## Ler as respostas dos formulários

```bash
curl "https://pilotstatus.com.br/v1/flows/flw_local_1/responses?page=1&pageSize=30" \
  -H "x-api-key: ps_sua_chave_aqui"
```

Devolve o que os clientes enviaram, ligado ao contato que respondeu, dentro da janela de retenção. Resposta vencida nunca é servida.

Num Flow `data_exchange` as respostas chegam **tela a tela**, e é em `submitted` que elas ficam — uma entrada por troca, da mais antiga para a mais nova:

```json
{
  "submitted": [
    {
      "screen": "WELCOME_SCREEN",
      "at": "2026-09-06T16:08:12.616Z",
      "data": { "observacao": "Aobaaa" },
      "omitted": null
    }
  ]
}
```

| Campo | Significado |
| --- | --- |
| `screen` | A tela de onde veio aquela troca, com o nome que a Meta deu. String, ou `null` quando a Meta não nomeou nenhuma. |
| `at` | ISO 8601 — quando deciframos aquela troca, minutos antes da submissão que criou a resposta em volta dela. |
| `data` | O objeto já parseado que a pessoa mandou naquela tela. `null` exatamente quando o `omitted` diz o motivo. |
| `omitted` | `"DATA_TOO_LARGE"`, `"LIMIT_REACHED"`, `"UNREADABLE"` ou `null` — são **três** motivos, não dois. Uma entrada ou traz `data` com `omitted: null`, ou traz `data: null` e o motivo. Não existe terceira forma. |

<Warning>
  **Num Flow `data_exchange`, o `response` é o lugar vazio — o que a pessoa digitou está aqui.** O `response` é o `nfm_reply` da Meta, parseado, e num Flow com endpoint esse reply carrega **só o `flow_token`** — `{"flow_token":"a1b2c3…"}` — enquanto o seu próprio endpoint recebeu `{"observacao":"Aobaaa"}` na mesmíssima submissão. Quem lê o `response` ali encontra um token e conclui que a pessoa não enviou nada.

  Num Flow **sem** endpoint vale o contrário: não há trocas para capturar, `submitted` vem `[]`, e os componentes de texto livre chegam no `response` exatamente como sempre chegaram.
</Warning>

<Warning>
  **Aqui o `submitted` é sempre um array — `[]` quando não há nada, nunca `null`.** ⛔ No webhook `flow.response_received` o mesmo campo é o contrário: `null`, nunca `[]`. Isso não é uma inconsistência à espera de ser arrumada, e "o mesmo campo se comporta igual nas duas superfícies" é justamente a suposição que mais custa caro. As duas resolvem problemas diferentes.

  **Nesta superfície de leitura** o valor vem de uma busca que responde *nada* para uma submissão sem trocas capturadas — e um campo posto a nada **desaparece do JSON** em vez de chegar vazio. O `[]` é o que mantém a chave presente, e o que mantém "nada foi capturado" separado de "não conseguimos olhar".

  **No evento** o payload também é guardado, e o redator só apaga um campo que tenha algo dentro. Um array vazio ali voltaria como o marcador de "conteúdo indisponível" e seria lido como *"havia respostas e nós escondemos"* — então lá o valor honesto é `null`.

  Portanto ramifique por `submitted.length` aqui e por `submitted !== null` no evento. Nenhuma das duas grafias é prova de que a pessoa não digitou nada. O `media` logo abaixo segue a regra desta superfície também: sempre um array, `[]` quando nada foi anexado.
</Warning>

<Note>
  **A lista é mais curta do que as trocas que o seu endpoint respondeu, e está certa assim.** Só as trocas `data_exchange` são capturadas. O `INIT` carrega o estado que **nós** semeamos — os params mandados no envio, devolvidos de volta — e o `BACK` é navegação; nenhum dos dois é algo que uma pessoa digitou. Contar as entradas contra os seus próprios traços e reportar a diferença como perda é justamente o engano que este parágrafo existe para evitar.

  **É a requisição que a Meta manda para nós, nunca o que o seu endpoint respondeu.** O `data` que você devolve no `SUCCESS`, `extension_message_response` incluído, é cifrado de volta para a Meta e não é anotado em lugar nenhum do Pilot Status — nem aqui, nem em nenhuma outra superfície.

  **É append-only, e não há deduplicação.** Quem volta uma tela e envia de novo produz uma segunda entrada legítima em vez de substituir a primeira, e o `at` é o que separa duas passagens sob um mesmo `flow_token`.
</Note>

<Warning>
  **Nada é truncado em silêncio — entrada sem conteúdo diz o porquê.** Uma troca grande demais mantém a linha e o lugar dela na ordem e diz `DATA_TOO_LARGE`; uma que não deu para ler diz `UNREADABLE`. O teto de **50 trocas** por formulário fecha a lista com uma entrada final dizendo `LIMIT_REACHED`, e nada depois dela foi guardado. O teto de tamanho — o que está por trás do `DATA_TOO_LARGE` — é medido em **bytes**, não em caracteres, então texto acentuado chega nele antes do que o comprimento sugere.
</Warning>

<Note>
  **Um número em `RELAY_ONLY` não guarda nada aqui** — nem entrada redigida, entrada nenhuma: não existe cópia guardada para redigir.

  **Estas entradas são podadas em 30 dias + 1, e o dia a mais não é arredondamento.** Uma troca é capturada enquanto a pessoa ainda está preenchendo o formulário, minutos antes da submissão que cria a resposta ao lado dela. Com 30 dias idênticos, as trocas venceriam primeiro, e uma resposta ainda sendo servida responderia `submitted: []` — indistinguível de um formulário em que ninguém digitou nada.
</Note>

Cada resposta traz um array `media` — os arquivos anexados dentro do formulário, re-hospedados por nós:

```json
{
  "media": [
    {
      "field": "documento",
      "fileName": "carteira.jpg",
      "mimeType": "image/jpeg",
      "sizeBytes": 184320,
      "status": "STORED",
      "url": "https://media.pilotstatus.com.br/public/tenants/.../flow-media/....jpg"
    }
  ]
}
```

| Campo | Significado |
| --- | --- |
| `field` | A chave sob a qual o arquivo veio — o nome que o **autor do Flow** deu ao componente. Não é palavra reservada nem tipo. |
| `fileName` | O nome que o aparelho de quem enviou reportou — e **nunca `null`**. Foto tirada na câmera não reporta nome nenhum, e aí entra o **nome do próprio campo**, então um `fileName` igual ao `field` pode ser um ou o outro e os dois são indistinguíveis. |
| `mimeType` | Detectado pelos **bytes** já descriptografados, nunca pelo nome do arquivo. `null` até ficar guardado. |
| `sizeBytes` | Tamanho do arquivo descriptografado. `null` até ficar guardado. |
| `status` | `PENDING` enquanto a transferência está em curso, depois `STORED` ou `FAILED`. |
| `url` | Um link estável nosso, **presente assim que a linha existe** — inclusive com `status` em `PENDING`. É opaco: busque, nunca monte um. |

<Note>
  **Aqui `media` é sempre um array — vazio quando não houve anexo — e isso deliberadamente não é o que o webhook faz.** O `flowMedia` do `flow.response_received` é `null` em vez de `[]`, porque o redator de armazenamento só troca um campo que tem algo dentro, e um array vazio seria lido como "houve anexos e nós escondemos". Ela também traz `sizeBytes`, que o evento não traz.

  **`[]` não é prova de que não havia arquivo.** O join dos anexos é best-effort de propósito — um anexo que não conseguimos ler custa um *campo*, nunca a página — então um join que falha deixa **todas as linhas daquela página com `media: []`**, ou seja, "não conseguimos olhar" servido como "não tinha nada". Reconcilie um Flow que coleta arquivos contra algo que você mesmo guardou.

  **É aqui que o *registro* é definitivo — a URL já era definitiva no evento.** A re-hospedagem é assíncrona: o evento é emitido assim que a submissão é gravada, e a transferência roda depois dele, então o evento normalmente chega antes de os bytes estarem no lugar. O `url` é um link para uma rota nossa e está presente durante tudo isso, também numa linha `PENDING` — buscá-lo espera pelo arquivo e então o entrega, e só responde `404` com o cabeçalho `Retry-After` se essa espera estourar. Ou seja: releia este endpoint para ter `status`, `mimeType` e `sizeBytes`, não para obter uma URL que o evento já te deu. O `url` só vem `null` quando a instalação não tem segredo de assinatura (aí ela cai na URL direta do objeto assim que o `status` for `STORED`), quando a Meta não mandou `media_id`, ou num número `RELAY_ONLY`.
</Note>

<Warning>
  **O objeto guardado fica numa URL pública — quem tem o link lê o arquivo.** É uma decisão explícita do dono, e a mesma propriedade que o `mediaLink` de entrada tem. Não existe `cdn_url` nem `encryption_metadata` nesta superfície nem em nenhuma outra: a Meta deriva uma chave AES por arquivo, e nem a chave nem a referência do CDN são guardadas ou publicadas.

  O tipo de conteúdo vem dos bytes e nunca é `text/html` nem `image/svg+xml`, com os bytes parecendo o que parecerem — os dois executariam script na origem que os serve.

  **E a cópia não vence.** Respostas, sessões e traços do endpoint são podados por uma janela de retenção; o arquivo não. `flow_media_assets` não tem coluna de expiração e nada na plataforma apaga a linha nem o objeto, então o link continua funcionando depois que a resposta a que ele pertencia já parou de ser servida aqui.
</Warning>

<Note>
  **Esta é a cópia armazenada, não a ao vivo.** Para receber as submissões conforme chegam, assine o evento de webhook `flow.response_received` — as respostas vêm nele, já parseadas. A mensagem de chat que carrega uma submissão traz só o rótulo da Meta (`Enviado` / `Sent`), então um webhook assinado apenas em `messages` não vê nada. Veja [Receber as respostas de um Flow](/pt-BR/guides/flow-responses).
</Note>

<Warning>
  **Uma página curta pode ser uma página truncada — e ela avisa.** `FlowResponse` não tem coluna `flowId` — a única aresta do Flow para as respostas passa pelo token da sessão — então uma requisição correlaciona no máximo **10.000** envios daquele Flow. Passando desse teto, o payload traz `"notice": "FLOW_RESPONSES_WINDOW_TRUNCATED"` ao lado dos normais `responses`/`total`/`page`/`pageSize`/`totalPages`.

  É um **`200`**, não um erro, e o campo some quando nada foi cortado. Leia: quem reconcilia contra uma página curta sem olhar o `notice` conclui que perdeu envios.
</Warning>

## Chave do endpoint `data_exchange`

<Note>
  Só é necessária para Flows cujas telas chamam o seu backend — veja [Conecte a sua API a um Flow](/pt-BR/guides/flow-data-exchange) para o quadro completo. `{numberId}` é o número ao qual a sua chave está amarrada. A chave privada nunca sai do Pilot Status e não é devolvida por endpoint nenhum; `endpointUrl` é a base para registrar no seu Flow, com o id do Flow acrescentado como segmento final.

  **A chave é por número; a URL de encaminhamento é por Flow.** As duas têm superfície aqui — a chave logo abaixo, a URL em [Endpoint do Flow](#endpoint-do-flow) — e nenhuma das duas aparece no `GET /v1/flows`, de propósito: uma chave de API pode ser uma aplicação de terceiros, e o endereço do seu webhook interno não é algo que uma integração somente-leitura tenha direito de receber.
</Note>

<Note>
  **As duas rotas agem sobre o número da própria chave, e o `{numberId}` do caminho tem de bater com ele.** Uma chave escopada por número já nomeia o seu; uma chave de conta precisa estreitar com `x-whatsapp-number-id`. Um id de caminho que não bate responde `404` `FLOW_NUMBER_NOT_FOUND` — nunca `403`, e o mesmo corpo quer o id seja de outro tenant, quer seja de outro número seu, para que um palpite errado não aprenda nada.

  `uploadedAt` é `null` quando um par foi gerado aqui mas a Meta nunca aceitou. Isso não é o mesmo que não ter chave, e é o estado que um `POST` repetido RETOMA em vez de substituir.
</Note>

### Ler o estado atual

```bash
curl "https://pilotstatus.com.br/v1/numbers/{numberId}/flow-endpoint-key" \
  -H "x-api-key: ps_sua_chave_aqui"
```

```json
{
  "configured": true,
  "publicKey": "-----BEGIN PUBLIC KEY-----\n...",
  "uploadedAt": "2026-09-02T10:00:00.000Z",
  "endpointUrl": "https://pilotstatus.com.br/api/flows/endpoint/AbC123...",
  "metaStatus": "VALID"
}
```

| `metaStatus` | Significado |
| --- | --- |
| `VALID` | A Meta tem a chave que nós temos. Nada a fazer. |
| `MISMATCH` | A Meta tem uma chave **diferente**. Todo Flow `data_exchange` deste número está falhando — rotacione. |
| `NOT_SET` | A Meta ainda não tem chave para este número. |
| `UNKNOWN` | Não conseguimos ler o lado da Meta. |

<Warning>
  **`UNKNOWN` não é `NOT_SET`, e juntar os dois sai caro.** Uma chamada que falhou não diz nada sobre o que a Meta tem. Tratá-la como "sem chave" leva a rotacionar — e rotacionar substitui uma chave que provavelmente estava boa.
</Warning>

### Gerar, rotacionar ou importar

Um `POST`, dois verbos. **A presença de `privateKey` decide qual**, e eles não são intercambiáveis: gerar registra uma chave pública nova na Meta e substitui o que estava lá; importar não registra nada.

| Corpo | O que faz |
| --- | --- |
| `{}` | **Gerar** — cria um par RSA-2048, guarda a metade privada cifrada e registra a pública na Meta. |
| `{"privateKey": "-----BEGIN PRIVATE KEY-----\n…"}` | **Importar** — guarda a chave que você já tem. Nada é registrado na Meta. |
| `{"privateKey": "…", "passphrase": "…"}` | Importa um PEM protegido por passphrase. |
| `{…, "confirm": true}` | Obrigatório quando qualquer um dos dois verbos substituiria uma chave **viva** na Meta. |

Só `confirm`, `privateKey` e `passphrase` são aceitos; qualquer outro campo é recusado, nunca ignorado. A resposta é a forma de leitura acima mais `"replaced"`, que diz se uma chave que estava viva acabou de ser deslocada — um `200` sozinho não diz.

```bash
# Gerar
curl -X POST "https://pilotstatus.com.br/v1/numbers/{numberId}/flow-endpoint-key" \
  -H "x-api-key: ps_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{}'
```

```bash
# Importar
curl -X POST "https://pilotstatus.com.br/v1/numbers/{numberId}/flow-endpoint-key" \
  -H "x-api-key: ps_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{ "privateKey": "-----BEGIN PRIVATE KEY-----\nMIIEvQIBADAN...\n-----END PRIVATE KEY-----\n" }'
```

<Warning>
  **Substituir uma chave VIVA exige `{"confirm": true}`, nos dois verbos.**

  Gerar é destrutivo na Meta: ela guarda exatamente uma pública por número, então registrar outra substitui a anterior — e a privada antiga é sobrescrita aqui no mesmo instante. Não dá para restaurar, e toda troca `data_exchange` em voo naquele número para de decifrar.

  Importar é destrutivo **aqui**: nada muda na Meta, mas a metade privada guardada é substituída, e se a Meta não conseguir confirmar a nova o número fica com uma chave que pode não decifrar nada. Por isso os dois são recusados com códigos diferentes — `FLOW_ENDPOINT_KEY_REQUIRES_CONFIRMATION` e `FLOW_ENDPOINT_KEY_IMPORT_REQUIRES_CONFIRMATION` — porque quem lesse "isto substitui o seu registro na Meta" depois de uma importação iria conferir na Meta uma mudança que nunca aconteceu.

  ⚠️ A **primeira** configuração NÃO pede confirmação, e retentar uma chave que a Meta nunca aceitou (`uploadedAt: null`) também não — não há o que destruir em nenhum dos dois casos. Confirmação exigida onde nada se perde treina o reflexo que a desarma no único caso em que ela protege.
</Warning>

<Note>
  **Uma importação é verificada antes de ser guardada.** Derivamos a metade pública da chave enviada e comparamos com a da Meta: coincidiu, é guardada e carimbada (`metaStatus: "VALID"`); **divergiu, é recusada de saída** com `FLOW_ENDPOINT_KEY_IMPORT_MISMATCH` e nada é gravado; se não conseguimos fazer a chamada ao Graph, a chave fica guardada com `uploadedAt: null` e `metaStatus` `UNKNOWN`/`NOT_SET` — que é o estado "não confirmada", não uma falha.
</Note>

<Warning>
  **`passphrase` é usada uma vez e não é guardada.** Ela abre o PEM; a chave passa a ser mantida normalizada e cifrada em repouso, e depois disso a passphrase não tem mais leitor. Guarde a sua própria cópia — não conseguimos devolvê-la. Envie só quando a chave tiver uma (string vazia é uma passphrase, não a ausência de uma), e nunca sozinha: `passphrase` sem `privateKey` é recusada com `FLOW_ENDPOINT_KEY_PASSPHRASE_ORPHAN`, porque senão essa mesma requisição **geraria** um par e substituiria o seu registro na Meta.
</Warning>

## Endpoint do Flow

Para onde as trocas já decifradas de um Flow `data_exchange` são encaminhadas. Por **Flow**, `flows:manage` em todos os verbos inclusive no `GET`, e `{flowId}` é o id **local** do `GET /v1/flows`.

Um caminho, dois atos diferentes. O `GET` lê esse estado e o `PUT` / `PATCH` guardam o **seu** destino; nenhum dos três fala com a Meta. O `POST` registra o **nosso** proxy como `endpoint_uri` do Flow **na Meta**.

```bash
curl "https://pilotstatus.com.br/v1/flows/{flowId}/endpoint" \
  -H "x-api-key: ps_sua_chave_aqui"
```

```bash
curl -X PUT "https://pilotstatus.com.br/v1/flows/{flowId}/endpoint" \
  -H "x-api-key: ps_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{ "url": "https://api.sua-empresa.com/flows/agendamento" }'
```

```bash
# Registra o NOSSO proxy como endpoint_uri deste Flow na Meta
curl -X POST "https://pilotstatus.com.br/v1/flows/{flowId}/endpoint" \
  -H "x-api-key: ps_sua_chave_aqui"
```

```json
{
  "flowId": "flw_local_1",
  "url": "https://api.sua-empresa.com/flows/agendamento",
  "hasSecret": true,
  "endpointUri": "https://pilotstatus.com.br/api/flows/endpoint/AbC123.../1122334455",
  "metaEndpointUri": null,
  "drift": false,
  "numberHasKey": true,
  "numberKeyUploadedAt": "2026-09-02T10:00:00.000Z",
  "warnings": ["FLOW_ENDPOINT_META_URI_UNKNOWN"],
  "secret": "9f2c…"
}
```

| Campo | Significado |
| --- | --- |
| `url` | O seu destino. `null` quando o Flow não tem nenhum. |
| `hasSecret` | Se existe um segredo de assinatura. O segredo em si nunca é legível. |
| `endpointUri` | A **nossa** URL de proxy para este Flow — o valor que o `endpoint_uri` da Meta precisa ter. |
| `metaEndpointUri` | O que a Meta tem registrado, como a sincronização horária leu pela última vez. |
| `drift` | `true` só quando os dois são conhecidos e diferem — a Meta está chamando outra pessoa. |
| `numberHasKey` / `numberKeyUploadedAt` | O estado da chave do número ao qual esta credencial está vinculada. |
| `warnings` | Toda razão pela qual este Flow não vai funcionar. Trate o conjunto como aberto. |
| `secret` | **Só na resposta que o criou**, e nunca mais. |

<Note>
  Campos do corpo: `url` (obrigatório, `https://` ou um `null` explícito para limpar — nunca omitido) e `rotateSecret` (booleano). `PUT` e `PATCH` são a mesma operação. O número vem da credencial e é recusado no corpo (`FLOW_NUMBER_FROM_KEY`).

  **Salvar a URL não registra nada na Meta** — isso é um ato separado sobre um sistema separado, para que um rename não sequestre em silêncio um Flow já apontado para o endpoint de outra pessoa. `metaEndpointUri`, `drift` e `warnings` são como você enxerga a diferença.
</Note>

### Registrar o `endpoint_uri` na Meta

Um `POST` no mesmo caminho escreve `endpointUri` no `endpoint_uri` do Flow na Meta. O corpo é opcional; `confirmOverwrite` (booleano) é o único campo aceito, e o número vem da credencial como em todo o resto. A resposta é o mesmo estado acima **sem** `secret` — o `POST` nunca cria nenhum.

<Warning>
  **Um Flow `data_exchange` não pode ser publicado enquanto isso não for feito.** A Meta recusa o `publish` com *"Publishing without specifying 'endpoint_uri' is forbidden"*.
</Warning>

<Note>
  **É idempotente.** Um Flow que já aponta para nós responde `200` sem escrever nada na Meta. A verificação lê a Meta ao vivo em vez da coluna `metaEndpointUri` sincronizada de hora em hora, porque essa coluna é muda sobre uma URI registrada na última hora — exatamente a janela em que duas pessoas configuram o mesmo Flow.
</Note>

<Warning>
  **O `409 FLOW_ENDPOINT_URI_WOULD_OVERWRITE` nomeia o endpoint que você está prestes a deslocar**, em `currentEndpointUri`. O nosso não é ecoado — ele carrega o token de endpoint do número, que é a credencial do proxy.

  Reenviar com `{"confirmOverwrite": true}` assume o Flow, e **isso tira todas as trocas dele de quem responde hoje**. A escrita da Meta é uma sobrescrita simples: sem mesclagem, sem desfazer e sem aviso ao endpoint deslocado.
</Warning>

<Warning>
  **`secret` é mostrado exatamente uma vez, na requisição que o criou.** Ele é guardado cifrado e não há caminho de leitura de volta. `secret: null` numa gravação posterior quer dizer que já existia um e foi mantido — quem diz se existe algum é `hasSecret`. `{"rotateSecret": true}` cria um novo, e é a única saída para um segredo que vazou.
</Warning>

Passo a passo completo, incluindo o contrato que o seu endpoint precisa cumprir: [Conecte a sua API a um Flow](/pt-BR/guides/flow-data-exchange).

## Erros

Toda falha desta superfície responde o mesmo envelope — existe exatamente uma forma para ler, e uma grafia:

```json
{ "error": "<português>", "errorEN": "<inglês>", "code": "<CÓDIGO>" }
```

`FLOW_JSON_INVALID` acrescenta um array `validationErrors`; `FLOW_UNKNOWN_FIELDS` acrescenta as chaves recusadas; `FLOW_ENDPOINT_URI_WOULD_OVERWRITE` acrescenta `currentEndpointUri`. Nunca assuma que o conjunto de códigos é fechado — trate os que você conhece e caia no `code` para o resto.

| Código | Status | Significado |
| --- | --- | --- |
| `FLOW_NOT_FOUND` | 404 | Nenhum Flow com esse id dentro da WABA da sua chave |
| `FLOW_NOT_DRAFT` | 409 | O Flow saiu de `DRAFT` — clone para começar nova versão |
| `FLOW_REQUIRES_META_NUMBER` | 422 | O número da chave não é Meta, ou não tem WABA |
| `FLOW_NUMBER_FROM_KEY` | 400 | A requisição nomeou o número (`whatsappNumberId`, `numberId` ou `wabaId`, no corpo ou na query) — ele vem da chave, e nunca é aceito ao lado dela |
| `FLOW_JSON_INVALID` | 422 | A Meta recusou o documento — leia `validationErrors` |
| `FLOW_JSON_REQUIRED` | 400 | `flowJson` ausente ou vazio |
| `FLOW_NAME_REQUIRED` | 400 | `name` faltando na criação |
| `FLOW_NAME_INVALID` | 400 | `name` presente mas não é string utilizável |
| `FLOW_CATEGORY_INVALID` | 400 | Categoria fora do conjunto que a Meta aceita |
| `FLOW_CLONE_SOURCE_INVALID` | 400 | `cloneFromFlowId` não é um id local utilizável |
| `FLOW_PATCH_EMPTY` | 400 | `PATCH` sem `name` e sem `categories` |
| `FLOW_UNKNOWN_FIELDS` | 400 | O corpo trouxe campo que a rota não aceita |
| `FLOW_PUBLISH_REQUIRES_CONFIRMATION` | 400 | `publish` sem `"confirm": true` |
| `FLOW_DEPRECATE_INVALID_SUCCESSOR` | 400 | `supersededByFlowId` presente mas em branco ou desconhecido |
| `FLOW_ENDPOINT_KEY_REQUIRES_CONFIRMATION` | 400 | Gerar por cima de uma chave VIVA sem `"confirm": true` |
| `FLOW_ENDPOINT_KEY_IMPORT_REQUIRES_CONFIRMATION` | 400 | Importar por cima de uma chave VIVA sem `"confirm": true` |
| `FLOW_ENDPOINT_KEY_IMPORT_MISMATCH` | 400 | A chave importada não é a que a Meta tem registrada. **Nada foi gravado** |
| `FLOW_ENDPOINT_KEY_PASSPHRASE_REQUIRED` | 400 | O PEM está protegido por passphrase e nenhuma foi enviada |
| `FLOW_ENDPOINT_KEY_PASSPHRASE_WRONG` | 400 | A passphrase não abre a chave — a chave em si não foi rejeitada |
| `FLOW_ENDPOINT_KEY_PASSPHRASE_ORPHAN` | 400 | `passphrase` sem `privateKey`. Recusada, não ignorada: sem a chave, esta requisição **geraria** um par |
| `FLOW_ENDPOINT_KEY_PEM_INVALID` | 400 | `privateKey` ilegível como PEM, não é RSA, ou tem menos de 2048 bits |
| `FLOW_ENDPOINT_KEY_IMPORT_INVALID` | 400 | `privateKey` ou `passphrase` presentes mas não são string |
| `FLOW_ENDPOINT_KEY_UNAVAILABLE` | 500 | Nosso. A metade privada não pode ser guardada cifrada, e recusamos gerar em vez de guardá-la em claro |
| `FLOW_ENDPOINT_URL_REQUIRED` | 400 | `url` ausente ou inutilizável. Ela pode ser `null` **explicitamente**, nunca por omissão |
| `FLOW_ENDPOINT_URL_NOT_HTTPS` | 400 | O destino não é `https://`. A URL recusada não é ecoada de volta |
| `FLOW_ENDPOINT_ROTATE_INVALID` | 400 | `rotateSecret` não é booleano. `"true"` não é convertido |
| `FLOW_ENDPOINT_CONFIRM_INVALID` | 400 | `confirmOverwrite` não é booleano. `"false"` é uma string verdadeira, e é recusada em vez de lida como consentimento |
| `FLOW_ENDPOINT_URI_WOULD_OVERWRITE` | 409 | A Meta já aponta este Flow para outro endpoint — nomeado em `currentEndpointUri`. Reenvie com `confirmOverwrite: true` para assumir |
| `FLOW_ENDPOINT_NUMBER_HAS_NO_KEY` | 422 | O número não tem chave de endpoint de Flow, então não há URL para registrar na Meta. Gere a chave primeiro |
| `FLOW_ENDPOINT_SECRET_UNAVAILABLE` | 500 | Nosso. O segredo de assinatura não pode ser guardado cifrado, e encaminhar sem assinar não é opção |
| `FLOW_NUMBER_WABA_MISMATCH` | 422 | O número da chave não está na WABA dona deste Flow e nunca poderá enviá-lo |
| `FLOW_NUMBER_NOT_FOUND` | 404 | O número do caminho não é o número ao qual esta chave está amarrada |
| `FLOW_BODY_INVALID` | 400 | Corpo malformado, ou campo obrigatório faltando |
| `INVALID_PAGINATION` | 400 | `page` × `pageSize` além do teto de offset profundo |
| `INTERNAL_ERROR` | 500 | Nosso. Tente de novo e informe o código ao suporte |

<Note>
  Os dois últimos **não têm prefixo `FLOW_`** — são compartilhados por toda a API pública e mantêm a grafia global. Um cliente que filtre por `code.startsWith("FLOW_")` perderia os dois.
</Note>
