Doze endpoints em `/v1/workspace` espelham o que o painel faz com o próprio workspace (nome, configurações, posse, arquivamento) e com membros e convites. Os membros são ilimitados em todos os planos.

## Qual credencial funciona onde

Esta é a parte para ler antes de qualquer coisa.

| Endpoint | Chave de workspace / número (`x-api-key`) | Chave de conta (`ps_account_`) | Token OAuth |
|---|:---:|:---:|:---:|
| `GET /v1/workspace` | ✅ | ✅ | ✅ |
| `PATCH /v1/workspace` | ✅ ¹ | ✅ ² | ✅ ² |
| `GET /v1/workspace/settings` | ✅ ¹ | ✅ | ✅ |
| `PATCH /v1/workspace/settings` | ✅ ¹ | ✅ ² | ✅ ² |
| `POST /v1/workspace/transfer-ownership` | ❌ | ✅ ³ | ✅ ³ |
| `POST /v1/workspace/archive` | ❌ | ✅ ³ | ✅ ³ |
| `GET /v1/workspace/members` | ✅ | ✅ | ✅ |
| `POST /v1/workspace/members` | ❌ | ✅ | ✅ |
| `POST /v1/workspace/members/{id}/resend` | ❌ | ✅ | ✅ |
| `PATCH /v1/workspace/members/{id}` | ❌ | ✅ | ✅ |
| `PATCH /v1/workspace/members/{id}/numbers` | ❌ | ✅ | ✅ |
| `DELETE /v1/workspace/members/{id}` | ❌ | ✅ | ✅ |

¹ Só chave com escopo de tenant. O nome e as configurações são da conta inteira, então uma chave com escopo de número recebe `403 NUMBER_SCOPE_NOT_ALLOWED`.
² O usuário precisa ser `ADMIN` ou `OWNER` (`workspace:settings:update`); abaixo disso, `403 PERMISSION_DENIED`.
³ O usuário precisa ser o `OWNER`; qualquer outro recebe `403 PERMISSION_DENIED`.

<Warning>
**Escrita exige um usuário identificado, de propósito.** Uma chave de workspace ou de número não tem usuário por trás — a chave é do workspace, não de uma pessoa. Se convidar fosse permitido com chave tenant-scoped, quem tivesse *qualquer* chave do workspace se convidaria como Administrador, e a chave viraria caminho de takeover da conta. Essa chave recebe **403 `MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`**.
</Warning>

Um token OAuth e uma [chave de conta](/pt-BR/api/key-types#chaves-de-conta) (com `x-workspace-id`) carregam um usuário e agem com o **papel atual** desse usuário no workspace: valem as mesmas regras do painel.

Transferir a posse e arquivar são as duas ações que mudam quem paga a conta ou trancam todo mundo do lado de fora, por isso exigem o **proprietário identificado**: um token OAuth/MCP ou uma chave de conta cujo usuário é o proprietário. **Nenhuma credencial de máquina as alcança** — qualquer chave `ps_` de workspace ou de número recebe **403 `MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`**. Nenhuma das duas tem ferramenta MCP ainda.

Todo endpoint desta página responde com `Cache-Control: no-store`. Um usuário por trás de um token que não é mais membro ativo recebe `403 WORKSPACE_MEMBERSHIP_REQUIRED`. Os erros trazem um `error` bilíngue (`English | Português`) e um `code`; um corpo que não é um objeto JSON é `400 INVALID_BODY`, e uma chave que o endpoint não aceita é `400 UNKNOWN_FIELDS`, com as chaves recusadas em `unknownFields`.

## Ler o workspace

```bash
curl https://api.pilotstatus.com.br/v1/workspace \
  -H "x-api-key: ps_..."
```

```json
{
  "id": "tn_...",
  "name": "Acme",
  "plan": "PREMIUM",
  "seatsUsed": 4,
  "seatLimit": null
}
```

`seatLimit` é sempre `null`: os membros são **ilimitados em todos os planos**. O campo continua na resposta por compatibilidade com integrações e SDKs existentes.

`seatsUsed` é **apenas informativo** — conta membros ativos e convites pendentes que ainda não venceram, e nunca bloqueia nada.

## Renomear o workspace

```bash
curl -X PATCH https://api.pilotstatus.com.br/v1/workspace \
  -H "x-api-key: ps_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"Acme Holdings"}'
```

```json
{ "id": "tn_...", "name": "Acme Holdings" }
```

`name` perde os espaços das pontas e precisa ter **de 1 a 60 caracteres**; senão, `400 INVALID_NAME`. O nome é um rótulo: não precisa ser único, e o `id` do workspace nunca muda. Funciona com chave com escopo de tenant ou com um usuário `ADMIN` ou `OWNER`. Ferramenta MCP: `workspace_update`.

## Configurações do workspace

### Ler

```bash
curl https://api.pilotstatus.com.br/v1/workspace/settings \
  -H "x-api-key: ps_..."
```

```json
{
  "settings": {
    "mainCurrency": "BRL",
    "mainTimezone": "America/Sao_Paulo",
    "mainLanguage": "pt",
    "billingMode": "SUBSCRIPTION",
    "currencyLocked": false
  },
  "phoneLinePrice": { "currency": "BRL", "price": 49.9 }
}
```

| Campo | Significado |
|---|---|
| `mainCurrency` | A moeda em que a conta inteira é cobrada |
| `mainTimezone` | Fuso horário IANA do workspace |
| `mainLanguage` | `pt`, `en` ou `es` |
| `billingMode` | `SUBSCRIPTION` ou `WALLET`. Definido pela plataforma |
| `currencyLocked` | `true` depois da primeira movimentação da carteira — a partir daí a moeda não muda mais |
| `phoneLinePrice` | Quanto uma linha telefônica **nova** custa por mês para este workspace, na moeda dele |

Qualquer papel lê, `ANALYST` inclusive, assim como uma chave com escopo de tenant. Ferramenta MCP: `workspace_settings_get`.

### Atualizar

```bash
curl -X PATCH https://api.pilotstatus.com.br/v1/workspace/settings \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"mainTimezone":"America/Manaus","mainLanguage":"en"}'
```

Uma atualização parcial que aceita **só** `mainTimezone` e `mainLanguage` — envie ao menos um. A resposta é `{ "settings": { ... } }`, no mesmo formato da leitura. As credenciais são as mesmas de renomear: chave com escopo de tenant, ou um usuário `ADMIN` ou `OWNER`. Ferramenta MCP: `workspace_settings_update`.

Ao contrário do painel, um valor inválido nunca é ignorado em silêncio:

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `NO_FIELDS` | Nem `mainTimezone` nem `mainLanguage` foi enviado |
| `400` | `INVALID_TIMEZONE` | `mainTimezone` não é um fuso IANA; `field` o nomeia |
| `400` | `INVALID_LANGUAGE` | `mainLanguage` não é `pt`, `en` nem `es`; `field` o nomeia e `accepted` lista os valores |
| `400` | `CURRENCY_NOT_HERE` | `mainCurrency` foi enviado. Quem muda a moeda é o **proprietário**, nas configurações de cobrança do painel, e ela trava após a primeira movimentação da carteira |
| `400` | `BILLING_MODE_NOT_HERE` | `billingMode` foi enviado. Ele é definido pela plataforma |
| `400` | `UNKNOWN_FIELDS` | Qualquer outra chave; `unknownFields` as nomeia |

Nada é gravado quando qualquer um desses volta.

## Listar membros

```bash
curl https://api.pilotstatus.com.br/v1/workspace/members \
  -H "x-api-key: ps_..."
```

Devolve membros ativos e convites pendentes numa lista só, distinguidos por `status`. O envelope também traz o mesmo `seatsUsed` informativo e `seatLimit: null`:

```json
{
  "members": [ ... ],
  "seatsUsed": 4,
  "seatLimit": null
}
```

<Warning>
A lista **nunca traz link nem token de convite**, e nunca vai trazer: guardamos apenas o hash do token, então o link não é derivável depois. Se você precisa do link de um convite pendente, chame `resend`.
</Warning>

## Convidar

```bash
curl -X POST https://api.pilotstatus.com.br/v1/workspace/members \
  -H "Authorization: Bearer <token-oauth>" \
  -H "Content-Type: application/json" \
  -d '{"email":"alguem@acme.com","role":"AGENT","sendEmail":true}'
```

| Campo | Significado |
|---|---|
| `email` | Normalizado para minúsculas. Um convite por endereço por workspace |
| `role` | `ADMIN`, `AGENT` ou `ANALYST`. **`OWNER` nunca é atribuível** |
| `allowedNumberIds` | Opcional. Restringe Atendente ou Analista a números específicos; ignorado para Administrador |
| `sendEmail` | Default `true`. Com `false`, nenhum e-mail sai e a resposta traz `inviteUrl` |

`sendEmail: false` é a escotilha para entregar o convite do seu jeito. **A resposta é o único lugar onde o link aparece** — se perder, chame `resend`, que emite um novo e mata o anterior.

Convidar um endereço que já tem convite pendente não é erro: rotaciona o token na mesma linha e devolve `200` em vez de `201`.

## Mudar papel do membro

```bash
curl -X PATCH https://api.pilotstatus.com.br/v1/workspace/members/mb_... \
  -H "Authorization: Bearer <token-oauth>" \
  -H "Content-Type: application/json" \
  -d '{"role":"ANALYST"}'
```

Mudar o papel é **só do Proprietário** e sempre exige `role`. Promover a `ADMIN` limpa o escopo por número, porque Administrador vê o workspace inteiro. Para mudar **só os números** que um Atendente ou Analista vê, sem mexer no papel, use o `PATCH /v1/workspace/members/{id}/numbers` abaixo — o Administrador também pode chamá-lo.

## Mudar quais números o membro vê

```bash
curl -X PATCH https://api.pilotstatus.com.br/v1/workspace/members/mb_.../numbers \
  -H "Authorization: Bearer <token-oauth>" \
  -H "Content-Type: application/json" \
  -d '{"allowedNumberIds":["wa_...","wa_..."]}'
```

Define quais números de WhatsApp do workspace um `AGENT` ou `ANALYST` vê e opera. O papel não muda. Funciona também em convites pendentes.

| Campo | Significado |
|---|---|
| `allowedNumberIds` | **Obrigatório.** Lista de ids de números. **Substitui a lista inteira** — envie todos os ids que o membro deve manter |

<Warning>
**`[]` significa TODOS os números, não nenhum** — inclusive os números conectados depois. Um membro restrito a números específicos **não** ganha números novos sozinho: ao conectar um número, adicione-o aqui para cada membro restrito que precisar dele.
</Warning>

- **Quem pode chamar:** um token OAuth/MCP ou uma chave de conta cujo usuário é `ADMIN` ou `OWNER` do workspace. Uma chave `ps_` de workspace ou de número recebe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`; `AGENT` ou `ANALYST` recebe `403 PERMISSION_DENIED`.
- **O corte é imediato:** os refresh tokens OAuth do membro são revogados, então um escopo menor vale na próxima chamada dele, em vez de sobreviver num token consentido com o alcance maior. Os conectores MCP dele podem precisar entrar de novo.
- **Proprietário e Administrador sempre veem todos os números**, por isso a chamada os recusa com `409 SCOPE_NOT_APPLICABLE`.

A resposta é o membro atualizado, no mesmo formato da listagem:

```json
{
  "member": {
    "id": "mb_...",
    "role": "AGENT",
    "status": "ACTIVE",
    "allowedNumberIds": ["wa_...", "wa_..."],
    ...
  }
}
```

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `INVALID_SCOPE` | `allowedNumberIds` ausente ou não é uma lista de strings |
| `400` | `UNKNOWN_FIELDS` | O corpo tem qualquer outra chave (`role` inclusive); `details.unknownFields` diz quais |
| `403` | `MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS` | Chamada com chave `ps_` de workspace ou de número |
| `403` | `PERMISSION_DENIED` | Quem chamou é `AGENT` ou `ANALYST` |
| `403` | `WORKSPACE_MEMBERSHIP_REQUIRED` | O usuário por trás do token não é mais membro ativo do workspace |
| `404` | `NOT_FOUND` | Esse id de membership não está neste workspace |
| `409` | `SCOPE_NOT_APPLICABLE` | O alvo é `OWNER` ou `ADMIN` |

## Erros que vale tratar

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `INVALID_BODY` | O corpo de um convite, troca de papel, troca de escopo ou reenvio não é JSON válido — nada é alterado e nenhum e-mail é enviado ([Corpo JSON malformado](/pt-BR/api/overview#corpo-json-malformado)) |
| `400` | `INVALID_EMAIL` | O endereço não é plausível |
| `409` | `ALREADY_MEMBER` | O endereço já é membro ativo |
| `409` | `OWNER_INVITE_FORBIDDEN` | `OWNER` foi pedido como papel |
| `409` | `OWNER_IMMUTABLE` | O alvo é o proprietário — mudança ou remoção recusada |
| `409` | `MEMBER_HAS_API_KEYS` | Veja abaixo |
| `429` | — | Limitado. Convite tem limite por workspace, por destinatário e por IP |

## Remover membro que criou chaves de API

O `DELETE` recusa com `409 MEMBER_HAS_API_KEYS` e lista as chaves:

```json
{
  "code": "MEMBER_HAS_API_KEYS",
  "apiKeys": [
    { "id": "key_...", "name": "n8n", "keyLast4": "9f21", "lastUsedAt": "2026-08-01T12:00:00.000Z" }
  ],
  "hint": "Repita com ?apiKeyAction=revoke ou ?apiKeyAction=keep."
}
```

Repita a chamada com a decisão explícita:

```bash
curl -X DELETE "https://api.pilotstatus.com.br/v1/workspace/members/mb_...?apiKeyAction=keep" \
  -H "Authorization: Bearer <token-oauth>"
```

- `revoke` — as chaves param de autenticar. O que integra por elas quebra na hora.
- `keep` — as chaves continuam funcionando e passam para quem chamou.

Não há default. Um integrador não pode derrubar integração de produção por omissão.

Revogar nunca é apagar: o registro sobrevive para que o histórico de mensagens e chamadas continue apontando para algo real.

## Transferir a posse

```bash
curl -X POST https://api.pilotstatus.com.br/v1/workspace/transfer-ownership \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"email":"new-owner@acme.com"}'
```

```json
{ "transferred": true, "newOwnerId": "usr_...", "yourNewRole": "ADMIN" }
```

Torna um membro ativo o novo **proprietário**. `email` é comparado com os e-mails dos membros sem diferenciar maiúsculas e minúsculas. O alvo precisa ter **aceitado** o convite — um convite pendente não serve.

<Warning>
**O que muda no instante em que a chamada volta:**

- **Você vira `ADMIN`** (`yourNewRole`). Tudo o que só o proprietário fazia — mover dinheiro, arquivar, transferir de novo — passa a ser do novo proprietário.
- **Os refresh tokens OAuth dos dois usuários são revogados.** Uma conexão MCP continua funcionando até o access token expirar e depois precisa consentir de novo.
- **A responsabilidade pela conta passa para o novo proprietário.**
</Warning>

Só o **proprietário** pode chamar, com token OAuth/MCP ou chave de conta. Uma chave `ps_` de workspace ou de número recebe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`; qualquer outra pessoa, `403 PERMISSION_DENIED`. Ainda não há ferramenta MCP para isso.

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `MISSING_EMAIL` | `email` ausente ou em branco |
| `400` | `NOT_A_MEMBER` | Nenhum membro deste workspace tem esse e-mail |
| `400` | `TARGET_NOT_ACTIVE` | A pessoa ainda não aceitou o convite |
| `409` | `ALREADY_OWNER` | A pessoa já é o proprietário |
| `409` | `NOT_OWNER` | Quem chamou não é mais o proprietário |
| `409` | `NO_OWNER` | O workspace não tem proprietário |
| `409` | `OWNERSHIP_CHANGED` | A posse mudou durante a chamada. Releia os membros e tente de novo |
| `409` | `WOULD_ORPHAN_WORKSPACE` | A mudança deixaria o workspace sem proprietário |

## Arquivar o workspace

<Warning>
**Arquivar tranca todo mundo do lado de fora — inclusive você, e a própria chamada que arquivou.** O token usado para de funcionar já na requisição seguinte, todas as chaves `ps_` do workspace deixam de autenticar e as sessões do chat incorporado são revogadas. **Não existe endpoint para desarquivar:** reverter exige falar com o suporte.
</Warning>

```bash
curl -X POST https://api.pilotstatus.com.br/v1/workspace/archive \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"confirmName":"Acme Holdings"}'
```

```json
{ "archived": true, "archivedAt": "2026-11-08T12:00:00.000Z" }
```

`confirmName` precisa ser o nome atual do workspace, **exatamente** — sem espaços nas pontas e diferenciando maiúsculas e minúsculas. Leia-o com `GET /v1/workspace`. Um nome errado ou ausente é `400 CONFIRMATION_MISMATCH` com `field: "confirmName"`, e a resposta nunca repete o nome verdadeiro.

Só o **proprietário** pode chamar, com token OAuth/MCP ou chave de conta. Uma chave `ps_` de workspace ou de número recebe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`; qualquer outra pessoa, `403 PERMISSION_DENIED`. Ainda não há ferramenta MCP para isso.

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `CONFIRMATION_MISMATCH` | `confirmName` ausente ou diferente do nome |
| `404` | `NOT_FOUND` | O workspace não existe mais |
| `409` | `ALREADY_ARCHIVED` | O workspace já está arquivado |
