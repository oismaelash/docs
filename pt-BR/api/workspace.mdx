Doze endpoints em `/v1/workspace` espelham o que o painel faz com o próprio workspace (nome, configurações, posse, arquivamento) e com membros e convites. Os membros são ilimitados em todos os planos.

## Qual credencial funciona onde

Esta é a parte para ler antes de qualquer coisa.

| Endpoint | Chave de workspace (`x-api-key`) ¹ | Chave de conta (`ps_account_`) | Token OAuth |
|---|:---:|:---:|:---:|
| `GET /v1/workspace` | ✅ | ✅ | ✅ |
| `PATCH /v1/workspace` | ✅ | ✅ ² | ✅ ² |
| `GET /v1/workspace/settings` | ✅ | ✅ | ✅ |
| `PATCH /v1/workspace/settings` | ✅ | ✅ ² | ✅ ² |
| `POST /v1/workspace/transfer-ownership` | ❌ | ✅ ³ | ✅ ³ |
| `POST /v1/workspace/archive` | ❌ | ✅ ³ | ✅ ³ |
| `GET /v1/workspace/members` | ✅ | ✅ ² | ✅ ² |
| `POST /v1/workspace/members` | ❌ | ✅ ² | ✅ ² |
| `POST /v1/workspace/members/{id}/resend` | ❌ | ✅ ² | ✅ ² |
| `PATCH /v1/workspace/members/{id}` | ❌ | ✅ ³ | ✅ ³ |
| `PATCH /v1/workspace/members/{id}/numbers` | ❌ | ✅ ² | ✅ ² |
| `DELETE /v1/workspace/members/{id}` | ❌ | ✅ ³ | ✅ ³ |

¹ **Chave de número nunca passa aqui.** Tudo nesta página é da conta inteira, então uma chave com escopo de número recebe `403 NUMBER_SCOPE_NOT_ALLOWED` em todos os endpoints acima — nas escritas marcadas com ❌ ela recebe antes o `403` de credencial de máquina descrito abaixo. O mesmo `403 NUMBER_SCOPE_NOT_ALLOWED` vale para um token OAuth consentido só para alguns números e para uma chave de conta cujo usuário é restrito a alguns números. Uma chave de workspace restringida com `x-whatsapp-number-id` continua passando.
² O usuário precisa ser `ADMIN` ou `OWNER`; abaixo disso, `403 PERMISSION_DENIED`.
³ O usuário precisa ser o `OWNER`; qualquer outro recebe `403 PERMISSION_DENIED`.

<Warning>
**Escrita exige um usuário identificado, de propósito.** Uma chave de workspace ou de número não tem usuário por trás — a chave é do workspace, não de uma pessoa. Se convidar fosse permitido com chave tenant-scoped, quem tivesse *qualquer* chave do workspace se convidaria como Administrador, e a chave viraria caminho de takeover da conta. Essa chave recebe **403 `MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`** nas escritas de membros.
</Warning>

Um token OAuth e uma [chave de conta](/pt-BR/api/key-types#chaves-de-conta) (com `x-workspace-id`) carregam um usuário e agem com o **papel atual** desse usuário no workspace, relido a cada requisição: valem as mesmas regras do painel.

Transferir a posse e arquivar são as duas ações que mudam quem paga a conta ou trancam todo mundo do lado de fora, por isso exigem o **proprietário identificado**: um token OAuth/MCP ou uma chave de conta cujo usuário é o proprietário. **Nenhuma credencial de máquina as alcança** — qualquer chave `ps_` de workspace ou de número recebe **403 `MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`**.

As respostas de sucesso vêm com `Cache-Control: no-store`. Um usuário que não é mais membro ativo recebe `401 OAUTH_MEMBERSHIP_REVOKED` por trás de um token OAuth (entre de novo) e `403 WORKSPACE_MEMBERSHIP_REQUIRED` por trás de uma chave de conta. Os erros trazem uma mensagem em `error` e um `code` estável — decida pelo `code`. A maioria das mensagens é bilíngue (`English | Português`); os conflitos de gestão de membros (`ALREADY_MEMBER`, `NOT_FOUND`, `OWNER_IMMUTABLE`, …), o `RATE_LIMITED` e as recusas de papel hoje vêm em um idioma só. Um corpo que não é um objeto JSON é `400 INVALID_BODY` e, nos endpoints de workspace, configurações, arquivamento e transferência, uma chave que o endpoint não aceita é `400 UNKNOWN_FIELDS`, com as chaves recusadas em `unknownFields`.

## Ler o workspace

```bash
curl https://pilotstatus.com.br/v1/workspace \
  -H "x-api-key: ps_..."
```

```json
{
  "id": "tn_...",
  "name": "Acme",
  "plan": "PREMIUM",
  "seatsUsed": 4,
  "seatLimit": null
}
```

`seatLimit` é sempre `null`: os membros são **ilimitados em todos os planos**. O campo continua na resposta por compatibilidade com integrações e SDKs existentes.

`seatsUsed` é **apenas informativo** — conta membros ativos e convites pendentes que ainda não venceram, e nunca bloqueia nada.

## Renomear o workspace

```bash
curl -X PATCH https://pilotstatus.com.br/v1/workspace \
  -H "x-api-key: ps_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"Acme Holdings"}'
```

```json
{ "id": "tn_...", "name": "Acme Holdings" }
```

`name` perde os espaços das pontas e precisa ter **de 1 a 60 caracteres**; senão, `400 INVALID_NAME`. O nome é um rótulo: não precisa ser único, e o `id` do workspace nunca muda. Funciona com chave com escopo de tenant ou com um usuário `ADMIN` ou `OWNER`. Ferramenta MCP: `workspace_update`.

## Configurações do workspace

### Ler

```bash
curl https://pilotstatus.com.br/v1/workspace/settings \
  -H "x-api-key: ps_..."
```

```json
{
  "settings": {
    "mainCurrency": "BRL",
    "mainTimezone": "America/Sao_Paulo",
    "mainLanguage": "pt",
    "billingMode": "SUBSCRIPTION",
    "currencyLocked": false
  },
  "phoneLinePrice": { "currency": "BRL", "price": 49.9 }
}
```

| Campo | Significado |
|---|---|
| `mainCurrency` | A moeda em que a conta inteira é cobrada |
| `mainTimezone` | Fuso horário IANA do workspace |
| `mainLanguage` | `pt`, `en` ou `es` |
| `billingMode` | `SUBSCRIPTION` ou `WALLET`. Definido pela plataforma |
| `currencyLocked` | `true` depois da primeira movimentação da carteira — a partir daí a moeda não muda mais |
| `phoneLinePrice` | Quanto uma linha telefônica **nova** custa por mês para este workspace, na moeda dele |

Qualquer papel lê, `ANALYST` inclusive, assim como uma chave com escopo de tenant. Ferramenta MCP: `workspace_settings_get`.

### Atualizar

```bash
curl -X PATCH https://pilotstatus.com.br/v1/workspace/settings \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"mainTimezone":"America/Manaus","mainLanguage":"en"}'
```

Uma atualização parcial que aceita **só** `mainTimezone` e `mainLanguage` — envie ao menos um. A resposta é `{ "settings": { ... } }`, no mesmo formato da leitura. As credenciais são as mesmas de renomear: chave com escopo de tenant, ou um usuário `ADMIN` ou `OWNER`. Ferramenta MCP: `workspace_settings_update`.

Ao contrário do painel, um valor inválido nunca é ignorado em silêncio:

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `NO_FIELDS` | Nem `mainTimezone` nem `mainLanguage` foi enviado |
| `400` | `INVALID_TIMEZONE` | `mainTimezone` não é um fuso IANA; `field` o nomeia |
| `400` | `INVALID_LANGUAGE` | `mainLanguage` não é `pt`, `en` nem `es`; `field` o nomeia e `accepted` lista os valores |
| `400` | `CURRENCY_NOT_HERE` | `mainCurrency` foi enviado. Quem muda a moeda é o **proprietário**, nas configurações de cobrança do painel, e ela trava após a primeira movimentação da carteira |
| `400` | `BILLING_MODE_NOT_HERE` | `billingMode` foi enviado. Ele é definido pela plataforma |
| `400` | `UNKNOWN_FIELDS` | Qualquer outra chave; `unknownFields` as nomeia |

Nada é gravado quando qualquer um desses volta.

## Listar membros

```bash
curl https://pilotstatus.com.br/v1/workspace/members \
  -H "x-api-key: ps_..."
```

Devolve membros ativos e convites numa lista só, distinguidos por `status`. Uma chave de workspace lê; um usuário precisa ser `ADMIN` ou `OWNER`. O envelope também traz o mesmo `seatsUsed` informativo e `seatLimit: null`:

```json
{
  "members": [
    {
      "id": "mb_...",
      "email": "alguem@acme.com",
      "name": "Alguém",
      "role": "AGENT",
      "status": "ACTIVE",
      "allowedNumberIds": [],
      "invitedAt": "2026-08-01T12:00:00.000Z",
      "joinedAt": "2026-08-01T12:30:00.000Z",
      "inviteExpiresAt": null,
      "inviteExpired": false,
      "inviteEmailSentAt": "2026-08-01T12:00:04.000Z",
      "inviteEmailStatus": null
    }
  ],
  "seatsUsed": 4,
  "seatLimit": null
}
```

| Campo | Significado |
|---|---|
| `id` | Id da membership — o `{id}` que os outros endpoints de membro recebem. **Não** é o id do usuário |
| `status` | `ACTIVE`, `PENDING` (convidado, ainda não aceitou) ou `DECLINED` |
| `allowedNumberIds` | Números a que um `AGENT`/`ANALYST` está restrito. `[]` = todos os números (sempre `[]` para `OWNER` e `ADMIN`) |
| `inviteExpired` | `true` quando um convite pendente passou de `inviteExpiresAt` |
| `inviteEmailStatus` | Para um convite pendente: `SENT`, `QUEUED` (menos de 5 minutos) ou `NOT_SENT`. `null` para quem não está pendente |

<Warning>
A lista **nunca traz link nem token de convite**, e nunca vai trazer: guardamos apenas o hash do token, então o link não é derivável depois. Se você precisa do link de um convite pendente, chame `resend`.
</Warning>

## Convidar

```bash
curl -X POST https://pilotstatus.com.br/v1/workspace/members \
  -H "Authorization: Bearer <token-oauth>" \
  -H "Content-Type: application/json" \
  -d '{"email":"alguem@acme.com","role":"AGENT","sendEmail":true}'
```

| Campo | Significado |
|---|---|
| `email` | Sem espaços nas pontas e normalizado para minúsculas. Um convite por endereço por workspace |
| `role` | Opcional, default `AGENT`. O `OWNER` pode atribuir `ADMIN`, `AGENT` ou `ANALYST`; o `ADMIN`, só `AGENT` ou `ANALYST`. **`OWNER` nunca é atribuível** |
| `allowedNumberIds` | Opcional. Restringe Atendente ou Analista a números específicos; ignorado para Administrador |
| `sendEmail` | Default `true`. Com `false` (o booleano JSON), nenhum e-mail sai e a resposta traz `inviteUrl` |

Um papel que quem chama não pode atribuir — `OWNER` inclusive, ou `ADMIN` quando quem chama é Administrador — é **`403 ROLE_NOT_ASSIGNABLE`**, com os papéis permitidos em `assignableRoles`.

```json Resposta (201)
{
  "member": { "id": "mb_...", "email": "alguem@acme.com", "role": "AGENT", "status": "PENDING", ... },
  "resent": false,
  "emailSent": false,
  "inviteUrl": "https://pilotstatus.com.br/invite/..."
}
```

`sendEmail: false` é a escotilha para entregar o convite do seu jeito. **A resposta é o único lugar onde o link aparece** — se perder, chame `resend`, que emite um novo e mata o anterior. Com `sendEmail: true`, `inviteUrl` não vem na resposta.

Convidar um endereço que já tem convite pendente (ou recusado) não é erro: rotaciona o token na mesma linha e devolve `200` com `"resent": true` em vez de `201`. Uma falha no envio do e-mail nunca derruba a chamada: o convite já está salvo.

**Limites de taxa.** Convites — com ou sem e-mail — são limitados a **30 por hora por workspace** (compartilhado com o `resend`), **3 por hora por endereço de destino** e **60 por hora por IP**. Acima de um limite: `429` com `code: "RATE_LIMITED"`, `retryAfterSeconds` e o header `Retry-After`. Nada é gravado.

Se os convites estiverem desligados para a conta, convidar e reenviar respondem `403 FEATURE_DISABLED`; listar, alterar e remover membros continuam funcionando.

## Reenviar um convite

```bash
curl -X POST https://pilotstatus.com.br/v1/workspace/members/mb_.../resend \
  -H "Authorization: Bearer <token-oauth>" \
  -H "Content-Type: application/json" \
  -d '{"sendEmail":false}'
```

Emite um novo link para um convite pendente — o link anterior morre na hora — e, a menos que `sendEmail` seja `false`, manda o e-mail de novo. O corpo é opcional (`sendEmail` tem default `true`). `ADMIN` ou `OWNER`.

```json
{ "member": { "id": "mb_...", "status": "PENDING", ... }, "emailSent": false, "inviteUrl": "https://pilotstatus.com.br/invite/..." }
```

`inviteUrl` só vem com `sendEmail: false`. Só o reenvio que manda e-mail tem limite de taxa: ele conta nos limites por workspace e por IP do convite e em **3 reenvios por hora por convite** (`429 RATE_LIMITED`). Um id que não está neste workspace é `404 NOT_FOUND`; um membro que já aceitou é `409 ALREADY_MEMBER`.

## Mudar papel do membro

```bash
curl -X PATCH https://pilotstatus.com.br/v1/workspace/members/mb_... \
  -H "Authorization: Bearer <token-oauth>" \
  -H "Content-Type: application/json" \
  -d '{"role":"ANALYST"}'
```

Mudar o papel é **só do Proprietário** e sempre exige `role` (`ADMIN`, `AGENT` ou `ANALYST`); papel ausente, ou `OWNER`, é `400 ROLE_NOT_ASSIGNABLE` com `assignableRoles`. O `allowedNumberIds` opcional define o escopo por número na mesma chamada; **se omitido, o escopo atual é mantido**. Promover a `ADMIN` limpa o escopo por número, porque Administrador vê o workspace inteiro. Os refresh tokens OAuth do membro são revogados. A resposta é `{ "member": { ... } }`. O papel do próprio proprietário não muda aqui (`409 OWNER_IMMUTABLE`) — use [Transferir a posse](#transferir-a-posse).

Para mudar **só os números** que um Atendente ou Analista vê, sem mexer no papel, use o `PATCH /v1/workspace/members/{id}/numbers` abaixo — o Administrador também pode chamá-lo.

## Mudar quais números o membro vê

```bash
curl -X PATCH https://pilotstatus.com.br/v1/workspace/members/mb_.../numbers \
  -H "Authorization: Bearer <token-oauth>" \
  -H "Content-Type: application/json" \
  -d '{"allowedNumberIds":["wa_...","wa_..."]}'
```

Define quais números de WhatsApp do workspace um `AGENT` ou `ANALYST` vê e opera. O papel não muda. Funciona também em convites pendentes.

| Campo | Significado |
|---|---|
| `allowedNumberIds` | **Obrigatório.** Lista de ids de números. **Substitui a lista inteira** — envie todos os ids que o membro deve manter |

<Warning>
**`[]` significa TODOS os números, não nenhum** — inclusive os números conectados depois. Um membro restrito a números específicos **não** ganha números novos sozinho: ao conectar um número, adicione-o aqui para cada membro restrito que precisar dele.
</Warning>

- **Quem pode chamar:** um token OAuth/MCP ou uma chave de conta cujo usuário é `ADMIN` ou `OWNER` do workspace. Uma chave `ps_` de workspace ou de número recebe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`; `AGENT` ou `ANALYST` recebe `403 PERMISSION_DENIED`.
- **O corte é imediato:** os refresh tokens OAuth do membro são revogados, então um escopo menor vale na próxima chamada dele, em vez de sobreviver num token consentido com o alcance maior. Os conectores MCP dele podem precisar entrar de novo.
- **Proprietário e Administrador sempre veem todos os números**, por isso a chamada os recusa com `409 SCOPE_NOT_APPLICABLE`.

A resposta é o membro atualizado, no mesmo formato da listagem:

```json
{
  "member": {
    "id": "mb_...",
    "role": "AGENT",
    "status": "ACTIVE",
    "allowedNumberIds": ["wa_...", "wa_..."],
    ...
  }
}
```

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `INVALID_SCOPE` | `allowedNumberIds` ausente ou não é uma lista de strings |
| `400` | `UNKNOWN_FIELDS` | O corpo tem qualquer outra chave (`role` inclusive); `details.unknownFields` diz quais |
| `403` | `MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS` | Chamada com chave `ps_` de workspace ou de número |
| `403` | `PERMISSION_DENIED` | Quem chamou é `AGENT` ou `ANALYST` |
| `401` | `OAUTH_MEMBERSHIP_REVOKED` | Token OAuth de um usuário que não é mais membro ativo do workspace — entre de novo |
| `403` | `WORKSPACE_MEMBERSHIP_REQUIRED` | Chave de conta de um usuário que não é mais membro ativo do workspace |
| `404` | `NOT_FOUND` | Esse id de membership não está neste workspace |
| `409` | `SCOPE_NOT_APPLICABLE` | O alvo é `OWNER` ou `ADMIN` |

## Remover membro ou revogar convite

```bash
curl -X DELETE https://pilotstatus.com.br/v1/workspace/members/mb_... \
  -H "Authorization: Bearer <token-oauth>"
```

Uma chamada para os dois: convite e membership são a mesma linha. **Só do Proprietário.** O proprietário não pode ser removido (`409 OWNER_IMMUTABLE`).

```json
{ "removed": true, "email": "alguem@acme.com", "apiKeysRevoked": 0, "apiKeysReassigned": 0, "oauthTokensRevoked": 1 }
```

Os refresh tokens OAuth do usuário removido são revogados (`oauthTokensRevoked`).

## Erros que vale tratar

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `INVALID_BODY` | O corpo de um convite, troca de papel, troca de escopo, remoção ou reenvio não é JSON válido — nada é alterado e nenhum e-mail é enviado ([Corpo JSON malformado](/pt-BR/api/overview#corpo-json-malformado)) |
| `400` | `INVALID_EMAIL` | O endereço não é plausível |
| `400` | `ROLE_NOT_ASSIGNABLE` | Troca de papel: `role` ausente, desconhecido ou `OWNER`. `assignableRoles` lista os válidos |
| `403` | `ROLE_NOT_ASSIGNABLE` | Convite: o seu papel não pode atribuir esse papel. `assignableRoles` lista os que você pode |
| `403` | `FEATURE_DISABLED` | Os convites estão desligados para a conta (só convidar e reenviar) |
| `404` | `NOT_FOUND` | Esse id de membership não está neste workspace |
| `409` | `ALREADY_MEMBER` | O endereço já é membro ativo (ou, no reenvio, o convite já foi aceito) |
| `409` | `OWNER_IMMUTABLE` | O alvo é o proprietário — mudança ou remoção recusada |
| `409` | `MEMBER_HAS_API_KEYS` | Veja abaixo |
| `409` | `WOULD_ORPHAN_WORKSPACE` | A mudança deixaria o workspace sem proprietário |
| `429` | `RATE_LIMITED` | Convite ou reenvio acima do limite. `retryAfterSeconds` e `Retry-After` dizem quando tentar de novo |

## Remover membro que criou chaves de API

O `DELETE` recusa com `409 MEMBER_HAS_API_KEYS` e lista as chaves:

```json
{
  "error": "O membro criou 1 chave(s) de API ainda ativa(s).",
  "code": "MEMBER_HAS_API_KEYS",
  "apiKeys": [
    { "id": "key_...", "name": "n8n", "keyLast4": "9f21", "whatsappNumberId": null, "lastUsedAt": "2026-08-01T12:00:00.000Z" }
  ],
  "hint": "Repeat with apiKeyAction=\"revoke\" or apiKeyAction=\"keep\"."
}
```

Repita a chamada com a decisão explícita, na query string ou como `{"apiKeyAction":"keep"}` no corpo (a query vence quando os dois vêm):

```bash
curl -X DELETE "https://pilotstatus.com.br/v1/workspace/members/mb_...?apiKeyAction=keep" \
  -H "Authorization: Bearer <token-oauth>"
```

- `revoke` — as chaves param de autenticar. O que integra por elas quebra na hora.
- `keep` — as chaves continuam funcionando e passam para quem chamou.

Não há default. Um integrador não pode derrubar integração de produção por omissão.

Revogar nunca é apagar: o registro sobrevive para que o histórico de mensagens e chamadas continue apontando para algo real.

## Transferir a posse

```bash
curl -X POST https://pilotstatus.com.br/v1/workspace/transfer-ownership \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"email":"new-owner@acme.com"}'
```

```json
{ "transferred": true, "newOwnerId": "usr_...", "yourNewRole": "ADMIN" }
```

Torna um membro ativo o novo **proprietário**. `email` é comparado com os e-mails dos membros sem diferenciar maiúsculas e minúsculas. O alvo precisa ter **aceitado** o convite — um convite pendente não serve.

<Warning>
**O que muda no instante em que a chamada volta:**

- **Você vira `ADMIN`** (`yourNewRole`). Tudo o que só o proprietário fazia — mover dinheiro, arquivar, transferir de novo — passa a ser do novo proprietário.
- **Os refresh tokens OAuth dos dois usuários são revogados.** Uma conexão MCP continua funcionando com o **novo** papel de cada usuário (aplicado na requisição seguinte) até o access token expirar e depois precisa consentir de novo.
- **A responsabilidade pela conta passa para o novo proprietário.**
</Warning>

Só o **proprietário** pode chamar, com token OAuth/MCP ou chave de conta. Uma chave `ps_` de workspace ou de número recebe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`; qualquer outra pessoa, `403 PERMISSION_DENIED`. Ferramenta MCP: `workspace_transfer_ownership`, com prévia e token de confirmação ([Servidor MCP](/pt-BR/integrations/mcp-server)).

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `MISSING_EMAIL` | `email` ausente ou em branco |
| `400` | `NOT_A_MEMBER` | Nenhum membro deste workspace tem esse e-mail |
| `400` | `TARGET_NOT_ACTIVE` | A pessoa ainda não aceitou o convite |
| `409` | `ALREADY_OWNER` | A pessoa já é o proprietário |
| `409` | `NOT_OWNER` | Quem chamou não é mais o proprietário |
| `409` | `NO_OWNER` | O workspace não tem proprietário |
| `409` | `OWNERSHIP_CHANGED` | A posse mudou durante a chamada. Releia os membros e tente de novo |
| `409` | `WOULD_ORPHAN_WORKSPACE` | A mudança deixaria o workspace sem proprietário |

## Arquivar o workspace

<Warning>
**Arquivar tranca todo mundo do lado de fora — inclusive você, e a própria chamada que arquivou.** O token usado para de funcionar já na requisição seguinte, todas as chaves `ps_` do workspace deixam de autenticar e as sessões do chat incorporado são revogadas. **Não existe endpoint para desarquivar:** reverter exige falar com o suporte.
</Warning>

```bash
curl -X POST https://pilotstatus.com.br/v1/workspace/archive \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"confirmName":"Acme Holdings"}'
```

```json
{ "archived": true, "archivedAt": "2026-11-08T12:00:00.000Z" }
```

`confirmName` precisa ser o nome atual do workspace, **exatamente** — sem espaços nas pontas e diferenciando maiúsculas e minúsculas. Leia-o com `GET /v1/workspace`. Um nome errado ou ausente é `400 CONFIRMATION_MISMATCH` com `field: "confirmName"`, e a resposta nunca repete o nome verdadeiro.

Só o **proprietário** pode chamar, com token OAuth/MCP ou chave de conta. Uma chave `ps_` de workspace ou de número recebe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`; qualquer outra pessoa, `403 PERMISSION_DENIED`. Ferramenta MCP: `workspace_archive`, com prévia e token de confirmação ([Servidor MCP](/pt-BR/integrations/mcp-server)).

| Status | `code` | O que aconteceu |
|---|---|---|
| `400` | `CONFIRMATION_MISMATCH` | `confirmName` ausente ou diferente do nome |
| `404` | `NOT_FOUND` | O workspace não existe mais |
| `409` | `ALREADY_ARCHIVED` | O workspace já está arquivado |
