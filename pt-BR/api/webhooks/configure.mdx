# Configurar webhooks

Gerencie todo o ciclo de vida do webhook via API pública — ou use a página **Webhooks** do painel (`/webhooks`). Um webhook é configurado **por número**; uma vez configurado, os eventos são entregues automaticamente (não é necessário vincular chave de API).

<Frame caption="A página de Webhooks — criar, editar, desativar ou excluir um webhook e inspecionar seus eventos de entrega.">
  ![Página de Webhooks do Pilot Status](/images/dashboard/webhooks.png)
</Frame>

Para payloads e a lista completa de eventos, consulte a [referência de eventos](/pt-BR/api/webhooks/events).

## Endpoints

| Método | Endpoint | Descrição |
| --- | --- | --- |
| `GET` | `/v1/webhooks` | Lista os webhooks visíveis no escopo da chave. |
| `POST` | `/v1/webhooks` | Cria um webhook assinado em **um** número. |
| `GET` | `/v1/webhooks/{id}` | Busca um webhook. |
| `PATCH` | `/v1/webhooks/{id}` | Atualiza `name`, `url`, `active`, `events`. |
| `DELETE` | `/v1/webhooks/{id}` | Exclui permanentemente o webhook. |
| `GET` | `/v1/webhooks/{id}/logs` | Tentativas de entrega recentes (`limit` 1–50, filtro `event`). |

## Escopo por número

Um webhook pertence a um único número do WhatsApp.

- Com uma chave **com escopo de número**, o número vem da própria chave; um `whatsappNumberId` no corpo deve corresponder a ele (caso contrário, **400 `NUMBER_MISMATCH`**).
- Com uma chave **com escopo de tenant**, informe o número de destino pelo campo `whatsappNumberId` do corpo ou pelo cabeçalho `x-whatsapp-number-id` — omitir ambos retorna **400 `NUMBER_REQUIRED`**; um número fora do seu tenant retorna **404 `NUMBER_NOT_FOUND`**.
- `GET /v1/webhooks` lista apenas os webhooks visíveis no escopo da chave (uma chave com escopo de número vê apenas os webhooks do seu próprio número). Um webhook fora do escopo da chave retorna **404 `WEBHOOK_NOT_FOUND`**.

## Exemplos

<CodeGroup>

```bash Create
curl -X POST "https://pilotstatus.com.br/v1/webhooks" \
  -H "x-api-key: ps_your_token_here" \
  -H "Content-Type: application/json" \
  -d '{ "url": "https://example.com/hooks/in", "name": "My hook", "events": ["message.received", "message.sent"] }'
```

```bash Pause (keep it, stop delivering)
curl -X PATCH "https://pilotstatus.com.br/v1/webhooks/wh_abc" \
  -H "x-api-key: ps_your_token_here" \
  -H "Content-Type: application/json" \
  -d '{ "active": false }'
```

```bash Delete
curl -X DELETE "https://pilotstatus.com.br/v1/webhooks/wh_abc" \
  -H "x-api-key: ps_your_token_here"
```

```bash Delivery logs
curl "https://pilotstatus.com.br/v1/webhooks/wh_abc/logs?limit=20&event=message.received" \
  -H "x-api-key: ps_your_token_here"
```

</CodeGroup>

## Ler os logs de entrega

`GET /v1/webhooks/{id}/logs` devolve as tentativas recentes, da mais nova para a mais antiga.
Dois campos juntos dizem *onde* a tentativa morreu:

| `status` | `statusCode` | `response` |
| --- | --- | --- |
| `SUCCESS` | o status HTTP (2xx) | o corpo do seu endpoint, cortado em 1000 caracteres |
| `FAILED` | o status HTTP | o corpo do seu endpoint — ele respondeu, mas não com 2xx |
| `FAILED` | `null` | a requisição nunca se completou; `response` traz a cadeia de causas |

O `statusCode` `null` é o caso que vale ler com atenção: nada chegou ao seu servidor, então
não existe status. O `response` traz então a cadeia de causas, da mais externa para a mais
interna, unidas por `<-` e marcadas com o código de erro do sistema:

```
fetch failed <- getaddrinfo EAI_AGAIN hooks.example.com [EAI_AGAIN]
fetch failed <- connect ECONNREFUSED 203.0.113.10:443 [ECONNREFUSED]
The operation was aborted due to timeout
```

Os códigos mais frequentes:

| Código | O que significa |
| --- | --- |
| `EAI_AGAIN`, `ENOTFOUND` | o seu hostname não resolveu |
| `ECONNREFUSED` | o host respondeu, mas nada escuta naquela porta |
| `ECONNRESET` | a conexão fechou no meio da requisição |
| `CERT_HAS_EXPIRED`, `DEPTH_ZERO_SELF_SIGNED_CERT` | o TLS foi recusado |
| *(sem código, "aborted due to timeout")* | o seu endpoint não respondeu a tempo |

<Note>
  Trate o `response` como **string de diagnóstico, não como contrato**. O texto vem do runtime
  e pode mudar entre versões; decida pelo `status` e pelo `statusCode`, e leia o `response`
  quando precisar saber o porquê.
</Note>

Uma tentativa falha é retentada com backoff exponencial antes de ser desistida, então uma
linha `FAILED` sozinha não quer dizer que o evento se perdeu — procure um `SUCCESS` posterior
no mesmo evento.

## Controle de eventos

<Warning>
  Uma **lista `events` vazia (ou omitida) NÃO dispara NADA** — não existe "assinar todos" implícito. Use `"*"` para assinar todos os eventos.
</Warning>

- No `PATCH`, **`events` substitui toda a lista de assinatura** (não é uma mesclagem).
- Eventos que o provedor do número não consegue emitir são descartados silenciosamente.

## Regras e erros

| Regra | Erro |
| --- | --- |
| Criar sem um número (chave com escopo de tenant, sem `whatsappNumberId` / cabeçalho) | **400 `NUMBER_REQUIRED`** |
| `whatsappNumberId` difere do número de uma chave com escopo de número | **400 `NUMBER_MISMATCH`** |
| `whatsappNumberId` no `PATCH` (o número não pode ser alterado após a criação — exclua e recrie) | **400 `NUMBER_RESCOPE_NOT_SUPPORTED`** |
| Número fora do seu tenant | **404 `NUMBER_NOT_FOUND`** |
| Webhook não visível no escopo da chave | **404 `WEBHOOK_NOT_FOUND`** |

<Note>
  **O `secret` de assinatura nunca é retornado** por nenhum desses endpoints.
</Note>

## Quantos webhooks por número

**Um número pode ter mais de um webhook.** O escopo é muitos-para-muitos: todo webhook ativo assinado naquele número recebe os eventos que assinou, e o segundo **não** substitui o primeiro. Use isso para separar responsabilidades — um endpoint para conversas, outro para saúde e monitoramento.

A única recusa é a **duplicata exata**: a mesma `url` no mesmo número — **409 `WEBHOOK_DUPLICATE`**. Não existe motivo legítimo para duas, e a integração que criava em vez de atualizar acumulava linhas em silêncio; agora recebe um conflito. Vale também um teto de **50** webhooks por workspace (**409 `WEBHOOK_LIMIT_REACHED`**) — deliberadamente folgado, já que um tenant com muitos números pode querer um por número.

```bash Dois endpoints no mesmo número
# 1) conversas → sua caixa de entrada / helpdesk
curl -X POST "https://pilotstatus.com.br/v1/webhooks" \
  -H "x-api-key: ps_your_token_here" -H "Content-Type: application/json" \
  -d '{ "url": "https://example.com/hooks/inbox", "name": "Inbox", "events": ["messages", "smb_message_echoes"] }'

# 2) tudo → seu endpoint de monitoramento (é a ÚNICA forma de receber a família
#    de saúde do número; veja a referência de eventos)
curl -X POST "https://pilotstatus.com.br/v1/webhooks" \
  -H "x-api-key: ps_your_token_here" -H "Content-Type: application/json" \
  -d '{ "url": "https://example.com/hooks/monitor", "name": "Monitor", "events": ["*"] }'
```

## Verifique a assinatura

**Todo webhook criado a partir de 15/09/2026 nasce assinado.** A criação cunha um segredo e devolve-o em claro naquele `201` — a única resposta na vida de um segredo que o carrega. Nenhuma leitura o traz de volta.

<Warning>
  **Webhooks criados antes dessa data não têm segredo, e continuam assim.** As entregas deles saem sem assinatura. É deliberado: ligar verificação de assinatura por baixo de uma integração viva é, por si só, uma interrupção. O `POST /v1/webhooks/{id}/rotate-secret` é como você a liga num deles — e a única forma de recuperar um segredo perdido, já que nenhuma leitura o devolve.

  Leia o `hasSecret` de cada webhook para distinguir os dois casos antes de decidir se o seu receptor pode recusar entrega sem assinatura.
</Warning>

## Rodar — ou cunhar um para um webhook antigo

```bash
curl -X POST "https://pilotstatus.com.br/v1/webhooks/wh_abc/rotate-secret" \
  -H "x-api-key: ps_your_token_here"
# → { "id": "wh_abc", "hasSecret": true, "secret": "…" }   ← em claro, uma vez
```

<Warning>
  **A rotação é imediata e não tem janela de sobreposição.** O segredo anterior deixa de verificar no instante em que a chamada retorna; entregas já em voo assinam com o valor que o despacho delas carregou. Aceite os dois segredos do seu lado durante um minuto, ou rode num momento de silêncio do número.
</Warning>

Quando um segredo está definido, o cabeçalho `x-pilot-status-signature` carrega o **HMAC-SHA256 do corpo bruto da requisição**, em hexadecimal, chaveado com o segredo. Calcule o HMAC sobre os bytes brutos exatamente como recebidos (antes de qualquer parse de JSON) e compare em tempo constante:

```javascript Node
const crypto = require("node:crypto");
const expected = crypto.createHmac("sha256", process.env.WEBHOOK_SECRET).update(rawBody).digest("hex");
const ok = crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(req.headers["x-pilot-status-signature"] ?? ""));
```

## Deduplicar retentativas: `Idempotency-Key`

Quando está presente, o `Idempotency-Key` é **estável por evento**: uma retentativa, um replay de backoff e um replay de failover do mesmo evento carregam o mesmo valor — é a chave certa para deduplicar. O mesmo valor também é mesclado no corpo JSON entregue como um campo `idempotencyKey` de primeiro nível, então dá para ler dos dois lugares.

<Warning>
  **O cabeçalho não vem em toda entrega.** Ele é derivado de um id de mensagem encontrado no payload (`messageId` / `internalMessageId`, no topo ou dentro de `data`). Um payload sem esse id não recebe **cabeçalho nenhum nem campo no corpo** — isso inclui:

  - todo **envelope nativo da Meta Cloud API** (`messages`, `smb_message_echoes`, `message_echoes`, os campos de template e de conta …), cujo topo é `{ object, entry }`;
  - os eventos `number.*` de ciclo de vida e os de saúde do número.

  Ou seja: o tráfego de conversa de um número Meta **não** é coberto por esse cabeçalho hoje. Deduplique pelos ids da própria Meta — e leia o aviso sobre wamid repetido na [referência de eventos](/pt-BR/api/webhooks/events#eventos-da-meta-cloud-api-envelope-nativo) antes de chavear só pelo wamid.
</Warning>

## Painel

Tudo acima também está disponível no painel em **`/webhooks`**: crie/edite webhooks por número, escolha eventos, pause/retome e inspecione os logs de entrega. A interface de Novo/Editar Webhook inclui o aviso de que `message.read` só dispara quando o destinatário tem os recibos de leitura do WhatsApp ativados.
