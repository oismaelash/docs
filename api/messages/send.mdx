# Send a WhatsApp Message

```text
POST https://pilotstatus.com.br/v1/messages/send
```

This is the **only** send endpoint. It supports three **mutually exclusive** top-level modes:

1. **Template send** — `templateId` (\+ optional `variables`)
2. **Free-form text send** — `text`
3. **Direct media send** — `media` \+ `mediaType` (no `templateId`, no `text`)

<Note>
  Exactly one mode must be used per request. There are no separate `/messages/text`, `/messages/media`, or `/messages/interactive` endpoints.
</Note>

## Headers

- `Content-Type: application/json`
- `x-api-key: ps_...` (or `x-api-key-id: <api_key_id>`) — a **number-scoped** key

<ParamField header="Idempotency-Key" type="string">
  **Optional.** Makes a retry safe: within **24 hours**, a second request with the same key and the same body returns the first accepted response instead of sending the message again. Any string up to **255 characters** with no control characters; too long or with a control character → **400 `IDEMPOTENCY_KEY_INVALID`**. Absent, the endpoint behaves exactly as before. See [Idempotency](#idempotency).
</ParamField>

## Destination (exactly one)

<ParamField body="destinationNumber" type="string">
  Destination phone in **E.164** with a leading `+` (e.g., `+5511999999999`).
</ParamField>

<ParamField body="groupId" type="string">
  WhatsApp group JID ending in `@g.us`.
</ParamField>

<ParamField body="newsletterId" type="string">
  WhatsApp channel JID ending in `@newsletter`.
</ParamField>

## Mode fields

<ParamField body="templateId" type="string">
  Template from the dashboard `/templates`. Mutually exclusive with `text` and direct-media mode.
</ParamField>

<ParamField body="variables" type="object">
  Key→value map for template variables. Missing required variables produce `MISSING_TEMPLATE_VARIABLES`. For a template created in Meta's console whose dynamic URL button has a numbered placeholder (`https://ctlnk.io/{{1}}` — not the body's `{{1}}`), pass the button's URL suffix as `button_<N>`, where `N` is the button's position among the template's buttons, starting at 1: `{ "1": "Maria", "button_1": "Gggkf" }`. See [Templates](/api/templates#button-placeholders-in-templates-created-in-meta). On an official number, the same key also carries the code of a copy-code button whose value has no `{{variable}}` — `{ "button_2": "BLACKFRIDAY" }`; see [Copy-code buttons on official numbers](/api/templates#copy-code-buttons-on-official-numbers).
</ParamField>

<ParamField body="text" type="string">
  Body of a free-form message. Required if `templateId` is not sent (and not doing a direct media send).
</ParamField>

<ParamField body="media" type="string">
  A public http(s) URL **or** a base64 data URI (e.g. `data:audio/ogg;base64,AAAA...`) to an image, video, document, or audio file. Base64 data URIs are accepted on Meta Cloud API and on **unofficial (Pilot Status web)** numbers. On unofficial numbers, Pilot Status uploads the decoded file to its own storage and sends the provider a URL; if that upload fails, the message fails with `MEDIA_REHOST_FAILED`. For stickers on unofficial numbers, use a public http(s) URL. Overrides any embedded `mediaUrl` in the template. Base64 is capped by decoded size: **50 MiB** (52,428,800 bytes) when `mediaType` is `document`, **16 MiB** (16,777,216 bytes) for every other type and when `mediaType` is omitted. Above the cap the request is refused with `400 Validation error`, and `details.fieldErrors.media` names the limit. Send a larger file as a public http(s) URL — on Meta Cloud API numbers it is then held to Meta's own ceilings (document 100 MB, video and audio 16 MB, image 5 MB), and a file above them fails after the `202` with `META_MEDIA_TOO_LARGE`. A URL — or a redirect it answers with — that points to an internal or private network address is never downloaded: the message fails after the `202` with `MEDIA_DOWNLOAD_FAILED`, on every number type.
</ParamField>

<ParamField body="mediaType" type="string">
  `image`, `video`, `document`, `audio`, `voice`, or `sticker`. Set it explicitly when the URL extension is not obvious (e.g. PDFs whose URL does not end in `.pdf`). `voice` is delivered as a WhatsApp **voice note (PTT)** on every number; `audio` is delivered as an **audio file** on official (Meta Cloud API) numbers and as a voice note on unofficial (Pilot Status web) numbers — to send a voice note, use `voice` (see [Audio and voice notes](/guides/media-messages#audio-and-voice-notes)). Before sending, audio is converted to AAC in MP4 (`audio/mp4`) on official numbers and to Ogg/Opus on unofficial numbers. For `audio` and `voice`, a presence indicator is shown to the contact just before delivery: unofficial (Pilot Status web) numbers show "recording audio" (gravando); Meta Cloud API numbers show "typing" (digitando) — the Cloud API has no recording variant, and it only appears when the conversation has a recent inbound message to attach to. Typing is shown before every conversational send on Meta and Evolution numbers — on Meta numbers unless `markRead` is `false` (see [Read receipt and typing](#read-receipt-and-typing)); you can also trigger it independently via [Typing Indicator](/api/messages/typing). `sticker` sends a WhatsApp **sticker** — direct media send only, never with `templateId`, never with a `caption`, and the file must be **`image/webp`** at **exactly 512×512 pixels** (static up to **100 KB**, animated up to **500 KB**).
</ParamField>

<ParamField body="mediaFilename" type="string">
  File name the recipient sees for a **document** — 1–240 characters; `/` and `\` are replaced with `_`. Accepted on:

  - a **direct document send** (`media` \+ `mediaType: "document"`, no `templateId`, no `text`). When omitted, the name falls back to the last segment of the URL.
  - a **template send whose approved template has a `DOCUMENT` header** — with `media` (the document that replaces the template's example) or without it (it renames the document stored on the template). If you also send `mediaType`, it must be `document`.

  Without `mediaFilename`, a template's document arrives with no proper title on official (Meta Cloud API) numbers — WhatsApp shows the generic "Document" — and with a name inferred from the URL on unofficial numbers. Works on Meta Cloud API, Evolution v2 and Evolution GO.

  A free-form `text` send with it returns `400` ("mediaFilename is only supported for direct media sends and templates with a document header"), as does any `mediaType` other than `document`. On a template whose header is `IMAGE`, `VIDEO`, `TEXT` or absent it returns `422` `MEDIA_FILENAME_REQUIRES_DOCUMENT_HEADER`, with `details.templateName` and `details.headerType` — the name would have nowhere to go, so it is refused rather than dropped.
</ParamField>

### Direct media send

Send media on its own by providing `media` \+ `mediaType` **without** `templateId` and **without** `text`. In this mode `buttons`, `header`, `footer`, and `variables` are **not allowed**; an optional `caption` is supported for `image`, `video`, and `document` but **not** for `audio`, `voice`, or `sticker`.

<Note>
  Media sends are available on **every plan, including Free** — they count against the number's message quota just like any other message. There is no separate paid gate for sending media.
</Note>

## Scheduling and delivery window

<ParamField body="deliverAt" type="string">
  ISO 8601 datetime to schedule the send.
</ParamField>

<ParamField body="deliverUntil" type="string">
  ISO 8601 deadline for delivery. If it expires, the message fails (see [Log Error Codes](/api/messages/log-error-codes)).
</ParamField>

## Read receipt and typing

<ParamField body="markRead" type="boolean">
  Whether this send marks the contact's last inbound message as **read** (blue ticks) and shows the **"typing"** (digitando) indicator before delivery. When omitted, the number's [`markReadOnSend`](/api/numbers/settings#read-receipt-on-send) setting decides — `true` unless you changed it. A value that is not a boolean is refused with `400`.
</ParamField>

On an **official (Meta Cloud API)** number, `markRead: false` sends the message **without** the typing indicator **and without** marking the conversation read. The two cannot be separated: the Cloud API only shows typing as part of a read receipt on the contact's last inbound message, so there is no way to show typing and keep the message unread.

Use it when an automated agent answers and a person should still find the conversation **unread** in WhatsApp later:

```json
{
  "destinationNumber": "+5511999999999",
  "text": "Thanks! A specialist will reply shortly.",
  "markRead": false
}
```

<Note>
  - On **unofficial (Pilot Status web)** numbers `markRead` has no effect: sending never marks anything read there. What marks messages read on arrival is the number's [`readMessages`](/api/numbers/settings) setting — keep it off if the conversation must stay unread.
  - The dashboard's unread counter is **not** reset by a send, whatever `markRead` says.
  - [`POST /v1/messages/typing`](/api/messages/typing) on a Meta number **also** marks the last inbound message read. An agent that wants to keep the conversation unread must not call it.
</Note>

## Other fields

<ParamField body="labels" type="string[]">
  Tag the destination with Labels (tenant scope). Processed asynchronously. With API key `retentionDays = 0`, Labels are created but the phone/group linkage may not be persisted (PII).
</ParamField>

<ParamField body="marketingOptions" type="object">
  For **MARKETING** templates only. `aiRewriteEnabled: true` enables automatic variation of the final message text to reduce repetitive patterns (anti-spam) while preserving intent. If variation cannot be applied, the original text is sent. MARKETING sends also receive an automatic variable queue delay (default **8–25 s**) to space out sending pace.
</ParamField>

<ParamField body="buttons" type="array">
  Up to 3 buttons that **override** the template's buttons (except on Meta numbers — see below). Each button has `type` and `displayText` plus type-specific fields:

  - `{ "type": "reply", "displayText": "Yes", "id": "yes" }` — quick reply
  - `{ "type": "url", "displayText": "Site", "url": "https://example.com" }` — URL button
  - `{ "type": "call", "displayText": "Call", "phoneNumber": "+5511999999999" }` — call button
  - `{ "type": "copy", "displayText": "Code", "copyCode": "ABC123" }` — copy button

  `buttons` can be combined with any `mediaType`. The API does not reject buttons with `mediaType: "video"` or `mediaType: "document"` (unofficial numbers accept them); note that Meta Cloud API may reject some button \+ video/document combinations at delivery time.

  On **Meta (official) numbers**, a template's buttons are fixed by the approved template: `buttons` does not replace them and does not fill a button variable. Fill a dynamic URL button through `variables` — by its name (e.g. `link`) or, for a numbered placeholder in a template created in Meta's console, as `button_<N>`. A copy-code button's code also goes in `variables` as `button_<N>`, not in `copyCode`.
</ParamField>

<ParamField body="header" type="object">
  Header for a free-form interactive message. Requires `buttons`. Types: `{ "type": "text", "content": "Header title" }` (up to 60 chars), or `image` / `video` / `document` with a public URL as `content`.
</ParamField>

<ParamField body="footer" type="string">
  Message footer (max 60 characters). Requires `buttons` or `list`.
</ParamField>

<ParamField body="list" type="object">
  Interactive single-select list for a free-form send. Requires `text`; mutually exclusive with `templateId`, `buttons`, `header`, and direct media (`footer` is allowed). See [Lists](#lists) below.
</ParamField>

### Free-form restrictions

- `media` and `mediaType` cannot be used with `text` (free-form).
- `header` is only supported when `buttons` is present; `footer` needs `buttons` or `list` (Meta Cloud API limitation).
- On Meta numbers, free-form messages only work within the WhatsApp **24h conversation window**. Outside the window, a `META_OUTSIDE_24H_WINDOW` error is returned in the `message.failed` webhook — use an approved template instead. You can check whether the window is open before sending with [`GET /v1/service-window`](/playground/messages/service-window).

## Buttons

`buttons` attaches up to **3** interactive buttons — on a **free-form text** send, or to **override** a template's buttons on a **template** send (not on Meta numbers — see the note below). Each item needs `type` \+ `displayText` and one type-specific field:

| `type` | Extra field | Behavior |
| --- | --- | --- |
| `reply` | `id` (string) | Quick-reply. The tap arrives as a normal inbound webhook whose `content` is the button label. The `id` comes back as `buttonId` on unofficial numbers when WhatsApp reports it, and as `interactive.button_reply.id` on official numbers. |
| `url` | `url` (https) | Opens a link. |
| `call` | `phoneNumber` (E.164) | Dials the number. |
| `copy` | `copyCode` (string) | Copies a code to the clipboard. |

```json
{
  "text": "Confirm your appointment?",
  "destinationNumber": "+5511999999999",
  "buttons": [
    { "type": "reply", "displayText": "Confirm", "id": "confirm" },
    { "type": "url", "displayText": "Details", "url": "https://example.com/order/123" }
  ]
}
```

- `header` is only allowed **together with** `buttons`; `footer` with `buttons` or `list` (Meta Cloud API limitation).
- There is no `button_reply` event. Match taps by `buttonId` when present (unofficial) or the native `button_reply.id` (official); otherwise by the label in `content` \+ `quotedMessageId`.
- On **Meta Cloud API** numbers, free-form buttons only work inside the 24-hour service window. Outside it, send an **approved template**. Template buttons use a **different vocabulary** — `QUICK_REPLY`, `URL`, `PHONE_NUMBER`, `COPY_CODE`, `PAYMENT_REQUEST` — defined when the template is created; see [Templates](/api/templates).

<Note>
  On **Meta (official) numbers**, a template's buttons are fixed by the approved template. On a template send there, request `buttons` does not replace them and does not fill a button variable — fill a dynamic URL button through `variables`, by its name (e.g. `link`) or, for a numbered placeholder in a template created in Meta's console, as `button_<N>` (see [Templates](/api/templates#button-placeholders-in-templates-created-in-meta)). The code of a copy-code button goes the same way, as `button_<N>` — not in `copyCode` (see [Copy-code buttons on official numbers](/api/templates#copy-code-buttons-on-official-numbers)).
</Note>

## Lists

`list` attaches an interactive **single-select list** to a **free-form text** send: `text` becomes the message body and `buttonText` labels the button that opens the menu of rows. Mutually exclusive with `templateId`, `buttons`, and direct media:

```json
{
  "text": "How can we help you today?",
  "destinationNumber": "+5511999999999",
  "list": {
    "buttonText": "See areas",
    "sections": [
      {
        "title": "Support",
        "rows": [
          { "id": "clients", "title": "Clients", "description": "Look up and register clients" },
          { "title": "Orders", "description": "Track an existing order" }
        ]
      }
    ]
  }
}
```

- Caps (Meta's, enforced uniformly on **every** number type): `buttonText` 1–20 chars, **1–10 sections**, max **10 rows total** across all sections, row `title` 1–24 chars, row `description` up to 72 chars, row `id` up to 200 chars (generated when absent). Section `title` is optional.
- Works on **both** number types with the same request: **Meta Cloud API** numbers send the official interactive list; **unofficial (Pilot Status web)** numbers send the native list.
- The recipient's selection arrives as a **normal inbound message/webhook**.

## Response (202)

```json
{
  "id": "msg_abc",
  "correlationId": "corr_123",
  "status": "QUEUED",
  "createdAt": "2026-02-24T15:00:00.000Z",
  "origin": "My WhatsApp"
}
```

<ResponseField name="id" type="string">
  Internal message ID. Persist this — it is the value to use with `GET /v1/messages/{id}` and it matches `internalMessageId` in webhooks.
</ResponseField>

<ResponseField name="correlationId" type="string">
  Correlation identifier for the send request.
</ResponseField>

<ResponseField name="status" type="string">
  Always `QUEUED` on accept.
</ResponseField>

A response replayed from an earlier request with the same `Idempotency-Key` carries the response header **`Idempotent-Replayed: true`**, with the same status and body as the original — the `id` is that of the message already queued. See [Idempotency](#idempotency).

## Correlation with webhooks

- The **`id`** field in the response is the same as the **`id`** field in `message.sent`, `message.delivered`, `message.read`, and `message.failed`. On **`message.reply`**, use **`quotedMessageId`** (the WhatsApp `messageId` of your original message) and **`correlationId`** to tie the reply to your send.
- The WhatsApp **`messageId`** (wamid) is **not** in the `202` body; it first appears on the **`message.sent`** webhook (and repeats on status events for that message).
- Persist **`id`** when you receive `202` and use [`GET /v1/messages/{id}`](/api/messages/status) with the same value.

## Idempotency

A client that times out or loses the connection on this request cannot tell whether the message was queued. Sending it again without protection can deliver it **twice**. The optional `Idempotency-Key` header closes that gap. What it guarantees, exactly:

- **Optional.** Without the header, nothing changes: every request is a new send.
- **24-hour window, per number.** The key is scoped to _(your workspace, the WhatsApp number of the API key, the key value)_. The same key on another number, or from another workspace, never collides with yours.
- **Same key, same body → the first response, nothing sent again.** Within the window, the request returns the stored response of the first accepted (`2xx`) call — same status, same body, same message `id` — and nothing is queued or sent. The replayed response carries the header **`Idempotent-Replayed: true`**.
- **Same key, different body → `409 IDEMPOTENCY_KEY_REUSED`.** A key identifies one message — whether the first call is still running or already finished. To send a different message, use a new key.
- **Same key while the first call is still in progress → `409 IDEMPOTENCY_KEY_IN_USE`.** Wait a moment and retry with the same key: once the first call finishes, you get its response.
- **Only `2xx` is remembered.** If the first call fails (`400`, `404`, `422 BILLING_SUSPENDED`, `429`, `5xx`…), the key is released: fix the body and retry with the **same** key.
- **Store unavailable → `503 IDEMPOTENCY_UNAVAILABLE`.** If you sent a key and the platform cannot check it, the request is refused instead of risking a duplicate — nothing was sent. It is safe to retry with the same key.

### Choosing the key

Derive the key from something stable on your side that identifies the message, so a re-run of the same job produces the same key — for example the order id plus the recipient (`order-48213-+5511999999999`). Or generate a UUID and **store it before the first attempt**, then reuse it on every retry. A key generated anew on each attempt protects nothing.

<Steps>
  <Step title="Send with a key">
    Send the request with an `Idempotency-Key` derived from your data.
  </Step>
  <Step title="On a timeout, 5xx or network error">
    Resend the **same body with the same key**. If the first call was accepted, you get its response (`Idempotent-Replayed: true`) and the message is not sent twice; if it was not, the message is sent now.
  </Step>
  <Step title="On 409 IDEMPOTENCY_KEY_IN_USE or 503 IDEMPOTENCY_UNAVAILABLE">
    Wait and retry with the same key, with backoff.
  </Step>
</Steps>

## Common errors

| Status | Meaning |
| --- | --- |
| `400` | Invalid payload (e.g., phone not in E.164, missing required fields, `MISSING_TEMPLATE_VARIABLES` / `INVALID_TEMPLATE_VARIABLE_VALUE` naming the key, or free-form not supported by the provider: `code: FREE_FORM_NOT_SUPPORTED`), or on an official number a template not approved on Meta: `code: META_TEMPLATE_NOT_APPROVED`, or an `Idempotency-Key` over 255 characters or with a control character: `code: IDEMPOTENCY_KEY_INVALID` (`details.maxLength`: `255`), or `mediaFilename` on a free-form `text` send or with a `mediaType` other than `document` |
| `401` | Missing/invalid API key header (`x-api-key` / `x-api-key-id`) |
| `403` | A tenant-scoped key used on a number-scoped endpoint |
| `404` | Template not found or without an approved version |
| `409` | A request with the same `Idempotency-Key` and the same body is still in progress (`code: IDEMPOTENCY_KEY_IN_USE`) — retry with the same key in a moment. Or the `Idempotency-Key` was already used with a different body in the last 24 hours (`code: IDEMPOTENCY_KEY_REUSED`) — use a new key |
| `422` | Tenant billing is suspended (`code: BILLING_SUSPENDED`) — dunning, or an unpaid WALLET / extras balance; regularize your credits or card to resume sending. Or `mediaFilename` on a template whose approved header is not `DOCUMENT` (`code: MEDIA_FILENAME_REQUIRES_DOCUMENT_HEADER`, `details.templateName`, `details.headerType`) |
| `429` | Rate limit |
| `503` | An `Idempotency-Key` was sent and the idempotency store is unavailable (`code: IDEMPOTENCY_UNAVAILABLE`) — nothing was sent; retry with the same key |

Asynchronous delivery failures (e.g. `META_OUTSIDE_24H_WINDOW`, `META_TEMPLATE_PAUSED`, `WHATSAPP_NOT_EXIST`) surface as `errorCode` on [`GET /v1/messages/{id}`](/api/messages/status) and [`GET /v1/messages`](/api/messages/list), in Logs, and via the `message.failed` webhook on unofficial numbers — see [Log Error Codes](/api/messages/log-error-codes).
