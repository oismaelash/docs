# Message Status

```text
GET https://pilotstatus.com.br/v1/messages/{messageId}
```

After sending a message and receiving an `id` (e.g., `msg_abc`) from [`POST /v1/messages/send`](/api/messages/send), query its current status.

To list and filter many messages (sent and received), see [`GET /v1/messages`](/api/messages/list).

<Frame caption="Log Details in the dashboard — the rendered message, template, live status (Read), and the same messageId you query via the API.">
  ![Log Details modal showing the rendered message bubble with quick-reply buttons, template name, Read status, timestamp, message ID with copy button, variables, and Resend and Full trace actions](/images/dashboard/log-details.png)
</Frame>

<Note>
  `{messageId}` accepts the internal message `id` returned by the send endpoint, the `correlationId`, or the provider WhatsApp message ID (wamid).
</Note>

<Note>
  **On an official (Meta) number** this `id` also comes back inside Meta's native status, as [`statuses[].biz_opaque_callback_data`](/api/webhooks/events#matching-a-status-to-your-send-—-biz_opaque_callback_data), so you can match the status to your send without calling this endpoint.
</Note>

## Example

<CodeGroup>

```bash x-api-key
curl "https://pilotstatus.com.br/v1/messages/msg_abc" \
  -H "x-api-key: ps_your_key_here"
```

```bash x-api-key-id
curl "https://pilotstatus.com.br/v1/messages/msg_abc" \
  -H "x-api-key-id: ck_xxx"
```

</CodeGroup>

### A failed send on an official number

A free-form message sent to an official (Meta) number after the 24-hour service window closed. Meta accepts the request and fails it afterwards, so the message has a wamid and a `sentAt`. There is no `template` key because the send used no template.

```json
{
  "id": "msg_def",
  "status": "FAILED",
  "correlationId": "corr_456",
  "destinationNumber": "+5511988887777",
  "createdAt": "2026-02-24T16:00:00.000Z",
  "sentAt": "2026-02-24T16:00:01.000Z",
  "deliveredAt": null,
  "readAt": null,
  "externalMessageId": "wamid.HBgLNTUxMTk4ODg4Nzc3Nw",
  "errorCode": "META_OUTSIDE_24H_WINDOW",
  "errorMessage": "Re-engagement message: Message failed to send because more than 24 hours have passed since the customer last replied to this number.",
  "origin": "API",
  "metaPricing": null
}
```

<ResponseField name="errorCode" type="string | null">
  Machine-readable reason for a failure, from a set listed in [Log Error Codes](/api/messages/log-error-codes). It is the same value [`GET /v1/messages`](/api/messages/list) returns for the same message. `null` when there is no error, and always `null` on `DELIVERED`, `READ`, `PLAYED` and `CANCELED`.

  **Branch on `errorCode`, never on `errorMessage`.** `errorMessage` is text for people, and its wording is not a contract. The set of codes grows, so treat a code you do not recognise as "needs review" rather than as an error.

  If the webhook for a send never arrived, query this endpoint by `id`, `correlationId` or wamid and classify the outcome by `errorCode`.
</ResponseField>

<ResponseField name="externalMessageId" type="string | null">
  The provider's message id — on an official number, Meta's wamid. `null` until the provider accepts the message, so it stays `null` on a message still `QUEUED` or refused before it left.
</ResponseField>

<ResponseField name="template" type="string">
  Name of the template the message was sent with. **The key is omitted, not `null`**, when the send used no template.
</ResponseField>

<ResponseField name="origin" type="string | null">
  Which rail the message went out on: `API`, `MCP`, `CHATWOOT`, `CHAT`, `DASHBOARD`, `SYSTEM`, or `null`. `APP` (outbound that did **not** go through us — the WhatsApp Business app on the phone, or another tool on the same WABA) appears only on [`GET /v1/messages`](/api/messages/list): those messages have no detail here.

  ⚠️ **`null` does not mean "inbound".** For that, read `direction` on [`GET /v1/messages`](/api/messages/list). A `null` on an `OUT` row is unclassified outbound — counting it as inbound undercounts your own sends in a billing report.
</ResponseField>

<ResponseField name="metaPricing" type="object | null">
  **Meta's own verdict on what this message was billed as** — `conversationId`, `originType`, `category` and `type`. `null` until Meta reports it.

  `type` separates `regular` (billed) from `free_entry_point` (window opened by an ad click) and `free_customer_service` (inside the service allowance).
</ResponseField>

<Note>
  **Do not infer the category from the template you sent.** Meta recategorizes templates (`template_category_update`), and the same send lands as `free_entry_point` or `free_customer_service` depending on how the window opened. Use `metaPricing` above.

  The same information arrives in real time on your webhook, as `pricing.category` / `pricing.type` inside `value.statuses[]` of the [native envelope](/api/webhooks/events#statuses-—-this-is-where-the-billed-category-is). `externalMessageId` (the wamid) is the field that joins the two.
</Note>

<Warning>
  **Messages sent from the phone app carry no billing block.** The ones that arrive via `smb_message_echoes` get delivered and read statuses normally, but `metaPricing` stays `null` and `pricing` never arrives on the webhook — measured in production, with no exception in the sample.

  For a billing report, **count them separately** rather than looking for a field that does not come.
</Warning>

## Statuses

| Status | Meaning |
| --- | --- |
| `QUEUED` | Queued / waiting for processing |
| `SENT` | Sent to the provider/WhatsApp |
| `DELIVERED` | Delivered to the device |
| `READ` | Marked as read |
| `PLAYED` | Voice/audio message listened to by the recipient |
| `FAILED` | Failed — branch on `errorCode` ([Log Error Codes](/api/messages/log-error-codes)); `errorMessage` has the human-readable reason |
| `CANCELED` | Scheduled send canceled via [`DELETE /v1/messages/cancel`](/api/messages/cancel) |

<Note>
  **Read receipts:** `READ` status and `readAt` are only available when the **contact who received the message** has **read receipts** enabled in WhatsApp (_Settings \> Privacy \> Read receipts_). Otherwise the lifecycle may stop at `DELIVERED`. The same applies to Logs and the `message.read` webhook.
</Note>

<Note>
  **`PLAYED` is a new value.** It is returned for voice and audio messages when the
  recipient listens to them, and it ranks **above** `READ`: a message that reaches
  `PLAYED` will not go back to `READ`. If your integration branches on `status` with an
  exhaustive `switch` or a fixed list, add `PLAYED` before it starts appearing — code
  that treats an unknown status as an error will see one.
</Note>

## Common errors

- `401` — missing/invalid API key header (`x-api-key` / `x-api-key-id`).
- `404` — message not found within the key's scope.
