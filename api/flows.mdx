Every endpoint below acts on **one number**, and that number must be a **Meta (Cloud API)** number. The WABA is derived from it — there is no parameter to name one, by design.

| Credential | How it names the number |
| --- | --- |
| Number key (`ps_number_`) | It is bound to one number already. |
| Workspace key (`ps_workspace_`), account key (`ps_account_`, plus `x-workspace-id`) or OAuth token | Send the `x-whatsapp-number-id` header. Without it the request is refused with `403` `TENANT_SCOPE_NOT_ALLOWED`. |

A number that is not Meta, or has no WABA, answers `422` `FLOW_REQUIRES_META_NUMBER`.

| Permission | Covers | Role |
| --- | --- | --- |
| `flows:read` | Listing Flows, reading a Flow's JSON, reading form responses and endpoint traces | AGENT, ADMIN, OWNER (not ANALYST) |
| `flows:manage` | Every write — create, update, upload JSON, preview, publish, deprecate, delete, sync from Meta — **and the whole `data_exchange` surface (the endpoint key and the Flow endpoint), reads included** | ADMIN, OWNER |

<Note>
  The role column applies to credentials that carry a **user** — OAuth tokens and account keys — and is checked against that user's live workspace role: a missing permission is `403` `PERMISSION_DENIED`, a user who is no longer a member is `403` `WORKSPACE_MEMBERSHIP_REQUIRED`. Number and workspace keys carry no user and are not role-gated.
</Note>

<Warning>
  **Reading the endpoint key or the Flow endpoint needs `flows:manage`, not `flows:read`**, even though both are `GET`s. Their responses carry `endpointUrl` / `endpointUri` / `metaEndpointUri`, and the token inside those URLs is a **credential**: Meta authenticates to the endpoint by decrypting, and the matching public key is public by construction. Whoever holds both can forge a request Pilot Status will decrypt and forward to your webhook under our signature. A read-only credential is still a credential — which is also why the value never appears on `GET /v1/flows`.
</Warning>

<Note>
  `flows:read` is a slug of its own and is **not** `templates:read`. A template listing returns text your workspace wrote; a Flow response returns what a **customer** typed into a form — a name, a phone, sometimes a document number. The two are gated separately on purpose.
</Note>

## List Flows

```bash
curl "https://pilotstatus.com.br/v1/flows?page=1&pageSize=30" \
  -H "x-api-key: ps_your_key_here"
```

```json
{
  "flows": [
    {
      "id": "flw_local_1",
      "metaFlowId": "1122334455",
      "name": "Agendamento",
      "metaStatus": "PUBLISHED",
      "categories": ["APPOINTMENT_BOOKING"],
      "jsonVersion": "7.1",
      "healthStatus": "AVAILABLE",
      "clonedFromFlowId": null,
      "supersededByFlowId": null,
      "createdAt": "2026-08-30T12:00:00.000Z",
      "updatedAt": "2026-09-01T09:12:00.000Z"
    }
  ],
  "total": 1, "page": 1, "pageSize": 30, "totalPages": 1
}
```

`page` starts at 1; `pageSize` defaults to 30 and is capped at 100. `page` × `pageSize` past 10,000 is `400` `INVALID_PAGINATION`.

<Note>
  `id` is the **local id** and is the only id you ever send back to us. `metaFlowId` is Meta's own and is read-only — it is `null` while a Flow exists here but has not reached Meta.
</Note>

## Create or clone

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Agendamento v2",
    "categories": ["APPOINTMENT_BOOKING"],
    "cloneFromFlowId": "flw_local_1"
  }'
```

Returns `201` with the new Flow in `DRAFT`. Omit `cloneFromFlowId` to start from scratch.

```json
{ "id": "flw_local_2", "metaFlowId": "9988776655" }
```

`name` (non-empty string, trimmed) and `categories` (non-empty array, each one of `SIGN_UP`, `SIGN_IN`, `APPOINTMENT_BOOKING`, `LEAD_GENERATION`, `CONTACT_US`, `CUSTOMER_SUPPORT`, `SURVEY`, `OTHER`) are required. Only `name`, `categories` and `cloneFromFlowId` are accepted: any other field is `400` `FLOW_UNKNOWN_FIELDS`, and `whatsappNumberId` / `wabaId` / `metaWabaId` are `400` `FLOW_NUMBER_FROM_KEY`. A body that is not a JSON object is `400` `FLOW_BODY_INVALID`.

<Warning>
  `cloneFromFlowId` is the **local id** of the source Flow — the `id` field, not `metaFlowId`. Cloning is the only way to change a Flow that has been published.
</Warning>

## Rename and re-categorize

```bash
curl -X PATCH "https://pilotstatus.com.br/v1/flows/flw_local_1" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Agendamento (matriz)", "categories": ["APPOINTMENT_BOOKING"] }'
```

Accepts **only** `name` and `categories`, at least one of them (`400` `FLOW_PATCH_EMPTY` otherwise). This never publishes and never deprecates — those have endpoints of their own, so that a mistake in a form cannot reach an irreversible operation. Answers `200`:

```json
{ "ok": true, "id": "flw_local_1" }
```

## Upload the Flow JSON

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows/flw_local_1/json" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "flowJson": "{\"version\":\"7.1\",\"screens\":[...]}" }'
```

Only a Flow in `DRAFT` accepts a document (`409` `FLOW_NOT_DRAFT` otherwise). A `200` means the document compiled, and `validationErrors` is then always empty:

```json
{ "id": "flw_local_1", "validationErrors": [] }
```

A document Meta refuses comes back as **`422` `FLOW_JSON_INVALID`**, with Meta's own list attached:

```json
{
  "error": "A Meta recusou este Flow JSON. Veja validationErrors.",
  "errorEN": "Meta rejected this Flow JSON. See validationErrors.",
  "code": "FLOW_JSON_INVALID",
  "validationErrors": [ { "error": "...", "line_start": 12, "message": "..." } ]
}
```

<Warning>
  **This is deliberately NOT how Meta's own API behaves, and the difference is the point.**

  Meta answers `200` with the problems listed _inside_ the payload — so an apparent success over an invalid document is the normal case there, and a client that only checks the status ships a Flow that never compiled.

  This route reads the list rather than the Graph status, and answers `422` whenever it is non-empty. A `200` from us therefore means what a `200` should mean. Read `validationErrors` on the `422` — it is Meta's own answer, verbatim.

  **And one refusal here is OURS, not Meta's** — see `FLOW_JSON_DEAD_FORM_PREFIX` below. Meta would have accepted that document.

  `flowJson` is a **string**, never a nested object: Meta compiles the exact bytes, and re-serializing would silently reorder what you wrote.
</Warning>

### The one refusal that is ours: `FLOW_JSON_DEAD_FORM_PREFIX`

A form value is referenced by the **literal keyword `form`** — `${form.quantity}`. The `name` of the enclosing `Form` component never appears in the reference: with a `Form` named `form_product` it is still `${form.quantity}`.

Meta accepts a document with the wrong prefix, reports `validation_errors: []`, publishes it — and then sends your endpoint `"data": {}` at runtime, where the only symptom is the person's phone saying _"Could not complete this step. Please try again."_ Since 12 September 2026 this route refuses that document instead of uploading it:

```json
{
  "error": "Este Flow JSON referencia valores pelo NOME DO FORM …",
  "errorEN": "This Flow JSON references values by the FORM'S NAME …",
  "code": "FLOW_JSON_DEAD_FORM_PREFIX",
  "deadRefs": [
    { "ref": "${form_product.quantity}", "suggestion": "${form.quantity}" }
  ]
}
```

Each entry of `deadRefs` carries the finished replacement, so the fix is a paste rather than a rule to apply by hand.

<Note>
  **Narrow on purpose, and a `200` here is not "the document is valid".** The check fires only when a reference's root matches the `name` of a `Form` declared in the same document — that case cannot resolve, ever. A root we do not recognise is left alone: our ignorance must not become your error. Everything else is still Meta's to judge, and still arrives as `FLOW_JSON_INVALID`.
</Note>

<Note>
  Each entry in `validationErrors` is Meta's, verbatim — `error`, `error_type`, `message` and `pointers` naming the offending components. One you will meet if a Flow collects files is `COMPONENT_TYPE_MAX_NUMBER_PER_SCREEN`: at most one `PhotoPicker` **or** `DocumentPicker` per screen. See [Flows](/concepts/flows) for that one quoted in full. The Node SDK reads the array with `flowJsonValidationErrors(err)`.
</Note>

## Read the Flow JSON

```bash
curl "https://pilotstatus.com.br/v1/flows/flw_local_1/json" \
  -H "x-api-key: ps_your_key_here"
```

```json
{ "id": "flw_local_1", "flowJson": "{\"version\":\"7.1\",\"screens\":[...]}" }
```

Reads the document Meta currently holds for the Flow, live from the Graph. `flowJson` is a **string**, returned byte for byte as Meta serves it — not parsed, not reformatted — so it can be edited and sent back to `POST /v1/flows/{id}/json` unchanged. Permission `flows:read`; the response is `Cache-Control: no-store`.

A Flow that has not reached Meta yet (`metaFlowId: null`) is `404` `FLOW_NOT_FOUND`. When Meta returns no document — a Flow that never received one, or a transient failure — the answer is `502` `FLOW_JSON_UNAVAILABLE`. Naming the number in the query (`whatsappNumberId`, `numberId`, `wabaId`, `metaWabaId`) is `400` `FLOW_NUMBER_FROM_KEY`.

## Preview link

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows/flw_local_1/preview" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "invalidate": false }'
```

```json
{
  "flowId": "flw_local_1",
  "previewUrl": "https://business.facebook.com/wa/manage/flows/1122334455/preview/?token=...",
  "expiresAt": "2026-09-08T12:00:00+0000",
  "invalidated": false,
  "requiresLogin": false,
  "warning": "Este link é público: ...",
  "warningEN": "This link is public: ..."
}
```

Asks Meta for the Flow's web preview link. The body is optional; `invalidate` (a real boolean) is the only field accepted, and `true` expires the previous link and mints a new one. `expiresAt` is Meta's value, verbatim, or `null` when Meta sends none. Permission `flows:manage`; the response is `Cache-Control: no-store`.

<Warning>
  **The link is public — anyone holding the URL opens the Flow with no login** (`requiresLogin: false`), so forwarding it shares the form. **And the preview is not a sandbox:** on a `data_exchange` Flow, Meta calls your endpoint for real, and whatever it writes stays written.
</Warning>

`"invalidate": "true"` (a string) is refused with `400` `FLOW_PREVIEW_INVALIDATE_INVALID` rather than coerced. When Meta returns no preview link the answer is `502` `FLOW_PREVIEW_UNAVAILABLE`.

## Publish

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows/flw_local_1/publish" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "confirm": true }'
```

<Warning>
  **Irreversible on Meta.** A published Flow can never be edited or unpublished — only cloned into a new one. `"confirm": true` (the boolean, exactly) is required; without it the request is refused with `400` `FLOW_PUBLISH_REQUIRES_CONFIRMATION`.
</Warning>

Only `confirm` is accepted. Answers `200`:

```json
{ "flowId": "flw_local_1", "published": true }
```

## Deprecate

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows/flw_local_1/deprecate" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "supersededByFlowId": "flw_local_2" }'
```

Retires the Flow without deleting it, and without deleting the responses people already submitted. `supersededByFlowId` is optional and is the successor's **local** id — but if you send it, it must name a real Flow of yours: an empty string is refused with `400` `FLOW_DEPRECATE_INVALID_SUCCESSOR` rather than silently ignored, because a broken version chain is invisible afterwards, and an id that does not resolve in your workspace is `404` `FLOW_NOT_FOUND`. The body is optional, but one that is not valid JSON is `400` `FLOW_BODY_INVALID` — never read as "no successor".

```json
{ "flowId": "flw_local_1", "deprecated": true, "supersededBy": "flw_local_2" }
```

## Delete

```bash
curl -X DELETE "https://pilotstatus.com.br/v1/flows/flw_local_1" \
  -H "x-api-key: ps_your_key_here"
```

Only a `DRAFT` can be deleted. Anything else returns `409` `FLOW_NOT_DRAFT`. Answers `200`:

```json
{ "ok": true, "id": "flw_local_1", "deleted": true }
```

## Sync from Meta

```bash
curl -X POST "https://pilotstatus.com.br/v1/flows/meta/sync" \
  -H "x-api-key: ps_your_key_here"
```

```json
{ "created": 1, "updated": 4, "seen": 5, "truncated": false }
```

Pulls the catalogue of the key's WABA from Meta into Pilot Status now, instead of waiting for the hourly sync — useful after creating or editing Flows directly in Meta's Business Manager. It takes **no fields**: send no body or `{}`. Any field is `400` `FLOW_UNKNOWN_FIELDS` (`whatsappNumberId` / `wabaId` / `metaWabaId` are `400` `FLOW_NUMBER_FROM_KEY`). Permission `flows:manage`.

`truncated: true` means the WABA has more Flows than one sync reads (20 pages of 100); the rest arrive on the next run. That is not an error.

<Note>
  **One sync per number at a time.** A second request while one is running answers `429` `FLOW_SYNC_IN_PROGRESS` with `Retry-After: 120`.
</Note>

## Read form responses

```bash
curl "https://pilotstatus.com.br/v1/flows/flw_local_1/responses?page=1&pageSize=30" \
  -H "x-api-key: ps_your_key_here"
```

Returns what customers submitted, joined to the contact who answered, within the retention window. Responses past their expiry are never served.

In a `data_exchange` Flow the answers arrive **screen by screen**, and `submitted` is where they are kept — one entry per exchange, oldest first:

```json
{
  "submitted": [
    {
      "screen": "WELCOME_SCREEN",
      "at": "2026-09-06T16:08:12.616Z",
      "data": { "observacao": "Aobaaa" },
      "omitted": null
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `screen` | The screen that exchange came from, as Meta named it. A string, or `null` when Meta named none. |
| `at` | ISO 8601 — when we decrypted that exchange, minutes before the submission that created the response around it. |
| `data` | The parsed object the person sent on that screen. `null` exactly when `omitted` says why. |
| `omitted` | `"DATA_TOO_LARGE"`, `"LIMIT_REACHED"`, `"UNREADABLE"` or `null` — **three** reasons, not two. An entry either carries `data` with `omitted: null`, or `data: null` and the reason. There is no third shape. |

<Warning>
  **In a `data_exchange` Flow, `response` is the empty place — what the person typed is here.** `response` is Meta's `nfm_reply`, parsed, and on a Flow with an endpoint that reply carries **only the `flow_token`** — `{"flow_token":"a1b2c3…"}` — while your own endpoint received `{"observacao":"Aobaaa"}` out of the very same submission. Read `response` there and you find a token, and conclude the person submitted nothing.

  On a Flow with **no** endpoint the opposite holds: there are no exchanges to capture, `submitted` is `[]`, and free-text components arrive in `response` exactly as they always have.
</Warning>

<Warning>
  **Here `submitted` is always an array — `[]` when there is nothing, never `null`.** ⛔ On the `flow.response_received` webhook the very same field is the opposite: `null`, never `[]`. That is not an inconsistency waiting to be tidied up, and "the same field behaves the same on both surfaces" is the assumption most likely to cost you an evening. The two are solving different problems.

  **On this read surface** the value comes from a lookup that answers *nothing* for a submission with no captured exchanges — and a field set to nothing **vanishes from the JSON** instead of arriving empty. `[]` is what keeps the key present, and what keeps "nothing was captured" apart from "we could not look".

  **On the event** the payload is also stored, and the redactor blanks a field only when it holds something. An empty array there would come back as the "content unavailable" marker and read as *"there were answers and we hid them"* — so `null` is the honest value there.

  So branch on `submitted.length` here and on `submitted !== null` on the event. Neither spelling is ever proof the person typed nothing. `media` below follows this surface's rule too: always an array, `[]` when nothing was attached.
</Warning>

<Note>
  **The list is shorter than the exchanges your endpoint answered, and that is correct.** Only `data_exchange` exchanges are captured. `INIT` carries the state **we** seeded — the params sent at send time, handed straight back — and `BACK` is navigation; neither is anything a person typed. Counting entries against your own traces and reporting the difference as loss is the mistake this paragraph exists to prevent.

  **It is the request Meta sends us, never what your endpoint replied.** The `data` you return on `SUCCESS`, `extension_message_response` included, is encrypted back to Meta and written down nowhere in Pilot Status — not here, not on any other surface.

  **Append-only, with no de-duplication.** Someone who walks back a screen and submits it again produces a second, genuine entry instead of replacing the first, and `at` is what separates two runs under one `flow_token`.
</Note>

<Warning>
  **Nothing is ever silently truncated — an entry missing its content says why.** An over-sized exchange keeps its row and its place in the order and says `DATA_TOO_LARGE`; one that could not be read says `UNREADABLE`. The per-form ceiling of **50 exchanges** closes the list with a final entry saying `LIMIT_REACHED`, and nothing after it was stored. That size ceiling — the one behind `DATA_TOO_LARGE` — is measured in **bytes**, not characters, so accented text reaches it sooner than its length suggests.
</Warning>

<Note>
  **A number in `RELAY_ONLY` keeps nothing here** — not a redacted entry, no entry at all: there is no stored copy to redact.

  **These entries are pruned on 30 days + 1, and the extra day is not a rounding.** An exchange is captured while the person is still filling the form, minutes before the submission that creates the response beside it. On an identical 30 days the exchanges would expire first, and a response still being served would answer `submitted: []` — indistinguishable from a form nobody typed into.
</Note>

Each response carries a `media` array — the files attached inside the form, re-hosted by us:

```json
{
  "media": [
    {
      "field": "documento",
      "mediaId": "1DC6DF81-E889-4A15-91EB-80753FB6E11B",
      "fileName": "carteira.jpg",
      "mimeType": "image/jpeg",
      "sizeBytes": 184320,
      "status": "STORED",
      "url": "https://media.pilotstatus.com.br/public/tenants/.../flow-media/....jpg"
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `field` | The key the file was listed under — whatever the **Flow's author** named the component. Not a reserved word, not a type. |
| `mediaId` | Meta's id for this file — **the only way to tell two attachments on one picker apart**, and what joins this entry to `submitted[].data.<field>[].media_id` on the same submission. `null` when Meta sent none, and `url` is `null` in the same case. Never match by array position: the two arrays are assembled from different sources. |
| `fileName` | The name the sender's device reported — and **never `null`**. A photo taken in the camera reports no name, and the **field's own name** is used in its place, so a `fileName` equal to `field` may be either and the two are indistinguishable. |
| `mimeType` | Sniffed from the decrypted **bytes**, never from the file name. `null` until stored. |
| `sizeBytes` | Size of the decrypted file. `null` until stored. |
| `status` | `PENDING` while the transfer is in flight, then `STORED` or `FAILED`. |
| `url` | A stable link of ours, **present as soon as the row exists** — including while `status` is `PENDING`. Opaque: fetch it, never build one. |

<Note>
  **`media` is always an array here — empty when nothing was attached — and that is deliberately not what the webhook does.** `flowMedia` on `flow.response_received` is `null` rather than `[]`, because the storage redactor replaces a field only when it holds something and an empty array would read as "there were attachments and we hid them". It also carries `sizeBytes`, which the event does not.

  **`[]` is not proof there was no file.** The attachment join is best-effort on purpose — an attachment we cannot read costs a *field*, never the page — so a join that fails leaves **every row on that page with `media: []`**, which is "we could not look" served as "there was nothing". Reconcile a Flow that collects files against something you kept yourself.

  **This is where the *record* is final — the URL was already final on the event.** The re-host is asynchronous: the event is emitted as soon as the submission is stored, and the transfer runs after it, so the event ordinarily arrives before the bytes are in place. `url` is a link to a route of ours and is present through all of it, on a `PENDING` row too — fetching it waits for the file and then serves it, and answers `404` with a `Retry-After` header only if that wait runs out. So read this endpoint back for `status`, `mimeType` and `sizeBytes`, not to obtain a URL the event already handed you. `url` is `null` only when the deployment has no signing secret (it then falls back to the direct object URL once `STORED`), when Meta sent no `media_id`, or on a `RELAY_ONLY` number.
</Note>

<Warning>
  **The stored object is at a public URL — whoever holds the link reads the file.** An explicit owner decision, and the same property the inbound `mediaLink` has. There is no `cdn_url` and no `encryption_metadata` on this surface or any other: Meta derives one AES key per file, and neither the key nor the CDN reference is stored or published.

  The content type comes from the bytes and is never `text/html` or `image/svg+xml`, whatever the bytes look like — both would execute script in the origin that serves them.

  **And the copy never expires.** Responses, sessions and endpoint traces are pruned on a retention window; the file is not. `flow_media_assets` carries no expiry column and nothing in the platform deletes the row or the object, so the link keeps working after the response it belonged to has stopped being served here.
</Warning>

<Note>
  **This is the stored copy, not the live one.** For submissions as they arrive, subscribe to the `flow.response_received` webhook event — the answers come with it, already parsed. The chat message that carries a submission holds only Meta's label (`Sent` / `Enviado`), so a webhook subscribed to `messages` alone sees nothing. See [Receive Flow responses](/guides/flow-responses).
</Note>

<Warning>
  **A short page can be a truncated page, and it says so.** `FlowResponse` carries no `flowId` column — the only edge from a Flow to its answers runs through the session token — so one request correlates at most **10,000** of that Flow's sends. Past that ceiling the payload carries `"notice": "FLOW_RESPONSES_WINDOW_TRUNCATED"` alongside the normal `responses`/`total`/`page`/`pageSize`/`totalPages`.

  It is a **`200`**, not an error, and the field is absent whenever nothing was cut. Read it: a caller that reconciles against a short page without checking `notice` concludes submissions were lost.
</Warning>

## Endpoint traces

```bash
curl "https://pilotstatus.com.br/v1/flows/flw_local_1/traces" \
  -H "x-api-key: ps_your_key_here"
```

```json
{
  "traces": [
    {
      "id": "cmf7t1r2a3c4e5s6",
      "action": "data_exchange",
      "screen": "WELCOME_SCREEN",
      "outcome": "CUSTOMER_ERROR",
      "httpStatus": 500,
      "durationMs": 812,
      "failureReason": "...",
      "forwardedBody": "{...}",
      "customerBody": "...",
      "createdAt": "2026-09-06T16:08:12.616Z"
    }
  ]
}
```

What **our** proxy saw on this Flow's `data_exchange` calls: Meta's `action`, the screen, the `outcome` (`FORWARDED`, `CUSTOMER_ERROR` or `NO_DESTINATION` — treat the set as open), the HTTP status your webhook answered (`null` when there was no response at all), how long it took, and on the failure path the bodies that were exchanged. It is the surface that proves "the problem is your backend, not your Flow". Permission `flows:read`; the response is `Cache-Control: no-store`.

- **Not paginated.** It returns the most recent **50** traces. Sending `page` or `pageSize` is `400` `FLOW_TRACES_NOT_PAGINATED`, because every page would return the same rows.
- **Short-lived.** A trace is served for **24 hours**. An empty list carries `"notice": "FLOW_TRACES_RETENTION_WINDOW"`, because `[]` can mean "never called" or "called, and aged out".
- **Bodies are redacted per number.** `forwardedBody` and `customerBody` are `null` on success. On a number in `RELAY_ONLY` — or when the number behind a trace can no longer be resolved — they are replaced with `"conteúdo indisponível"`; `outcome`, `httpStatus`, `durationMs` and `failureReason` stay intact.
- The Flow is resolved inside the key's WABA; a Flow of another WABA is `404` `FLOW_NOT_FOUND`.

## `data_exchange` endpoint key

<Note>
  Only needed for Flows whose screens call your backend — see [Connect your API to a Flow](/guides/flow-data-exchange) for the full picture. `{numberId}` is the number your API key is bound to. The private key never leaves Pilot Status and is returned by no endpoint; `endpointUrl` is the base to register on your Flow, with the Flow id appended as a final segment.

  **The key is per number; the forwarding URL is per Flow.** Both have a surface here — the key below, the URL under [Flow endpoint](#flow-endpoint) — and neither appears on `GET /v1/flows`, deliberately: an API key can be a third-party application, and the address of your internal webhook is not something a read-only integration is owed.
</Note>

<Note>
  **Both endpoints act on the key's own number, and `{numberId}` in the path must agree with it.** A number-scoped key names its number by itself; an account-wide key must narrow with `x-whatsapp-number-id`. A path id that does not match answers `404` `FLOW_NUMBER_NOT_FOUND` — never `403`, and the same body whether the id belongs to another tenant or to another of your own numbers, so that a wrong guess learns nothing.

  `uploadedAt` is `null` when a pair was generated here but Meta never accepted it. That is not the same as no key at all, and it is the state a repeat `POST` resumes rather than replaces.
</Note>

### Read the current state

```bash
curl "https://pilotstatus.com.br/v1/numbers/{numberId}/flow-endpoint-key" \
  -H "x-api-key: ps_your_key_here"
```

```json
{
  "configured": true,
  "publicKey": "-----BEGIN PUBLIC KEY-----\n...",
  "uploadedAt": "2026-09-02T10:00:00.000Z",
  "endpointUrl": "https://pilotstatus.com.br/api/flows/endpoint/AbC123...",
  "metaStatus": "VALID"
}
```

| `metaStatus` | Meaning |
| --- | --- |
| `VALID` | Meta holds the key we hold. Nothing to do. |
| `MISMATCH` | Meta holds a **different** key. Every `data_exchange` Flow on this number is failing — rotate. |
| `NOT_SET` | Meta holds no key for this number yet. |
| `UNKNOWN` | We could not read Meta's side. |

<Warning>
  **`UNKNOWN` is not `NOT_SET`, and collapsing them is expensive.** A Graph call that failed says nothing about what Meta holds. Treating it as "no key" means rotating — and rotating replaces a key that was probably fine.
</Warning>

### Generate, rotate, or import

One `POST`, two verbs. **The presence of `privateKey` decides which**, and they are not interchangeable: generating registers a new public key at Meta and replaces whatever was there; importing registers nothing.

| Body | What it does |
| --- | --- |
| `{}` | **Generate** — mint an RSA-2048 pair, store the private half encrypted, register the public half with Meta. |
| `{"privateKey": "-----BEGIN PRIVATE KEY-----\n…"}` | **Import** — store the key you already own. Nothing is registered with Meta. |
| `{"privateKey": "…", "passphrase": "…"}` | Import a passphrase-protected PEM. |
| `{…, "confirm": true}` | Required when either verb would replace a key that is **live** at Meta. |

Only `confirm`, `privateKey` and `passphrase` are accepted; anything else is refused, never ignored. The response is the read shape above plus `"replaced"`, which says whether a key that was live has just been displaced — a `200` alone does not.

```bash
# Generate
curl -X POST "https://pilotstatus.com.br/v1/numbers/{numberId}/flow-endpoint-key" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{}'
```

```bash
# Import
curl -X POST "https://pilotstatus.com.br/v1/numbers/{numberId}/flow-endpoint-key" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "privateKey": "-----BEGIN PRIVATE KEY-----\nMIIEvQIBADAN...\n-----END PRIVATE KEY-----\n" }'
```

<Warning>
  **Replacing a LIVE key requires `{"confirm": true}`, on both verbs.**

  Generating is destructive at Meta: Meta holds exactly one public key per phone number, so registering a new one replaces the old — and the previous private half is overwritten here at the same moment. It cannot be restored, and every `data_exchange` exchange in flight on that number stops decrypting.

  Importing is destructive **here**: nothing at Meta changes, but the stored private half is replaced, and if Meta cannot confirm the new one the number is left holding a key that may decrypt nothing. The two are refused with different codes for that reason — `FLOW_ENDPOINT_KEY_REQUIRES_CONFIRMATION` and `FLOW_ENDPOINT_KEY_IMPORT_REQUIRES_CONFIRMATION` — because a caller who read "this replaces your Meta registration" after an import would go checking Meta for a change that never happened.

  ⚠️ The **first** setup does not ask, and neither does retrying a key Meta never accepted (`uploadedAt: null`) — there is nothing to destroy in either case. A confirmation demanded where nothing can be lost trains the reflex that disarms it in the one case where it protects.
</Warning>

<Note>
  **An import is verified before it is stored.** We derive the public half from the key you sent and compare it with Meta's: a match is stored and stamped (`metaStatus: "VALID"`); a **mismatch is refused outright** with `FLOW_ENDPOINT_KEY_IMPORT_MISMATCH` and nothing is written; a Graph call we could not make leaves the key stored with `uploadedAt: null` and `metaStatus` `UNKNOWN`/`NOT_SET`, which is the "not confirmed" state, not a failure.
</Note>

<Warning>
  **`passphrase` is used once and is not stored.** It opens the PEM; the key is then kept normalised and encrypted at rest, and the passphrase has no reader afterwards. Keep your own copy — we cannot return it. Send it only when the key has one (an empty string is a passphrase, not the absence of one), and never on its own: `passphrase` without `privateKey` is refused with `FLOW_ENDPOINT_KEY_PASSPHRASE_ORPHAN`, because that same request would otherwise **generate** a pair and replace your registration at Meta.
</Warning>

## Flow endpoint

Where a `data_exchange` Flow's decrypted exchanges are forwarded. Per **Flow**, `flows:manage` on every verb including the `GET`, and `{flowId}` is the **local** id from `GET /v1/flows`.

One path, two different acts. `GET` reads that state and `PUT` / `PATCH` store **your** destination; none of the three talks to Meta. `POST` registers **our** proxy as the Flow's `endpoint_uri` **at Meta**.

```bash
curl "https://pilotstatus.com.br/v1/flows/{flowId}/endpoint" \
  -H "x-api-key: ps_your_key_here"
```

```bash
curl -X PUT "https://pilotstatus.com.br/v1/flows/{flowId}/endpoint" \
  -H "x-api-key: ps_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "url": "https://api.your-company.com/flows/booking" }'
```

```bash
# Register OUR proxy as this Flow's endpoint_uri at Meta
curl -X POST "https://pilotstatus.com.br/v1/flows/{flowId}/endpoint" \
  -H "x-api-key: ps_your_key_here"
```

```json
{
  "flowId": "flw_local_1",
  "url": "https://api.your-company.com/flows/booking",
  "hasSecret": true,
  "endpointUri": "https://pilotstatus.com.br/api/flows/endpoint/AbC123.../1122334455",
  "metaEndpointUri": null,
  "drift": false,
  "numberHasKey": true,
  "numberKeyUploadedAt": "2026-09-02T10:00:00.000Z",
  "warnings": ["FLOW_ENDPOINT_META_URI_UNKNOWN"],
  "secret": "9f2c…"
}
```

| Field | Meaning |
| --- | --- |
| `url` | Your destination. `null` when the Flow has none. |
| `hasSecret` | Whether a signing secret exists. The secret itself is never readable. |
| `endpointUri` | **Our** proxy URL for this Flow — the value Meta's `endpoint_uri` must hold. |
| `metaEndpointUri` | What Meta has registered, as the hourly sync last read it. |
| `drift` | `true` only when both are known and differ — Meta is calling someone else. |
| `numberHasKey` / `numberKeyUploadedAt` | The key state of the number this credential is bound to. |
| `warnings` | Every reason this Flow will not work. Treat the set as open. |
| `secret` | **Only on the response that minted it**, and never again. |

<Note>
  Body fields: `url` (required, `https://` or an explicit `null` to clear — never omitted) and `rotateSecret` (boolean). `PUT` and `PATCH` are the same operation. The number comes from the credential and is refused in the body (`FLOW_NUMBER_FROM_KEY`).

  **Saving the URL does not register anything at Meta** — that is a separate act against a separate system, so that a rename cannot silently hijack a Flow already pointed at someone else's endpoint. `metaEndpointUri`, `drift` and `warnings` are how you see the difference.
</Note>

### Register `endpoint_uri` at Meta

`POST` to the same path writes `endpointUri` into the Flow's `endpoint_uri` at Meta. The body is optional; `confirmOverwrite` (boolean) is the only field it accepts, and the number comes from the credential as everywhere else. The response is the state shape above **without** `secret` — `POST` never mints one.

<Warning>
  **A `data_exchange` Flow cannot be published until this is done.** Meta refuses `publish` with *"Publishing without specifying 'endpoint_uri' is forbidden"*.
</Warning>

<Note>
  **Idempotent.** A Flow already pointing at us answers `200` with no write at Meta. The check reads Meta live rather than the hourly-synced `metaEndpointUri`, because that column is silent about a URI registered in the last hour — the exact window in which two people wire the same Flow.
</Note>

The `POST` response adds two fields to the state shape: `republished` and `finalStatus`.

<Warning>
  **Writing `endpoint_uri` on a `PUBLISHED` Flow makes Meta move it back to `DRAFT`.** When that happens we publish it again in the same request and answer `republished: true` with `finalStatus: "PUBLISHED"`. If that re-publish fails, or Meta does not report `PUBLISHED` afterwards, the answer is `502` `FLOW_REPUBLISH_FAILED` with `finalStatus` in the body: the endpoint **was** registered, and the Flow is left in `DRAFT` — publish it again. When nothing was written, `republished` is `false` and `finalStatus` is the status Meta reported.
</Warning>

<Warning>
  **`409 FLOW_ENDPOINT_URI_WOULD_OVERWRITE` names the endpoint you are about to displace**, in `currentEndpointUri`. Ours is not echoed — it embeds the number's endpoint token, which is the credential of the proxy.

  Re-sending with `{"confirmOverwrite": true}` takes the Flow over, and **that removes every exchange of it from whoever answers today**. Meta's write is a plain overwrite: no merge, no undo, and no notice to the displaced endpoint.
</Warning>

<Warning>
  **`secret` is shown exactly once, on the request that minted it.** It is stored encrypted with no read path back. `secret: null` on a later save means one already existed and was kept — `hasSecret` is what says whether there is one at all. `{"rotateSecret": true}` mints a fresh one, and is the only exit from a secret that leaked.
</Warning>

<Note>
  **Over an OAuth token, every secret this route mints is written to an audit trail** (user, OAuth client, workspace, Flow, IP, user agent — never the secret), with the same role rule as the rest of the route (`flows:manage`: ADMIN and OWNER).

  - `rotateSecret: true` is recorded **before** rotating. If the audit row cannot be written, nothing is rotated and the answer is `500` `OAUTH_SECRET_AUDIT_UNAVAILABLE`.
  - A secret minted by the first save is recorded **after** the save. If the audit row cannot be written, the destination is still saved but the secret is withheld: `secret: null`, plus `secretWithheld: true`, `secretWithheldReason` and `secretWithheldCode: "OAUTH_SECRET_AUDIT_UNAVAILABLE"`. Send `rotateSecret: true` to obtain a new one.

  API keys never go through this trail.
</Note>

Full walkthrough, including the contract your endpoint must satisfy: [Connect your API to a Flow](/guides/flow-data-exchange).

## Errors

Every failure of this surface answers the same envelope — there is exactly one shape to read, and one spelling:

```json
{ "error": "<Portuguese>", "errorEN": "<English>", "code": "<CODE>" }
```

`FLOW_JSON_INVALID` adds a `validationErrors` array; `FLOW_JSON_DEAD_FORM_PREFIX` adds `deadRefs`; `FLOW_ENDPOINT_URI_WOULD_OVERWRITE` adds `currentEndpointUri`; `FLOW_REPUBLISH_FAILED` adds `finalStatus`. `FLOW_UNKNOWN_FIELDS` names the offending keys **in the message** only. Never assume the set of codes is closed — branch on the ones you handle and fall through to `code` for the rest.

When Meta's Graph refuses a call, the answer is `400` with the same envelope, Meta's reason translated into both languages, and a `code` derived from Meta's error. Authentication and authorization failures (`401`, `403` `TENANT_SCOPE_NOT_ALLOWED` / `PERMISSION_DENIED` / `WORKSPACE_MEMBERSHIP_REQUIRED`) use the standard `/v1` envelope, `{ "error", "code" }`.

| Code | Status | Meaning |
| --- | --- | --- |
| `FLOW_NOT_FOUND` | 404 | No Flow with that id inside your key's WABA — or, on routes that call Meta, a Flow that has not reached Meta yet (`metaFlowId: null`) |
| `FLOW_NOT_DRAFT` | 409 | The Flow left `DRAFT` — clone it to start a new version |
| `FLOW_REQUIRES_META_NUMBER` | 422 | The key's number is not a Meta number, or has no WABA |
| `FLOW_NUMBER_FROM_KEY` | 400 | The request named the number or the WABA (`whatsappNumberId`, `numberId`, `wabaId` or `metaWabaId`, in the body — or in the query on `PATCH`/`DELETE /v1/flows/{id}` and `GET /v1/flows/{id}/json`) — it comes from the key, and is never accepted alongside it |
| `FLOW_JSON_INVALID` | 422 | Meta refused the document — read `validationErrors` |
| `FLOW_JSON_DEAD_FORM_PREFIX` | 422 | **Ours.** The document references form values by the `Form`'s own name — read `deadRefs` |
| `FLOW_JSON_REQUIRED` | 400 | `flowJson` absent or empty |
| `FLOW_NAME_REQUIRED` | 400 | `name` missing on create |
| `FLOW_NAME_INVALID` | 400 | `name` present but not a usable string |
| `FLOW_CATEGORY_INVALID` | 400 | A category outside the set Meta accepts |
| `FLOW_CLONE_SOURCE_INVALID` | 400 | `cloneFromFlowId` is not a usable local id |
| `FLOW_PATCH_EMPTY` | 400 | `PATCH` with neither `name` nor `categories` |
| `INVALID_BODY` | 400 | `PATCH` body that is not valid JSON (an empty body answers `FLOW_PATCH_EMPTY`). This one uses the standard `/v1` envelope — `error` carries both languages, no `errorEN`. See [Malformed JSON body](/api/overview#malformed-json-body) |
| `FLOW_UNKNOWN_FIELDS` | 400 | The body carried a field the route does not accept |
| `FLOW_PUBLISH_REQUIRES_CONFIRMATION` | 400 | `publish` without `"confirm": true` |
| `FLOW_DEPRECATE_INVALID_SUCCESSOR` | 400 | `supersededByFlowId` present but not a non-blank string. An id that does not resolve is `404` `FLOW_NOT_FOUND` |
| `FLOW_JSON_UNAVAILABLE` | 502 | `GET /v1/flows/{id}/json`: Meta returned no document for this Flow |
| `FLOW_PREVIEW_INVALIDATE_INVALID` | 400 | `invalidate` is not a boolean. `"true"` is not coerced |
| `FLOW_PREVIEW_UNAVAILABLE` | 502 | Meta returned no preview link |
| `FLOW_TRACES_NOT_PAGINATED` | 400 | `page` or `pageSize` sent to `GET /v1/flows/{id}/traces`, which is not paginated |
| `FLOW_SYNC_IN_PROGRESS` | 429 | A sync of this number is already running. Retry after `Retry-After` seconds (120) |
| `FLOW_REPUBLISH_FAILED` | 502 | `endpoint_uri` was registered, but the Flow Meta moved to `DRAFT` could not be published again — read `finalStatus` and publish it |
| `OAUTH_SECRET_AUDIT_UNAVAILABLE` | 500 | OAuth only: the secret rotation could not be recorded in the audit trail, so it was not performed. Standard `/v1` envelope |
| `FLOW_ENDPOINT_KEY_REQUIRES_CONFIRMATION` | 400 | Generating over a LIVE key without `"confirm": true` |
| `FLOW_ENDPOINT_KEY_IMPORT_REQUIRES_CONFIRMATION` | 400 | Importing over a LIVE key without `"confirm": true` |
| `FLOW_ENDPOINT_KEY_IMPORT_MISMATCH` | 400 | The imported key is not the one Meta has registered. **Nothing was written** |
| `FLOW_ENDPOINT_KEY_PASSPHRASE_REQUIRED` | 400 | The PEM is passphrase-protected and none was sent |
| `FLOW_ENDPOINT_KEY_PASSPHRASE_WRONG` | 400 | The passphrase does not open the key — the key itself was not rejected |
| `FLOW_ENDPOINT_KEY_PASSPHRASE_ORPHAN` | 400 | `passphrase` with no `privateKey`. Refused, not ignored: without the key this request would **generate** a pair |
| `FLOW_ENDPOINT_KEY_PEM_INVALID` | 400 | `privateKey` is unreadable as PEM, is not RSA, or is under 2048 bits |
| `FLOW_ENDPOINT_KEY_IMPORT_INVALID` | 400 | `privateKey` or `passphrase` present but not a string |
| `FLOW_ENDPOINT_KEY_UNAVAILABLE` | 500 | Ours. The private half cannot be stored encrypted, and we refuse to generate rather than store it in the clear |
| `FLOW_ENDPOINT_URL_REQUIRED` | 400 | `url` absent or unusable. It may be `null` **explicitly**, never by omission |
| `FLOW_ENDPOINT_URL_NOT_HTTPS` | 400 | The destination is not `https://`. The refused URL is not echoed back |
| `FLOW_ENDPOINT_ROTATE_INVALID` | 400 | `rotateSecret` is not a boolean. `"true"` is not coerced |
| `FLOW_ENDPOINT_CONFIRM_INVALID` | 400 | `confirmOverwrite` is not a boolean. `"false"` is a truthy string and is refused, never read as consent |
| `FLOW_ENDPOINT_URI_WOULD_OVERWRITE` | 409 | Meta already points this Flow at another endpoint — named in `currentEndpointUri`. Re-send with `confirmOverwrite: true` to take it over |
| `FLOW_ENDPOINT_NUMBER_HAS_NO_KEY` | 422 | The number holds no Flow endpoint key, so there is no URL to register at Meta. Generate the key first |
| `FLOW_ENDPOINT_SECRET_UNAVAILABLE` | 500 | Ours. The signing secret cannot be stored encrypted, and forwarding unsigned is not an option |
| `FLOW_NUMBER_WABA_MISMATCH` | 422 | The key's number is not in the WABA that owns this Flow and can never send it |
| `FLOW_NUMBER_NOT_FOUND` | 404 | The number in the path is not the number this key is bound to |
| `FLOW_BODY_INVALID` | 400 | Malformed body, or a required field missing |
| `INVALID_PAGINATION` | 400 | `page` × `pageSize` past the deep-offset ceiling |
| `INTERNAL_ERROR` | 500 | Ours. Retry, then tell support the code |

<Note>
  The last two carry **no `FLOW_` prefix** — they are shared across the public API and keep their global spelling. A client matching on `code.startsWith("FLOW_")` would miss both.
</Note>
