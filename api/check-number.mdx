Check whether one or more phone numbers are registered on WhatsApp, using the connected number's own session. Useful to validate a list before sending, or to resolve the exact registered digits (jid local-part) that WhatsApp will actually deliver to.

## Endpoint

`POST https://pilotstatus.com.br/v1/numbers/check`

## Availability (unofficial numbers only)

<Warning>
  This lookup is only available for **unofficial (Pilot Status web) numbers**. The Meta Cloud API has **no** number-existence lookup, so a **Meta** number returns:

  ```json
  HTTP 400
  { "error": "…", "code": "NOT_SUPPORTED_FOR_META" }
  ```
</Warning>

## Required headers

- `x-api-key: <your_number_scoped_key>` — a **number-scoped** key (`ps_*`), or an account-wide key together with the `x-whatsapp-number-id: <numberId>` header, which selects the number to check against. An account-wide key without that header gets `403 TENANT_SCOPE_NOT_ALLOWED`.
- **OAuth / MCP tokens and account keys** (`ps_account_`) also need the `contacts:read` permission (roles `AGENT`, `ADMIN`, `OWNER`); the `ANALYST` role gets `403 PERMISSION_DENIED`.

## Request body

Send **either** a list or a single number:

<ParamField body="numbers" type="string[]">
  Phone numbers to check (1–20 items). Each may be in any common format (E.164, with/without `+`, with separators).
</ParamField>

<ParamField body="number" type="string">
  A single number — treated as `numbers: [number]`.
</ParamField>

An empty/invalid body (no numbers, more than 20, wrong types, none of the inputs a phone number) returns **`400 VALIDATION_ERROR`** — so does a body that is not valid JSON. If both are sent, `numbers` wins and `number` is ignored. Inputs that do not look like a phone number are dropped from the results.

```json
{ "numbers": ["+5511955554444", "5511888888888"] }
```

```json
{ "number": "+5511955554444" }
```

## Brazil (\+55) 9th-digit double-check

Brazilian mobile numbers are ambiguous: the same line may be registered on WhatsApp **with or without** the extra `9` after the area code. To avoid false negatives, each `+55` mobile input is checked **both** with and without the 9th digit, and the input counts as existing if **any** variant is registered.

The returned `number` is the **registered** digits of the matching variant — which may differ from what you sent.

**Example:** sending `"+5511955554444"` (with the 9th digit) can resolve to the registered number `"551155554444"` (without it):

```json
{
  "results": [
    { "input": "+5511955554444", "exists": true, "number": "551155554444", "name": "Maria Souza" }
  ]
}
```

## Example

<CodeGroup>

```bash cURL
curl -X POST "https://pilotstatus.com.br/v1/numbers/check" \
  -H "Content-Type: application/json" \
  -H "x-api-key: ps_your_key_here" \
  -d '{ "numbers": ["+5511955554444", "5511888888888"] }'
```

```json Response (200)
{
  "results": [
    { "input": "+5511955554444", "exists": true,  "number": "551155554444", "name": "Maria Souza" },
    { "input": "5511888888888",  "exists": false, "number": null,           "name": null }
  ]
}
```

</CodeGroup>

## Result object fields

<ResponseField name="input" type="string" required>
  The original string you sent, echoed back so you can correlate results.
</ResponseField>

<ResponseField name="exists" type="boolean" required>
  `true` if **any** candidate variant of the input is registered on WhatsApp, else `false`.
</ResponseField>

<ResponseField name="number" type="string | null" required>
  The **registered** WhatsApp digits (jid local-part) of the matching variant — `null` when not registered. For `+55` mobiles this may drop the 9th digit (see above).
</ResponseField>

<ResponseField name="name" type="string | null" required>
  The public WhatsApp display name when the provider returns one, else `null`.
</ResponseField>

## Common errors (stable API codes)

- `400 VALIDATION_ERROR` — missing/invalid body (no numbers, more than 20, or wrong types).
- `400 NOT_SUPPORTED_FOR_META` — the number is a Meta Cloud API number (no existence lookup on Meta).
- `400 NUMBER_NOT_FOUND` — the credential resolves to no WhatsApp number with a connected instance.
- `409 WHATSAPP_INSTANCE_NOT_CONNECTED` — the session is not `OPEN`.
- `409 LINKED_WHATSAPP_INSTANCE_NOT_FOUND` — the instance the key points at was removed.
- `503 WHATSAPP_SESSION_KEY_MISSING` — the unofficial provider's session key is not configured for the instance.
- `401` — missing or invalid credential (`{"error": "Invalid API key"}`).
- `403 TENANT_SCOPE_NOT_ALLOWED` — an account-wide key without `x-whatsapp-number-id`.
- `403 PERMISSION_DENIED` — OAuth/MCP token or account key whose role lacks `contacts:read`.
- Upstream provider failures surface as `WHATSAPP_UPSTREAM_ERROR` (with the provider's status, `details.status` and `details.body`) / `502 WHATSAPP_INVALID_JSON` (same envelope as the group endpoints).
