# Create, connect and delete numbers

Create a WhatsApp number via the public API, connect it (QR code or pairing code), and delete it when no longer needed.

<Note>
  Use a **tenant-scoped** API key (recommended for SaaS platforms managing multiple numbers). Authenticate with `x-api-key: ps_...`.

  **A number key cannot create numbers.** A number key (`ps_number_`, or a legacy number-scoped `ps_` key) on `POST /v1/numbers`, `POST /v1/numbers/meta` or `POST /v1/numbers/remote-pairing` gets `403 NUMBER_KEY_CANNOT_CREATE_NUMBER`, before anything is looked up or created. Use a workspace key — also when you narrow it with `x-whatsapp-number-id` — or an account key with `x-workspace-id`. See [API key types](/api/key-types).

  With an OAuth / MCP token or an account key (`ps_account_`), the workspace role is checked: creating, connecting and logging out a number need `numbers:connect`, deleting needs `numbers:delete` and restoring needs `numbers:restore` — **Admin or Owner** — and purging needs `numbers:purge` — **Owner** only. Otherwise the answer is `403 PERMISSION_DENIED`. Workspace and number keys (`ps_workspace_`, `ps_number_`) carry no role and are not subject to this check.
</Note>

## POST /v1/numbers — Create a number

```bash
curl -X POST "https://pilotstatus.com.br/v1/numbers" \
  -H "Content-Type: application/json" \
  -H "x-api-key: ps_your_token_here" \
  -d '{
    "name": "My WhatsApp",
    "number": "+5511999999999"
  }'
```

<ParamField body="name" type="string" required>
  Display name for the number (1–60 characters).
</ParamField>

<ParamField body="number" type="string" required>
  The phone number in E.164 format (e.g. `+5511999999999`): digits only, optional leading `+`, at least 10 characters.
</ParamField>

<ParamField body="settings" type="object">
  Optional — the same `settings` block as [`PATCH /v1/numbers/{id}`](/api/numbers/settings), applied before the number connects. This is where `historyImportEnabled` has to be decided. An invalid block answers `400 INVALID_SETTINGS` and nothing is created.
</ParamField>

<ParamField body="piiMode" type="string" default="STORE_INDEFINITE">
  Optional data-retention policy: `STORE_INDEFINITE`, `STORE_X_DAYS` or `RELAY_ONLY` — see [Number settings](/api/numbers/settings). Any other value answers `400` `{ "error": "Invalid piiMode" }`.
</ParamField>

<ParamField body="piiRetentionDays" type="integer">
  Required with `piiMode: "STORE_X_DAYS"`: an integer from 1 to 3650. Ignored for the other modes.
</ParamField>

<ParamField body="linkToApiKey" type="boolean" deprecated>
  **Retired — accepted but does nothing.** Sending it is not an error, and no API key is touched: `linkedApiKeyId` in the response is **always `null`**. It used to re-point a number-scoped key at the number you had just created, silently unscoping it from the number it was bound to.
</ParamField>

The response includes `qrcodeBase64` and `pairingCode` (WhatsApp letter pairing code; may be `null` if the provider does not return one). Show the QR code to the person who owns the phone, or let them type the pairing code.

```json Response (201)
{
  "numberId": "cmm0abc123",
  "instance": {
    "id": "cmm0inst456",
    "number": "5511999999999",
    "name": "My WhatsApp",
    "provider": "PILOT_STATUS",
    "status": "CONNECTING"
  },
  "qrcodeBase64": "data:image/png;base64,iVBORw0KGgo...",
  "pairingCode": "ABCD-1234",
  "linkedApiKeyId": null
}
```

<ResponseField name="numberId" type="string">
  The **number id** — the same `id` that [`GET /v1/numbers`](/api/numbers/list) returns, that `DELETE /v1/numbers/{id}` takes, and that every webhook carries in `data.numberId`. Store it now: you no longer need to list the numbers to find the id of the one you just created.
</ResponseField>

`instance` is unchanged, and `instance.id` is still the **instance** id, not the number id. Key your records on `numberId`.

The `201` also carries `settings` — the [settings](/api/numbers/settings) the number was created with, defaults included — and, when the body set one of the unofficial-number fields, `settingsSync` (`applied` / `failed` / `skipped`) reporting the push to the provider.

<Warning>
  Call these endpoints only from your **backend** — never expose your `ps_` key in the browser.
</Warning>

### Meta (official Cloud API) numbers

`POST /v1/numbers` creates an **unofficial (QR-paired)** number. For official Meta Cloud API numbers, use one of the Meta flows instead:

- `POST /v1/numbers/meta` — direct BYO-WABA: bring your own WABA credentials, or
- Hosted Meta Embedded Signup via a [remote pairing link](/api/numbers/remote-pairing) with `metaFlow`.

### POST /v1/numbers/meta — bring your own WABA

Provisions an **official Meta Cloud API number** from WABA credentials you already own. This flow is for platforms that already control the WABA and hold a **system-user token**. If you don't have these credentials, use the hosted Embedded Signup via a [remote pairing link](/api/numbers/remote-pairing) with `provider=META` instead.

A workspace key can call it. A number key is refused (`403 NUMBER_KEY_CANNOT_CREATE_NUMBER`), and so is an OAuth token granted specific numbers (`403 NUMBERS_GRANT_NOT_ALLOWED`). Over OAuth or with an account key it needs `numbers:connect` (Admin or Owner).

```bash
curl -X POST "https://pilotstatus.com.br/v1/numbers/meta" \
  -H "Content-Type: application/json" \
  -H "x-api-key: ps_your_token_here" \
  -d '{
    "name": "My Official Number",
    "number": "+5511999999999",
    "metaPhoneId": "123456789012345",
    "metaWabaId": "987654321098765",
    "metaAccessToken": "EAAG...",
    "metaAppSecret": "your_meta_app_secret",
    "metaAppId": "112233445566778"
  }'
```

<ParamField body="name" type="string" required>
  Display name for the number (1–60 characters).
</ParamField>

<ParamField body="number" type="string" required>
  The phone number as digits, with an optional leading `+` (at least 8 characters).
</ParamField>

<ParamField body="metaPhoneId" type="string" required>
  The Meta **phone number ID** of the WABA phone.
</ParamField>

<ParamField body="metaWabaId" type="string" required>
  The **WhatsApp Business Account (WABA) ID**.
</ParamField>

<ParamField body="metaAccessToken" type="string" required>
  A **system-user access token** with access to the WABA.
</ParamField>

<ParamField body="metaAppSecret" type="string" required>
  The app secret of your Meta app.
</ParamField>

<ParamField body="metaAppId" type="string" required>
  The ID of your Meta app.
</ParamField>

<ParamField body="routeWebhooksToPilot" default="false" type="boolean">
  When `true`, Pilot Status subscribes your WABA to **its own** webhook callback (setting Meta's `override_callback_uri` plus a per-number verify token), so inbound messages reach Pilot automatically — you never paste a webhook URL into your Meta App Dashboard. The response then returns `webhook.routedToPilot: true`.

  **Default `false`.** The override is a single per-WABA value, so enabling it **redirects every number on that WABA** away from whatever callback your app currently uses (for example your own backend, or an existing Chatwoot). Only set it when you want Pilot Status to own this WABA's webhook delivery.
</ParamField>

<ParamField body="linkToApiKey" type="boolean" deprecated>
  **Retired — accepted but does nothing**, exactly as on `POST /v1/numbers` above. `linkedApiKeyId` in the response is always `null`.
</ParamField>

Errors:

- `400 INVALID_BODY` — the body of `POST /v1/numbers` or `POST /v1/numbers/meta` is not valid JSON; nothing is created. See [Malformed JSON body](/api/overview#malformed-json-body).
- `400` — `{ "error": "Validation error", "details": … }`: missing or invalid body fields. On `POST /v1/numbers` also `400 INVALID_SETTINGS` (bad `settings` block) and `400` `{ "error": "Invalid piiMode" }` / the `piiRetentionDays` message.
- `402 PLAN_NUMBER_LIMIT_REACHED` — your plan's own number allowance is full. **On the Free plan** adding credits does **not** clear it: free a slot, buy an extra number yourself or move up a plan. **On a paid plan** it is answered only when you never bought an extra number and the next one cannot be funded.
- `402 INSUFFICIENT_FUNDS` — paid plans only: the number would be a **paid extra** and there is neither wallet balance nor a saved card.
- `403 NUMBER_KEY_CANNOT_CREATE_NUMBER` — a number key (`ps_number_`, or a legacy number-scoped `ps_` key) cannot create numbers. Use a workspace key or an account key. The body is `{ "error": "A number key cannot create WhatsApp numbers: use a workspace API key or an account API key (ps_account_…) to connect a new number | Uma chave de número não pode criar números de WhatsApp: use uma API key de workspace ou uma API key de conta (ps_account_…) para conectar um novo número", "code": "NUMBER_KEY_CANNOT_CREATE_NUMBER" }`.
- `403 NUMBERS_GRANT_NOT_ALLOWED` — per-number OAuth grants cannot provision numbers.
- `403 PERMISSION_DENIED` — OAuth token or account key of a user below Admin (`numbers:connect`).
- `409` — "Number already exists".
- `409 NUMBER_SOFT_DELETED` — `POST /v1/numbers` only: the phone was deleted in this workspace and is inside its 30-day window; the body carries `numberId` and `restorableUntil`. A number key never gets this answer: it is refused first with `403 NUMBER_KEY_CANNOT_CREATE_NUMBER`. See the DELETE section below.
- `502` — `POST /v1/numbers` only: `{ "error": "Failed to create instance", "details": "Upstream provider returned …" }`. Nothing is kept.

### Capacity errors and what fixes them

Both provisioning routes on this page (`POST /v1/numbers` and `POST /v1/numbers/meta`) check capacity **before** the number row is written, and both refuse with **`402`**. The status alone does not tell you what to do — the `error` field does. On these two routes the discriminator arrives in `error` **only**; `POST /v1/numbers/remote-pairing` sends the same values in both `error` and `code`.

| `error` | What it means | What fixes it |
| --- | --- | --- |
| `PLAN_NUMBER_LIMIT_REACHED` on the **Free plan** | The plan's own allowance is full. Free never buys an extra number by itself, so this is the answer whether or not you have credits or a saved card. | Free a slot (`DELETE /v1/numbers/{id}`), buy an extra number yourself ([it converts the account to On Demand and asks for confirmation](/api/extra-numbers#free-plan)) or move up a plan. **Money alone does not fix this one.** |
| `PLAN_NUMBER_LIMIT_REACHED` on a **paid plan** | The ceiling is your plan's own allowance, no extra number was ever bought or granted, and the next one cannot be funded. | Free a slot or move up a plan — or add credits or save a card: with funds the number is created, and the extra is charged at its [first connection](/api/extra-numbers#charged-at-the-first-connection). |
| `INSUFFICIENT_FUNDS` (paid plans only) | The next number is a **paid extra** — either a plan that bills per number, or an account that already bought extras — and it cannot be funded. | Add credits or save a card, then retry. |

The body carries the numbers behind the refusal, so you never have to guess:

```json
{
  "error": "PLAN_NUMBER_LIMIT_REACHED",
  "plan": "FREE",
  "maxNumbers": 1,
  "currentNumberCount": 1,
  "extras": 1,
  "proratedTotal": 14.95,
  "walletBalance": 0,
  "currency": "BRL"
}
```

<Note>
  **Changed.** A plan whose allowance was simply full used to answer `INSUFFICIENT_FUNDS` as well — so an account with one number on a one-number plan was told it had no money, and went looking for a balance that was never the problem. The status is unchanged (`402`); what is new is the value in `error`, and the fields alongside it.
</Note>

#### Webhook delivery (inbound)

Sending works the moment the number is created — it does not depend on the webhook. For Pilot Status to also **receive** inbound messages, Meta must deliver this WABA's webhooks to Pilot. The response carries a `webhook` object for exactly this:

```json
{
  "webhook": {
    "url": "https://webhook.pilotstatus.com.br/api/meta/webhook",
    "verifyToken": "…",
    "routedToPilot": false
  }
}
```

`webhook.verifyToken` is returned to every `ps_` key. Over an OAuth / MCP connection it is returned only after the reveal is recorded in the workspace's audit trail; if that record cannot be written, the number is still created, but `verifyToken` comes back `null` together with `secretWithheld: true`, `secretWithheldCode: "OAUTH_SECRET_AUDIT_UNAVAILABLE"` and a bilingual `secretWithheldReason`.

Two ways to wire it:

- **Automatic** — pass `routeWebhooksToPilot: true` in the request. Pilot subscribes the WABA for you and the response returns `webhook.routedToPilot: true`; nothing else to configure.
- **Manual** — in your Meta App Dashboard, set the WhatsApp product's **Callback URL** to `webhook.url` and the **Verify token** to `webhook.verifyToken`.

The hosted `metaFlow: "credentials"` connect page (see [remote pairing](/api/numbers/remote-pairing)) exposes the same choice as a checkbox.

## GET /v1/numbers/{id}/connect — Regenerate the QR code

Generates a **new QR code and pairing code** when the instance is not `OPEN`.

```bash
curl "https://pilotstatus.com.br/v1/numbers/wa_abc/connect" \
  -H "x-api-key: ps_your_token_here"
```

- Response includes fresh `qrcodeBase64` and `pairingCode`.
- If the number is already connected (`OPEN`), the endpoint returns **409** — there is nothing to pair.
- **Free plan:** when the plan's allowance is already full and this number never connected, the endpoint returns `402` with `{ "error": "PLAN_NUMBER_LIMIT_REACHED", "code": "PLAN_NUMBER_LIMIT_REACHED", "message": "…", "plan": "FREE", "maxNumbers": 1, "currentNumberCount": 1 }`, and no QR code is generated. `message` is a bilingual sentence, `English | Português`. Re-pairing a number that had already connected is never refused. See [Free plan](/api/extra-numbers#free-plan).
- Not applicable to **Meta** numbers (they do not use QR pairing): the endpoint answers `404` `{ "error": "Not found" }`, as it does for an unknown id.
- `502` `{ "error": "Failed to generate QR code", "code": "EMPTY_CONNECT_BUNDLE" }` when the provider returned neither a QR code nor a pairing code — retry.
- `{id}` may be the number id or the instance id. Over OAuth or with an account key it needs `numbers:connect` (Admin or Owner).
- Reflects the same connection state as the Numbers page in the dashboard.

## DELETE /v1/numbers/{id} — Remove a number

```bash
curl -X DELETE "https://pilotstatus.com.br/v1/numbers/wa_abc" \
  -H "x-api-key: ps_your_token_here"
```

```json
{ "ok": true, "restorableUntil": "2026-10-23T12:33:06.604Z" }
```

`{id}` may be the number id or the instance id. Unknown id: `404` `{ "error": "Number not found" }`.

This is a **30-day soft delete**, not a wipe:

* The paired device is **logged out right away** — the number stops sending and receiving.
* The number itself (id, API keys, webhooks, message history) is kept until `restorableUntil`, then destroyed for good by a background job.
* While it is in that window, creating the **same phone** again with `POST /v1/numbers` returns **`409 NUMBER_SOFT_DELETED`** (the body carries the old `numberId`). Restore it, or purge it first.

<Note>
  **Billing:** on Pay As You Go a deleted number is not charged on the next cycle — purged or not. On the other plans deleting does **not** reduce your paid capacity; to pay for fewer extra numbers, [schedule a reduction](/api/extra-numbers).
</Note>

## POST /v1/numbers/{id}/restore — Undo a delete

```bash
curl -X POST "https://pilotstatus.com.br/v1/numbers/wa_abc/restore" \
  -H "x-api-key: ps_your_tenant_scoped_key"
```

```json
{ "ok": true, "requiresReconnect": true }
```

Brings the number back within its 30-day window, with the same id, API keys, webhooks and history. It restores the **record, not the connection** — the device was logged out on delete, so reconnect it afterwards with `GET /v1/numbers/{id}/connect` (or re-provision a Meta number). A successful restore emits `number.restored` to the number's webhooks.

* **`404`** with `code: RESTORE_WINDOW_EXPIRED` once the 30 days are over.
* **`409 NUMBER_ALREADY_ACTIVE`** when the same phone was reconnected in the meantime — use the active number.
* **Restoring a number that had already connected can charge.** Such a number goes back into your number count. If that takes the workspace past the capacity it has paid for, one extra number is charged at the restore, prorated for the rest of the cycle. When that cannot be paid, you get **`422 INSUFFICIENT_FUNDS`** (or `PLAN_NUMBER_LIMIT_REACHED`) with `proratedTotal` and `walletBalance`, nothing is charged, and the number stays deleted. Retrying the same restore never charges twice.
* **A number that never connected costs nothing to restore.** It does not count yet, and it is charged at its [first connection](/api/extra-numbers#charged-at-the-first-connection), like any other.

## DELETE /v1/numbers/{id}/purge — Delete permanently

```bash
curl -X DELETE "https://pilotstatus.com.br/v1/numbers/wa_abc/purge" \
  -H "x-api-key: ps_your_tenant_scoped_key"
```

```json
{ "ok": true }
```

<Warning>
  **Irreversible.** Purging destroys the number immediately, with everything under it — message history, chats, templates, the number's webhooks and API keys — and deregisters a Meta number at Meta. There is no restore after it.
</Warning>

* Works on a number already deleted with `DELETE /v1/numbers/{id}` — the usual flow is delete, then purge — or on an active one.
* Use it when the **same phone** has to be created again right away (the `409 NUMBER_SOFT_DELETED` case).
* It saves nothing on the bill compared to `DELETE`.
* Call it with a **tenant-scoped key**. A key bound to the deleted number stops authenticating as soon as the number is deleted.
* With an OAuth / MCP token, only the workspace **OWNER** may purge (`403 PERMISSION_DENIED` otherwise).

## Related webhooks

- `number.created` — fires when the instance is created.
- `number.connected` — fires when the customer completes the QR / pairing connection (state `OPEN`).
- `number.removed` — fires on deletion.
- `number.restored` — fires when a deleted number is restored within its 30-day window (this route or the dashboard). The number comes back disconnected.

See the [webhook event reference](/api/webhooks/events).
