Twelve endpoints under `/v1/workspace` mirror what the dashboard does with the workspace itself (name, settings, ownership, archive) and with members and invitations. Members are unlimited on every plan.

## Which credential works where

This is the part to read before anything else.

| Endpoint | Workspace key (`x-api-key`) ¹ | Account key (`ps_account_`) | OAuth token |
|---|:---:|:---:|:---:|
| `GET /v1/workspace` | ✅ | ✅ | ✅ |
| `PATCH /v1/workspace` | ✅ | ✅ ² | ✅ ² |
| `GET /v1/workspace/settings` | ✅ | ✅ | ✅ |
| `PATCH /v1/workspace/settings` | ✅ | ✅ ² | ✅ ² |
| `POST /v1/workspace/transfer-ownership` | ❌ | ✅ ³ | ✅ ³ |
| `POST /v1/workspace/archive` | ❌ | ✅ ³ | ✅ ³ |
| `GET /v1/workspace/members` | ✅ | ✅ ² | ✅ ² |
| `POST /v1/workspace/members` | ❌ | ✅ ² | ✅ ² |
| `POST /v1/workspace/members/{id}/resend` | ❌ | ✅ ² | ✅ ² |
| `PATCH /v1/workspace/members/{id}` | ❌ | ✅ ³ | ✅ ³ |
| `PATCH /v1/workspace/members/{id}/numbers` | ❌ | ✅ ² | ✅ ² |
| `DELETE /v1/workspace/members/{id}` | ❌ | ✅ ³ | ✅ ³ |

¹ **Number keys never pass here.** Everything on this page belongs to the whole account, so a number-scoped key gets `403 NUMBER_SCOPE_NOT_ALLOWED` on every endpoint above — on the writes marked ❌ it gets the machine-credential `403` described below first. The same `403 NUMBER_SCOPE_NOT_ALLOWED` goes to an OAuth token consented for specific numbers only, and to an account key whose user is restricted to some numbers. A workspace key narrowed with `x-whatsapp-number-id` still passes.
² The user must be `ADMIN` or `OWNER`; below that, `403 PERMISSION_DENIED`.
³ The user must be the `OWNER`; anyone else gets `403 PERMISSION_DENIED`.

<Warning>
**Writes require a user on the wire, on purpose.** A workspace or number key has no user behind it — the key belongs to the workspace, not to a person. If inviting were allowed with a tenant-scoped key, then whoever holds *any* key of the workspace could invite themselves an Admin, and the key would become a path to taking over the account. Such a key gets **403 `MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`** on the member writes.
</Warning>

An OAuth token and an [account key](/api/key-types#account-keys) (with `x-workspace-id`) both carry a user, and act with that user's **current role** in the workspace, re-read on every request: the same rules as in the dashboard apply.

Transferring ownership and archiving are the two actions that change who pays the bill or lock everyone out, so they take the **OWNER on the wire**: an OAuth/MCP token or an account key whose user is the owner. **No machine credential reaches them** — any workspace or number `ps_` key gets **403 `MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`**.

Successful responses carry `Cache-Control: no-store`. A user who is no longer an active member gets `401 OAUTH_MEMBERSHIP_REVOKED` behind an OAuth token (sign in again) and `403 WORKSPACE_MEMBERSHIP_REQUIRED` behind an account key. Errors carry an `error` message and a stable `code` — branch on `code`. Most messages are bilingual (`English | Português`); the member-management conflicts (`ALREADY_MEMBER`, `NOT_FOUND`, `OWNER_IMMUTABLE`, …), `RATE_LIMITED` and the role refusals currently come in a single language. A body that is not a JSON object is `400 INVALID_BODY`, and on the workspace, settings, archive and transfer endpoints a key the endpoint does not accept is `400 UNKNOWN_FIELDS` with the offending keys in `unknownFields`.

## Read the workspace

```bash
curl https://pilotstatus.com.br/v1/workspace \
  -H "x-api-key: ps_..."
```

```json
{
  "id": "tn_...",
  "name": "Acme",
  "plan": "PREMIUM",
  "seatsUsed": 4,
  "seatLimit": null
}
```

`seatLimit` is always `null`: members are **unlimited on every plan**. The field stays in the response for compatibility with existing integrations and SDKs.

`seatsUsed` is **informational only** — it counts active members and pending invitations that have not expired, and never blocks anything.

## Rename the workspace

```bash
curl -X PATCH https://pilotstatus.com.br/v1/workspace \
  -H "x-api-key: ps_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"Acme Holdings"}'
```

```json
{ "id": "tn_...", "name": "Acme Holdings" }
```

`name` is trimmed and must be **1 to 60 characters**, otherwise `400 INVALID_NAME`. The name is a label: it does not need to be unique, and the workspace `id` never changes. Works with a tenant-scoped key, or with a user who is `ADMIN` or `OWNER`. MCP tool: `workspace_update`.

## Workspace settings

### Read

```bash
curl https://pilotstatus.com.br/v1/workspace/settings \
  -H "x-api-key: ps_..."
```

```json
{
  "settings": {
    "mainCurrency": "BRL",
    "mainTimezone": "America/Sao_Paulo",
    "mainLanguage": "pt",
    "billingMode": "SUBSCRIPTION",
    "currencyLocked": false
  },
  "phoneLinePrice": { "currency": "BRL", "price": 49.9 }
}
```

| Field | Meaning |
|---|---|
| `mainCurrency` | The currency the whole account is charged in |
| `mainTimezone` | IANA time zone of the workspace |
| `mainLanguage` | `pt`, `en` or `es` |
| `billingMode` | `SUBSCRIPTION` or `WALLET`. Set by the platform |
| `currencyLocked` | `true` once the wallet has had its first movement — from then on the currency can no longer change |
| `phoneLinePrice` | What one **new** phone line costs this workspace per month, in its currency |

Any role reads it, `ANALYST` included, as does a tenant-scoped key. MCP tool: `workspace_settings_get`.

### Update

```bash
curl -X PATCH https://pilotstatus.com.br/v1/workspace/settings \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"mainTimezone":"America/Manaus","mainLanguage":"en"}'
```

A partial update that accepts **only** `mainTimezone` and `mainLanguage` — send at least one. The response is `{ "settings": { ... } }`, in the same shape as the read. Same credentials as renaming: a tenant-scoped key, or a user who is `ADMIN` or `OWNER`. MCP tool: `workspace_settings_update`.

Unlike the dashboard, an invalid value is never skipped silently:

| Status | `code` | What happened |
|---|---|---|
| `400` | `NO_FIELDS` | Neither `mainTimezone` nor `mainLanguage` was sent |
| `400` | `INVALID_TIMEZONE` | `mainTimezone` is not an IANA zone; `field` names it |
| `400` | `INVALID_LANGUAGE` | `mainLanguage` is not `pt`, `en` or `es`; `field` names it and `accepted` lists the values |
| `400` | `CURRENCY_NOT_HERE` | `mainCurrency` was sent. The **owner** changes the currency in the dashboard's billing settings, and it locks after the wallet's first movement |
| `400` | `BILLING_MODE_NOT_HERE` | `billingMode` was sent. It is set by the platform |
| `400` | `UNKNOWN_FIELDS` | Any other key; `unknownFields` names them |

Nothing is written when any of these is returned.

## List members

```bash
curl https://pilotstatus.com.br/v1/workspace/members \
  -H "x-api-key: ps_..."
```

Returns active members and invitations in one list, distinguished by `status`. A workspace key reads it; a user needs `ADMIN` or `OWNER`. The envelope also carries the same informational `seatsUsed` and `seatLimit: null`:

```json
{
  "members": [
    {
      "id": "mb_...",
      "email": "someone@acme.com",
      "name": "Someone",
      "role": "AGENT",
      "status": "ACTIVE",
      "allowedNumberIds": [],
      "invitedAt": "2026-08-01T12:00:00.000Z",
      "joinedAt": "2026-08-01T12:30:00.000Z",
      "inviteExpiresAt": null,
      "inviteExpired": false,
      "inviteEmailSentAt": "2026-08-01T12:00:04.000Z",
      "inviteEmailStatus": null
    }
  ],
  "seatsUsed": 4,
  "seatLimit": null
}
```

| Field | Meaning |
|---|---|
| `id` | Membership id — the `{id}` the other member endpoints take. **Not** the user id |
| `status` | `ACTIVE`, `PENDING` (invited, not accepted yet) or `DECLINED` |
| `allowedNumberIds` | Numbers an `AGENT`/`ANALYST` is limited to. `[]` = all numbers (always `[]` for `OWNER` and `ADMIN`) |
| `inviteExpired` | `true` when a pending invitation is past `inviteExpiresAt` |
| `inviteEmailStatus` | For a pending invitation: `SENT`, `QUEUED` (less than 5 minutes old) or `NOT_SENT`. `null` for anyone who is not pending |

<Warning>
The list **never contains an invitation link or token**, and it never will: only a hash of the token is stored, so the link is not derivable after the fact. If you need a link for a pending invitation, call `resend`.
</Warning>

## Invite

```bash
curl -X POST https://pilotstatus.com.br/v1/workspace/members \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"email":"someone@acme.com","role":"AGENT","sendEmail":true}'
```

| Field | Meaning |
|---|---|
| `email` | Trimmed and normalized to lowercase. One invitation per address per workspace |
| `role` | Optional, default `AGENT`. An `OWNER` can assign `ADMIN`, `AGENT` or `ANALYST`; an `ADMIN` only `AGENT` or `ANALYST`. **`OWNER` is never assignable** |
| `allowedNumberIds` | Optional. Limits an Agent or Analyst to specific numbers; ignored for Admins |
| `sendEmail` | Default `true`. With `false` (the JSON boolean), no e-mail is sent and the response carries `inviteUrl` |

A role the caller cannot assign — `OWNER` included, or `ADMIN` when the caller is an Admin — is **`403 ROLE_NOT_ASSIGNABLE`**, with the roles you may assign in `assignableRoles`.

```json Response (201)
{
  "member": { "id": "mb_...", "email": "someone@acme.com", "role": "AGENT", "status": "PENDING", ... },
  "resent": false,
  "emailSent": false,
  "inviteUrl": "https://pilotstatus.com.br/invite/..."
}
```

`sendEmail: false` is the hatch for delivering the invitation your own way. **The response is the only place the link appears** — if you lose it, call `resend`, which issues a new one and kills the old. With `sendEmail: true`, `inviteUrl` is not in the response.

Inviting an address that already has a pending (or declined) invitation is not an error: it rotates the token in place and returns `200` with `"resent": true` instead of `201`. An e-mail delivery failure never fails the call: the invitation is already saved.

**Rate limits.** Invitations — with or without e-mail — are limited to **30 per hour per workspace** (shared with `resend`), **3 per hour per recipient address** and **60 per hour per IP**. Over a limit: `429` with `code: "RATE_LIMITED"`, `retryAfterSeconds` and a `Retry-After` header. Nothing is written.

If invitations are turned off for the account, invite and resend answer `403 FEATURE_DISABLED`; listing, changing and removing members keep working.

## Resend an invitation

```bash
curl -X POST https://pilotstatus.com.br/v1/workspace/members/mb_.../resend \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"sendEmail":false}'
```

Issues a new invitation link for a pending invitation — the previous link dies on the spot — and, unless `sendEmail` is `false`, e-mails it again. The body is optional (`sendEmail` defaults to `true`). `ADMIN` or `OWNER`.

```json
{ "member": { "id": "mb_...", "status": "PENDING", ... }, "emailSent": false, "inviteUrl": "https://pilotstatus.com.br/invite/..." }
```

`inviteUrl` comes only with `sendEmail: false`. Only a resend that sends an e-mail is rate limited: it counts against the workspace and IP limits of the invite and against **3 resends per hour per invitation** (`429 RATE_LIMITED`). An id not in this workspace is `404 NOT_FOUND`; a member who already accepted is `409 ALREADY_MEMBER`.

## Change a member's role

```bash
curl -X PATCH https://pilotstatus.com.br/v1/workspace/members/mb_... \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"role":"ANALYST"}'
```

Changing the role is **OWNER only** and always needs `role` (`ADMIN`, `AGENT` or `ANALYST`); a missing role, or `OWNER`, is `400 ROLE_NOT_ASSIGNABLE` with `assignableRoles`. The optional `allowedNumberIds` sets the number scope in the same call; **omitted, the current scope is kept**. Promoting to `ADMIN` clears the number scope, because Admins are workspace-wide. The member's OAuth refresh tokens are revoked. The response is `{ "member": { ... } }`. The owner's own role cannot change here (`409 OWNER_IMMUTABLE`) — use [Transfer ownership](#transfer-ownership).

To change **only the numbers** an Agent or Analyst sees, without touching the role, use `PATCH /v1/workspace/members/{id}/numbers` below — Admins can call that one too.

## Change which numbers a member sees

```bash
curl -X PATCH https://pilotstatus.com.br/v1/workspace/members/mb_.../numbers \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"allowedNumberIds":["wa_...","wa_..."]}'
```

Sets which WhatsApp numbers of the workspace an `AGENT` or `ANALYST` sees and acts on. The role does not change. Works on pending invitations too.

| Field | Meaning |
|---|---|
| `allowedNumberIds` | **Required.** Array of number ids. **Replaces the whole list** — send every id the member should keep |

<Warning>
**`[]` means ALL numbers, not none** — including numbers connected later. A member restricted to specific numbers does **not** gain new numbers automatically: when you connect a number, add it here for each restricted member who needs it.
</Warning>

- **Who can call it:** an OAuth/MCP token or an account key whose user is `ADMIN` or `OWNER` of the workspace. A workspace or number `ps_` key gets `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`; an `AGENT` or `ANALYST` gets `403 PERMISSION_DENIED`.
- **It cuts immediately:** the member's OAuth refresh tokens are revoked, so a narrower scope applies on their next call instead of surviving in a token consented to with the wider reach. Their MCP connectors may need to sign in again.
- **Owners and Admins always see every number**, so the call refuses them with `409 SCOPE_NOT_APPLICABLE`.

The response is the updated member, in the same shape the list returns:

```json
{
  "member": {
    "id": "mb_...",
    "role": "AGENT",
    "status": "ACTIVE",
    "allowedNumberIds": ["wa_...", "wa_..."],
    ...
  }
}
```

| Status | `code` | What happened |
|---|---|---|
| `400` | `INVALID_SCOPE` | `allowedNumberIds` is missing or is not an array of strings |
| `400` | `UNKNOWN_FIELDS` | The body has any other key (`role` included); `details.unknownFields` names them |
| `403` | `MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS` | Called with a workspace or number `ps_` key |
| `403` | `PERMISSION_DENIED` | The caller is `AGENT` or `ANALYST` |
| `401` | `OAUTH_MEMBERSHIP_REVOKED` | OAuth token whose user is no longer an active member of the workspace — sign in again |
| `403` | `WORKSPACE_MEMBERSHIP_REQUIRED` | Account key whose user is no longer an active member of the workspace |
| `404` | `NOT_FOUND` | That membership id is not in this workspace |
| `409` | `SCOPE_NOT_APPLICABLE` | The target is `OWNER` or `ADMIN` |

## Remove a member or revoke an invitation

```bash
curl -X DELETE https://pilotstatus.com.br/v1/workspace/members/mb_... \
  -H "Authorization: Bearer <oauth-token>"
```

One call for both: an invitation and a membership are the same row. **OWNER only.** The owner cannot be removed (`409 OWNER_IMMUTABLE`).

```json
{ "removed": true, "email": "someone@acme.com", "apiKeysRevoked": 0, "apiKeysReassigned": 0, "oauthTokensRevoked": 1 }
```

The removed user's OAuth refresh tokens are revoked (`oauthTokensRevoked`).

## Errors worth handling

| Status | `code` | What happened |
|---|---|---|
| `400` | `INVALID_BODY` | The body of an invite, role change, scope change, removal or resend is not valid JSON — nothing is changed and no email is sent ([Malformed JSON body](/api/overview#malformed-json-body)) |
| `400` | `INVALID_EMAIL` | The address is not plausible |
| `400` | `ROLE_NOT_ASSIGNABLE` | Role change: `role` missing, unknown or `OWNER`. `assignableRoles` lists the valid ones |
| `403` | `ROLE_NOT_ASSIGNABLE` | Invite: your role cannot assign that role. `assignableRoles` lists the ones you can |
| `403` | `FEATURE_DISABLED` | Invitations are turned off for the account (invite and resend only) |
| `404` | `NOT_FOUND` | That membership id is not in this workspace |
| `409` | `ALREADY_MEMBER` | That address is already an active member (or, on resend, the invitation was already accepted) |
| `409` | `OWNER_IMMUTABLE` | The target is the owner — change or removal refused |
| `409` | `MEMBER_HAS_API_KEYS` | See below |
| `409` | `WOULD_ORPHAN_WORKSPACE` | The change would leave the workspace without an owner |
| `429` | `RATE_LIMITED` | Invite or resend over a limit. `retryAfterSeconds` and `Retry-After` say when to retry |

## Removing a member who created API keys

`DELETE` refuses with `409 MEMBER_HAS_API_KEYS` and lists the keys:

```json
{
  "error": "O membro criou 1 chave(s) de API ainda ativa(s).",
  "code": "MEMBER_HAS_API_KEYS",
  "apiKeys": [
    { "id": "key_...", "name": "n8n", "keyLast4": "9f21", "whatsappNumberId": null, "lastUsedAt": "2026-08-01T12:00:00.000Z" }
  ],
  "hint": "Repeat with apiKeyAction=\"revoke\" or apiKeyAction=\"keep\"."
}
```

Repeat the call with an explicit decision, in the query string or as `{"apiKeyAction":"keep"}` in the body (the query wins when both are sent):

```bash
curl -X DELETE "https://pilotstatus.com.br/v1/workspace/members/mb_...?apiKeyAction=keep" \
  -H "Authorization: Bearer <oauth-token>"
```

- `revoke` — the keys stop authenticating. Integrations through them break immediately.
- `keep` — the keys keep working and are reassigned to the caller.

There is no default. An integrator must not take down production integrations by omission.

Revoking is never a delete: the record survives so message and call history keeps pointing somewhere real.

## Transfer ownership

```bash
curl -X POST https://pilotstatus.com.br/v1/workspace/transfer-ownership \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"email":"new-owner@acme.com"}'
```

```json
{ "transferred": true, "newOwnerId": "usr_...", "yourNewRole": "ADMIN" }
```

Makes an active member the new **owner**. `email` is matched against the members' e-mails without regard to case. The target must have **accepted** the invitation — a pending invitation does not qualify.

<Warning>
**What changes the moment it returns:**

- **You become `ADMIN`** (`yourNewRole`). Everything only the owner could do — moving money, archiving, transferring again — is now the new owner's.
- **The OAuth refresh tokens of both users are revoked.** An MCP connection keeps working with each user's **new** role (applied on the next request) until its access token expires, then has to consent again.
- **Responsibility for the bill moves to the new owner.**
</Warning>

Only the **owner** can call it, with an OAuth/MCP token or an account key. A workspace or number `ps_` key gets `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`; anyone else, `403 PERMISSION_DENIED`. MCP tool: `workspace_transfer_ownership`, with a preview and a confirmation token ([MCP server](/integrations/mcp-server)).

| Status | `code` | What happened |
|---|---|---|
| `400` | `MISSING_EMAIL` | `email` is missing or blank |
| `400` | `NOT_A_MEMBER` | No member of this workspace has that e-mail |
| `400` | `TARGET_NOT_ACTIVE` | The person has not accepted the invitation yet |
| `409` | `ALREADY_OWNER` | The person is already the owner |
| `409` | `NOT_OWNER` | The caller is no longer the owner |
| `409` | `NO_OWNER` | The workspace has no owner |
| `409` | `OWNERSHIP_CHANGED` | Ownership changed during the call. Re-read the members and try again |
| `409` | `WOULD_ORPHAN_WORKSPACE` | The change would leave the workspace without an owner |

## Archive the workspace

<Warning>
**Archiving locks everyone out — you included, and the call that does it.** The token you used stops working on its very next request, every `ps_` key of the workspace stops authenticating, and embedded chat sessions are revoked. **There is no unarchive endpoint:** reverting it requires contacting support.
</Warning>

```bash
curl -X POST https://pilotstatus.com.br/v1/workspace/archive \
  -H "Authorization: Bearer <oauth-token>" \
  -H "Content-Type: application/json" \
  -d '{"confirmName":"Acme Holdings"}'
```

```json
{ "archived": true, "archivedAt": "2026-11-08T12:00:00.000Z" }
```

`confirmName` must be the workspace's current name, **exactly** — trimmed, and case-sensitive. Read it with `GET /v1/workspace`. A wrong or missing name is `400 CONFIRMATION_MISMATCH` with `field: "confirmName"`, and the response never echoes the real name.

Only the **owner** can call it, with an OAuth/MCP token or an account key. A workspace or number `ps_` key gets `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE`; anyone else, `403 PERMISSION_DENIED`. MCP tool: `workspace_archive`, with a preview and a confirmation token ([MCP server](/integrations/mcp-server)).

| Status | `code` | What happened |
|---|---|---|
| `400` | `CONFIRMATION_MISMATCH` | `confirmName` is missing or does not match the name |
| `404` | `NOT_FOUND` | The workspace no longer exists |
| `409` | `ALREADY_ARCHIVED` | The workspace is already archived |
