Pilot Status ofrece un servidor oficial de **Model Context Protocol (MCP)** que expone la API pública `/v1` como herramientas MCP. Los agentes de IA y los clientes LLM pueden usarlo para enviar mensajes, consultar conversaciones y administrar números, plantillas, webhooks, grupos y llamadas de voz, directamente desde el contexto del modelo.

## Conector alojado

El servidor usa el transporte **streamable HTTP** y funciona como conector alojado en:

```text
https://mcp.pilotstatus.com.br/mcp
```

Agrégalo como **Custom Connector** en claude.ai (Settings → Connectors → Add custom connector). claude.ai ejecuta el inicio de sesión OAuth 2.1 (SSO de Pilot Status): no se comparte ninguna API key con el cliente. Durante el paso de consentimiento apruebas el acceso para **todo el tenant** u otorgas solo **números específicos**; una concesión por número restringe todas las herramientas a esos números. Solo el **Owner** del workspace o un **Admin** puede otorgar todo el tenant: para un Agent o Analyst, la pantalla de consentimiento muestra esa opción deshabilitada y explica por qué. Consulta [Secretos y API keys por OAuth](#secretos-y-api-keys-por-oauth) para saber qué puede hacer la app con claves y secretos.

Cualquier cliente MCP que admita conectores OAuth personalizados puede conectarse de la misma forma. Los clientes configurados por archivo pueden, en cambio, enviar una clave `ps_*` en el encabezado `x-api-key`:

```json
{
  "mcpServers": {
    "pilot-status": {
      "type": "http",
      "url": "https://mcp.pilotstatus.com.br/mcp",
      "headers": { "x-api-key": "ps_your_key_here" }
    }
  }
}
```

<Tip>
Empieza aquí: `/mcp` es el predeterminado, y tu cliente muestra cada llamada para que la apruebes. Para agentes que generan informes, recorren muchos elementos o funcionan con un contexto ajustado, usa **`https://mcp.pilotstatus.com.br/code`** en lugar de `/mcp` (no junto con él): el agente recibe 2 herramientas (`describe` y `execute`) en vez de 151 y escribe un script en TypeScript que llama a `await ps.<tool>(args)`. Mismas credenciales. [MCP Code Mode](/es/integrations/mcp-code-mode)
</Tip>

## Conecta tu cliente

Dos formas de entrar, sea cual sea el cliente: **OAuth** (el cliente abre una página de inicio de sesión y consentimiento de Pilot Status; no se copia ninguna clave a ningún lado) o una **API key** en el encabezado `x-api-key`. Usa `/code` en lugar de `/mcp` en cualquier URL de abajo para obtener [Code Mode](/es/integrations/mcp-code-mode).

| Cliente | Cómo |
| --- | --- |
| **claude.ai** y **Claude Desktop** | Settings → Connectors → **Add custom connector**, URL `https://mcp.pilotstatus.com.br/mcp`, sin client id ni secret. Conéctate, inicia sesión en Pilot Status y elige el acceso en la pantalla de consentimiento. Los conectores agregados en claude.ai también aparecen en Claude Desktop. |
| **Claude Code** | OAuth: `claude mcp add --transport http pilot-status https://mcp.pilotstatus.com.br/mcp`, luego ejecuta `/mcp` en Claude Code y elige **Authenticate**. API key: agrega `--header "x-api-key: ps_your_key_here"` al mismo comando. |
| **ChatGPT** | Donde tu plan permita conectores personalizados (modo desarrollador), crea un conector con la URL `https://mcp.pilotstatus.com.br/mcp` y autenticación **OAuth**. ChatGPT se registra por sí mismo, así que deja vacíos el client id y el secret. |
| **Cursor** | API key en `~/.cursor/mcp.json` (o `.cursor/mcp.json` en el proyecto): `{ "mcpServers": { "pilot-status": { "url": "https://mcp.pilotstatus.com.br/mcp", "headers": { "x-api-key": "ps_your_key_here" } } } }`. O OAuth: omite `headers` (`{ "mcpServers": { "pilot-status": { "url": "https://mcp.pilotstatus.com.br/mcp" } } }`) y luego haz clic en **Connect** junto al servidor en **Settings → MCP**; Cursor abre la página de inicio de sesión y consentimiento de Pilot Status y vuelve por su callback `cursor://`. |
| **VS Code** (modo agente de Copilot) | API key en `.vscode/mcp.json`: `{ "servers": { "pilot-status": { "type": "http", "url": "https://mcp.pilotstatus.com.br/mcp", "headers": { "x-api-key": "ps_your_key_here" } } } }`. |
| **Cualquier otro cliente MCP** | Streamable HTTP en la URL de arriba. Un cliente que admita OAuth con registro dinámico de clientes se conecta sin configuración (callbacks: `https://`, `http://` en loopback o un esquema de app nativa; ver abajo); de lo contrario, envía `x-api-key`. |

Qué clave enviar en `x-api-key`: una **clave de número** (`ps_number_…`) actúa sobre un número; una **clave de workspace** (`ps_workspace_…`) actúa sobre todo el workspace, así que pasa `whatsappNumberId` a las herramientas con alcance de número; una **clave de cuenta** (`ps_account_…`) también necesita `x-workspace-id` ([abajo](#con-una-clave-de-cuenta)). [Tipos de API key](/es/concepts/key-types)

### Qué hace el inicio de sesión OAuth

- **Qué workspace.** La conexión actúa sobre un workspace: la pantalla de consentimiento muestra su nombre arriba ("Access will be bound to this workspace"). Si perteneces a más de uno, cambia de workspace ahí mismo antes de autorizar. Si el workspace cambia en otra pestaña antes de que hagas clic en **Authorize**, la autorización se rechaza y la pantalla te pide recargar, así el token nunca queda vinculado a un workspace que no viste. Para dos workspaces, agrega dos conexiones.
- **Qué puede alcanzar.** En la pantalla de consentimiento eliges **Entire account** (solo Owner o Admin del workspace) o **números específicos** (cualquier rol, limitado a los números a los que tú mismo tienes acceso). Una concesión por número restringe todas las herramientas a esos números y bloquea las herramientas a nivel de cuenta como `billing_checkout`, `api_keys_*` y `numbers_create`. El consentimiento se pide en **cada** autorización, incluso con una sesión activa.
- **Tu rol sigue aplicándose.** El token nunca hace más de lo que permite tu rol en el workspace, y las herramientas exclusivas del dueño vuelven a verificar el rol en cada llamada.
- **Duración de la sesión.** El token de acceso dura 1 hora y el cliente lo renueva por su cuenta; el refresh token dura 30 días y se reemplaza en cada uso. Tras 30 días sin uso, o después de una transferencia de propiedad, conéctate de nuevo. El token de acceso no es una foto fija: cada solicitud vuelve a verificar tu membresía **actual** (en caché por un máximo de 30 segundos). Un cambio de rol o de números se aplica en la siguiente llamada a una herramienta, y la eliminación del workspace termina la conexión de inmediato (`401`, el cliente te pide conectarte de nuevo).
- **Revocar.** Quita el conector en tu cliente. Las claves y secretos que la app ya obtuvo siguen siendo válidos: consulta [Secretos y API keys por OAuth](#secretos-y-api-keys-por-oauth).

Para desarrolladores de clientes: el servidor MCP publica `/.well-known/oauth-protected-resource` (RFC 9728) y responde a una solicitud no autenticada con `401` y un desafío `WWW-Authenticate`. Cuando la API rechaza el token OAuth de una solicitud (vencido, revocado), toda la respuesta es `401` con `WWW-Authenticate: Bearer error="invalid_token", …, resource_metadata="…"`, para que el cliente renueve el token o vuelva a iniciar sesión; con una API key, el rechazo sigue siendo un error de herramienta. El servidor de autorización, `https://pilotstatus.com.br`, publica `/.well-known/oauth-authorization-server`: registro dinámico de clientes en `/api/oauth/register` (clientes públicos, `token_endpoint_auth_method: none`), authorization code solo con **PKCE S256**, y refresh tokens. Las URI de redirección pueden ser `https://`; `http://` en un host de loopback (`localhost`, `127.0.0.1`, `[::1]`, cualquier puerto); o, para apps nativas (RFC 8252), un esquema de uso privado en DNS inverso (`com.example.app:/callback`) o uno de `cursor`, `vscode`, `vscode-insiders`, `windsurf`. Los esquemas como `javascript:`, `data:` y `file:`, los fragmentos y las credenciales de usuario se rechazan. PKCE sigue siendo obligatorio para todos los clientes. El transporte no tiene estado: el JSON-RPC va en un `POST`; `GET` y `DELETE` responden `405`.

## Autenticación

| Método | Cómo |
| --- | --- |
| OAuth 2.1 | `Authorization: Bearer <token>`, gestionado por el cliente tras el inicio de sesión ([Conecta tu cliente](#conecta-tu-cliente)) |
| API key | Encabezado `x-api-key` con una clave `ps_*` |
| Clave de cuenta | Encabezado `x-api-key` con una clave `ps_account_*`, más `x-workspace-id` con el workspace sobre el que actuar |

Todas las herramientas excepto `docs_search` aceptan un argumento adicional, **`whatsappNumberId`**: el número sobre el que actuar, obtenido de `numbers_list`. Con un token OAuth o una clave de workspace, las herramientas con alcance de número (mensajes, conversaciones, grupos, plantillas, webhooks, llamadas, Chatwoot…) **lo necesitan**: el servidor lo envía a la API como el encabezado `x-whatsapp-number-id`. Con una clave de número se ignora: la clave ya indica su número. Las herramientas a nivel de cuenta (`api_keys_list`, `billing_checkout`, `branding_*`, `workspace_*`, líneas telefónicas…) necesitan un token OAuth o una clave de workspace; una clave de número recibe `403`.

### Con una clave de cuenta

Una [clave de cuenta](/es/concepts/key-types#claves-de-cuenta) (`ps_account_…`, creada en **Profile → API**) pertenece a un usuario y alcanza todos los workspaces de los que es miembro activo, así que la conexión debe indicar sobre cuál actuar: agrega un encabezado `x-workspace-id` con un id de workspace de `workspaces_list`. El servidor lo reenvía en cada llamada, en `/mcp` y en [`/code`](/es/integrations/mcp-code-mode). Dentro de ese workspace, la clave actúa con el rol actual del usuario.

```json
{
  "mcpServers": {
    "pilot-status": {
      "type": "http",
      "url": "https://mcp.pilotstatus.com.br/mcp",
      "headers": { "x-api-key": "ps_account_your_key_here", "x-workspace-id": "your_workspace_id" }
    }
  }
}
```

- **Sin `x-workspace-id`**, solo funcionan las herramientas `workspaces_*` y `docs_search` (`docs_search` no llama a ningún endpoint `/v1`, así que no necesita workspace). Cualquier otra herramienta responde `WORKSPACE_ID_REQUIRED` sin llamar a la API, con un mensaje que explica dónde configurar el id.
- **Para cambiar de workspace**, cambia el encabezado y vuelve a conectarte, o configura una conexión por workspace. La propia clave `ps_workspace_` de un workspace no necesita el encabezado.
- Con un token OAuth el encabezado se ignora: el token ya indica su workspace.

## Autoalojado

El servidor se publica como `@pilot-status/mcp-server` en npm (comando `pilot-status-mcp`, Node.js 20 o posterior). Usa **solo streamable HTTP** (no hay modo stdio) y escucha en `http://localhost:8787/mcp` (`PORT` y `HOST` lo cambian):

```bash
PILOT_STATUS_API_KEY=ps_your_key_here npx -y @pilot-status/mcp-server
```

Luego apunta tu cliente a la URL local, como en [Conecta tu cliente](#conecta-tu-cliente):

```json
{
  "mcpServers": {
    "pilot-status": { "type": "http", "url": "http://localhost:8787/mcp" }
  }
}
```

La clave puede venir del proceso (`PILOT_STATUS_API_KEY`) o del encabezado `x-api-key` de cada solicitud, que tiene prioridad sobre la variable. Llama a `https://pilotstatus.com.br` (`PILOT_STATUS_API_URL` lo cambia) y ofrece las mismas 151 herramientas que el conector alojado; Code Mode (`/code`) no está disponible en la versión autoalojada. Un servidor autoalojado también lee `PILOT_STATUS_API_KEY` de su entorno y, para una clave de cuenta, `PILOT_STATUS_WORKSPACE_ID`. Esa variable se aplica solo a la clave definida en `PILOT_STATUS_API_KEY`, nunca a una clave que una conexión envía en su propio encabezado `x-api-key`: con esa, envía `x-workspace-id`.

Notas:

- `templates_create`/`templates_update` requieren el objeto `examples` (una muestra real por variable; si falta → `400 TEMPLATE_EXAMPLES_REQUIRED`) y aceptan encabezados multimedia **solo por URL**: el base64 es exclusivo de REST.
- `templates_insights` (solo lectura) devuelve las analíticas de Meta de una plantilla mediante `GET /v1/templates/{id}/insights`: argumentos `id` y `days` opcional (`7`, `30` o `90`; por defecto `30`). Devuelve los `totals` de enviados/entregados/leídos, `readRate` (`null` cuando no se entregó nada), los `clicks` en botones y una serie `daily`, además del nombre, estado, categoría, idioma y `qualityScore` de la plantilla. Solo las plantillas de Meta tienen insights: una plantilla que no es de Meta falla con `409 TEMPLATE_NOT_ON_META`, y las cuentas de WhatsApp Business App / coexistence fallan con `422 TEMPLATE_INSIGHTS_UNAVAILABLE_SMB` (Meta no ofrece insights allí; no reintentes). La primera llamada puede activar los insights de plantillas en la WABA en Meta. Requiere una API key con alcance de número.
- `templates_update` devuelve `409 TEMPLATE_NOT_EDITABLE` cuando Meta no permite editar la plantilla en su estado actual (solo se pueden editar las plantillas rechazadas); la plantilla guardada no cambia. Crea una plantilla nueva con el cambio, o envía el documento al momento del envío. [Editar](/es/api/templates#editar)
- `templates_submit` envía una plantilla a Meta para su aprobación (`POST /v1/templates/{id}/submit`, argumento `id`) y `templates_sync` trae el catálogo de la WABA desde Meta (`POST /v1/templates/sync`, sin argumentos, devuelve `{ created, updated }`; `429 TEMPLATE_SYNC_IN_PROGRESS` mientras se ejecuta otra sincronización del número). Ambas necesitan un número de Meta Cloud API (`422 TEMPLATE_REQUIRES_META_NUMBER` en caso contrario) y una credencial con alcance de número. [Enviar a Meta](/es/api/templates#enviar-a-meta)
- `templates_delete` es destructiva y pide confirmación con un token: consulta [Confirmación para herramientas destructivas](#confirmación-para-herramientas-destructivas). Meta elimina por nombre, así que se borran todas las versiones de idioma de ese nombre en la WABA.
- `messages_send` admite los tres modos de envío: `templateId`, `text` o medios directos (`media` \+ `mediaType`; usa `mediaType: "voice"` para una nota de voz en cualquier número; `"audio"` llega como archivo de audio en números oficiales y como nota de voz en los no oficiales).
- `messages_send` con `mediaType: "audio"` o `"voice"` acepta `media` **solo como una URL http(s) pública** de un archivo de audio real. Un data URI en base64 para audio o voz (o cualquier medio `data:audio/*`, sea cual sea el `mediaType`) se rechaza con `400 MCP_AUDIO_URL_REQUIRED` antes de enviar nada: no se crea ningún mensaje. Los data URI de imagen y documento se siguen aceptando, para un archivo que el usuario realmente adjuntó. La regla es exclusiva de MCP: se aplica a `/mcp`, a [Code Mode](/es/integrations/mcp-code-mode) y al agente de IA de la app; la [API REST](/es/api/messages/send) sigue aceptando audio como data URI. Existe porque los modelos inventan audio en base64: esos bytes no son un archivo reproducible y el envío fallaba después con [`MEDIA_TRANSCODE_FAILED`](/es/api/messages/log-error-codes#preparación-de-multimedia-en-números-oficiales).
- `messages_send` acepta `markRead: false` para responder en un número oficial (Meta) sin el indicador de escritura y sin marcar la conversación como leída, para un agente cuyas respuestas una persona todavía debería encontrar sin leer. El valor predeterminado para todo el número es `markReadOnSend` en `numbers_settings_update` / `numbers_create`. `messages_typing` en un número de Meta marca la conversación como leída, así que un agente así no debe llamarla. [Confirmación de lectura y escritura](/es/api/messages/send#confirmación-de-lectura-e-indicador-de-escritura)
- `messages_send` acepta un `idempotencyKey` opcional (hasta 255 caracteres), enviado como el encabezado `Idempotency-Key`. Dentro de 24 horas, volver a llamarla con la misma clave y los mismos argumentos devuelve la primera respuesta aceptada sin enviar de nuevo, así un agente que reintenta tras un timeout no le escribe dos veces al contacto. La misma clave con argumentos diferentes da `409 IDEMPOTENCY_KEY_REUSED`; mientras la primera llamada sigue en curso, `409 IDEMPOTENCY_KEY_IN_USE`. Deriva la clave de lo que hace único al envío (por ejemplo id del pedido \+ destinatario). [Idempotencia](/es/api/messages/send#idempotencia)
- `messages_unread_counts` (solo lectura) devuelve el conteo de mensajes entrantes no leídos **por número** en una sola llamada mediante `GET /v1/messages/unread/counts`: úsala en lugar de llamar a `messages_unread` una vez por número. Omite `whatsappNumberIds` para todos los números que la credencial puede ver; cada `total` es igual al `total` de `messages_unread` para ese número. Devuelve `{ byNumber: [{ whatsappNumberId, number, displayName, total }], total }`.
- Medios entrantes: en números META pasa `media.id` a `media_get`; en números no oficiales (Pilot Status web) usa `media.url` directamente.
- `numbers_delete` es una eliminación lógica de 30 días, que se deshace con `numbers_restore`. `numbers_purge` elimina un número de forma permanente e irreversible; con un token OAuth solo el OWNER del workspace puede llamarla.
- `numbers_pay` paga el cargo pendiente de número extra de un número y reanuda el envío desde él (`POST /v1/numbers/{id}/pay`); con fondos disponibles cobra en el momento. Necesita una clave con alcance de tenant con `billing:manage`; con un token OAuth solo el OWNER del workspace lo tiene.
- `leads_list` y `leads_get` leen los leads capturados de los formularios instantáneos de Meta Lead Ads (Facebook/Instagram) en las páginas de Facebook vinculadas al número de WhatsApp de la clave, y necesitan una clave con alcance de número. `leads_get` toma el `id` del lead de Pilot Status de `leads_list`, no el `leadgenId` de Meta. `consentGiven` tiene tres estados: `true` (marcó la casilla de consentimiento de WhatsApp), `false` (la dejó sin marcar) y `null` (desconocido: nunca es un rechazo ni un consentimiento). Un lead censurado (`redacted: true`, por ejemplo en un número RELAY_ONLY) sigue contando, con `fullName`, `email` y `phone` en null. Ambas envuelven los endpoints REST documentados en [`GET /v1/leads`](/es/api/leads).
- Configuración de anuncios de Meta y Lead Ads: `ads_accounts_*`, `lead_pages_*` y `lead_forms_*` necesitan el permiso `integrations:manage` (ADMIN u OWNER del workspace), incluidas las lecturas; `ads_summary` necesita `analytics:read`, que tienen todos los roles, y no incluye contenido de conversaciones. No hay paso de inicio de sesión: el acceso viene de compartir como socio; el anunciante agrega el portafolio comercial de Pilot Status (`partnerBusinessId`) como socio en Meta Business Manager. `ads_accounts_*` aceptan una credencial de toda la cuenta; las herramientas de Lead Ads y `ads_summary` ven todo el workspace con una credencial de toda la cuenta y solo el número vinculado con una con alcance de número. `lead_pages_unlink` BORRA todos los leads capturados a través del vínculo y sus configuraciones de formulario (irreversible). Con `autoSendEnabled: true`, `lead_forms_update` hace que la plataforma envíe un mensaje a cada lead nuevo automáticamente, sin intervención humana. `ads_summary` devuelve `conversations` (conversaciones distintas) y `messages` por separado, además de `leadCount` por anuncio, con un máximo de 200 anuncios (`truncated`). Envuelven los endpoints REST documentados en [Anuncios](/es/api/ads) y [Páginas de Lead Ads](/es/api/lead-pages).
- `webhooks_create` y `webhooks_update`: `"*"` suscribe a todos los eventos excepto `lead.received`, que es opcional: inclúyelo por nombre (por ejemplo `["*", "lead.received"]`). Consulta [`lead.received`](/es/api/webhooks/events#payload-lead).
- `webhooks_create` devuelve el `secret` de firma en texto plano **una vez**, al crearlo; ninguna lectura lo vuelve a devolver. `webhooks_rotate_secret` genera uno nuevo (también es la forma de firmar un webhook creado antes del 2026-09-15): se devuelve una vez, y el secreto anterior deja de verificar de inmediato, sin ventana de superposición; guárdalo antes que nada. Consulta [Verificar la firma](/es/api/webhooks/configure#verificar-la-firma).
- `webhooks_reactivate` reanuda un webhook que la pausa automática detuvo y libera los eventos retenidos; llamarla en un webhook que ya está entregando no hace nada.
- Las herramientas de líneas telefónicas aceptan solo una credencial con alcance de tenant. Las herramientas `phone_lines_verification_*` son solo para OWNER (`phone_lines:purchase`); `phone_lines_verification_start` requiere un `idempotencyKey` (enviado como el encabezado `Idempotency-Key`). `phone_lines_activation_audio` devuelve los metadatos de la grabación y la URL de descarga, nunca el audio en sí.
- `phone_lines_webhooks_*` administran los [webhooks de líneas telefónicas](/es/api/phone-lines/webhooks), un registro propio que recibe solo eventos `phone_line.*` (los webhooks de número de `webhooks_*` nunca los reciben). Solo credencial con alcance de tenant; `phone_lines:webhooks` (ADMIN u OWNER del workspace). `phone_lines_webhooks_list` también devuelve `events`, el catálogo de eventos a los que se puede suscribir: `events` acepta una lista no vacía de ellos, o `["*"]` para todos los eventos de líneas telefónicas. `phone_lines_webhooks_create` devuelve el secreto de firma `plwh_` **una vez**: guárdalo de inmediato, no se puede volver a leer y no hay rotación. Con una conexión OAuth, cada creación queda registrada en el log de auditoría ([ver abajo](#secretos-y-api-keys-por-oauth)). No es idempotente: cada llamada crea otro webhook. `phone_lines_webhooks_update` con `active: false` pausa un webhook; `phone_lines_webhooks_delete` lo elimina junto con su historial de entregas de forma permanente. `phone_lines_webhooks_deliveries_list` nunca incluye el payload; `phone_lines_webhooks_deliveries_get` lo devuelve tal como se firmó, y en `phone_line.code_received` contiene el código de activación.
- `billing_checkout` acepta un `method` opcional: `card` (por defecto) devuelve una `url` de checkout alojado; `pix` (solo workspaces en BRL, de lo contrario `400 PIX_NOT_ELIGIBLE`) devuelve `orderId` y `pix { transactionId, copyPaste, qrCode, expiresAt }` para que el usuario pague en la app de su banco. `successUrl`/`cancelUrl` solo se aplican a los checkouts con tarjeta (`400 FIELD_NOT_APPLICABLE` con `pix`). No se cobra nada hasta que una persona paga. `billing_topups_get` lee el pedido de recarga por ese `orderId` (`status` `pending`, `paid` (billetera acreditada), `expired` o `failed`) sin llamar al proveedor de pagos. Los endpoints de Stripe Elements (`/v1/billing/card/setup-intent*`, `/v1/billing/payment-intents*`) no tienen herramienta: su `clientSecret` solo lo puede usar Stripe.js en un navegador. Consulta [Billetera y tarjeta por API](/es/api/wallet-and-card).
- `workspace_webhooks_*` administran los [webhooks del workspace](/es/api/workspace-webhooks) (`/v1/workspace/webhooks*`): el mismo registro que `phone_lines_webhooks_*` (mismas filas, secreto `plwh_`, firma y entregas), con un conjunto de eventos más amplio: todos los eventos `phone_line.*` más `wallet.topup_paid` (se acreditó una recarga de la billetera). `"*"` sigue significando solo todos los eventos de líneas telefónicas: `wallet.topup_paid` es opcional, inclúyelo por nombre (por ejemplo `["*", "wallet.topup_paid"]`). Solo credencial con alcance de tenant; `phone_lines:webhooks` (ADMIN u OWNER del workspace). `workspace_webhooks_create` devuelve el secreto de firma **una vez**, como `phone_lines_webhooks_create` (con una conexión OAuth, registrado en el log de auditoría).
- `workspace_update` (argumento `name`, de 1 a 60 caracteres, sin espacios en los extremos) renombra el workspace; `workspace_settings_get` (sin argumentos) lee su moneda, zona horaria, idioma, modo de facturación y el precio de una línea telefónica nueva; `workspace_settings_update` (argumentos `mainTimezone?`, una zona IANA, y `mainLanguage?`, `pt`, `en` o `es`) cambia solo esos dos campos: la moneda la cambia el dueño en el panel, y el modo de facturación la plataforma. Aceptan una credencial con alcance de tenant; con un token OAuth, `workspace_update` y `workspace_settings_update` necesitan ADMIN u OWNER, y `workspace_settings_get` cualquier rol. Consulta [API de workspace](/es/api/workspace#renombrar-el-workspace).
- **`workspace_archive`, `workspace_transfer_ownership` y `workspace_members_remove` son destructivas y requieren confirmación**, como `templates_delete`. La primera llamada (sin `confirm_token`) no cambia nada: lee `GET /v1/workspace` y `GET /v1/workspace/members` y devuelve un `preview` (el workspace y cada miembro que pierde acceso al archivar; el nuevo dueño y el actual al transferir; el correo, rol, números del miembro y lo que pierde al eliminar) más un `confirm_token` de un solo uso válido por 5 minutos. Muestra la vista previa al usuario; solo una segunda llamada con los **mismos argumentos** y ese token ejecuta [`POST /v1/workspace/archive`](/es/api/workspace#archivar-el-workspace), [`POST /v1/workspace/transfer-ownership`](/es/api/workspace#transferir-la-propiedad) o [`DELETE /v1/workspace/members/{id}`](/es/api/workspace#eliminar-un-miembro-que-creó-claves-de-api). Argumentos diferentes dan `CONFIRM_TOKEN_MISMATCH`, un token reutilizado `CONFIRM_TOKEN_USED`, uno vencido `CONFIRM_TOKEN_EXPIRED`. Si el servidor no puede verificar que el token sea de un solo uso, la llamada se rechaza con `503 CONFIRM_TOKEN_STORE_UNAVAILABLE` y no se ejecuta nada: reintenta.
  - Las tres son **solo para el dueño** y necesitan el token OAuth/MCP del dueño (archivar y transferir también aceptan su clave de cuenta). Una clave `ps_` de workspace o de número recibe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_WORKSPACE` (archivar, transferir) o `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS` (eliminar).
  - `workspace_archive` acepta `confirmName`, el nombre del workspace escrito exactamente (distingue mayúsculas y minúsculas); si no coincide, se rechaza en la vista previa con `400 CONFIRMATION_MISMATCH` y sin token. Archivar deja a todos sin acceso, incluido quien llama, y no hay endpoint para desarchivar.
  - `workspace_transfer_ownership` acepta el `email` del nuevo dueño (un miembro que aceptó la invitación; `NOT_A_MEMBER`, `TARGET_NOT_ACTIVE` y `ALREADY_OWNER` se rechazan en la vista previa). Tú pasas a ser ADMIN y se revocan los refresh tokens OAuth de ambos usuarios, así que esta conexión actúa como ADMIN desde la siguiente llamada y debe volver a dar su consentimiento cuando venza su token de acceso.
  - `workspace_members_remove` acepta `id` y, después de un `409 MEMBER_HAS_API_KEYS`, `apiKeyAction` (`revoke` o `keep`): ese 409 consume el token y no elimina nada, así que pide una nueva vista previa con la decisión.
  - El agente de IA de la app no ofrece archivar ni transferir.
- `workspaces_*` aceptan solo una **clave de cuenta** (`ps_account_…`, creada en Profile → API, enviada como `x-api-key`): un token OAuth/de conector, una clave de workspace o una clave de número recibe `403 ACCOUNT_KEY_REQUIRED`. `workspaces_list` lista los workspaces de los que el usuario de la clave es miembro activo, con su rol; `workspaces_create` crea uno cuyo dueño es ese usuario y devuelve su clave principal de workspace **una vez** (`409 WORKSPACE_LIMIT_REACHED` al llegar al tope del usuario); su `shareCard: true` opcional vincula el nuevo workspace a la tarjeta de reserva del usuario, y si se omite o es `false` queda sin compartir. `workspaces_shared_card_link` y `workspaces_shared_card_unlink` (argumento `workspaceId`) llaman a `PUT` y `DELETE /v1/workspaces/{workspaceId}/shared-card`: necesitan que el usuario sea OWNER de ese workspace, cambian quién paga sus renovaciones y piden confirmación. `workspaces_api_keys_list` (enmascaradas), `workspaces_api_keys_create` (una clave `ps_workspace_` con nombre, devuelta una vez; `409 WORKSPACE_KEY_LIMIT_REACHED`) y `workspaces_api_keys_revoke` (`409 PRIMARY_KEY_NOT_REVOCABLE` para la clave principal) necesitan que el rol vigente del usuario sea ADMIN u OWNER en ese workspace; de lo contrario, `403 WORKSPACE_MEMBERSHIP_REQUIRED` o `PERMISSION_DENIED`. El agente de IA de la app no las ofrece. No necesitan `x-workspace-id`, y `docs_search` tampoco; todas las demás herramientas usadas con una clave de cuenta sí (consulta [Con una clave de cuenta](#con-una-clave-de-cuenta)). Consulta [Crear workspaces](/es/api/workspaces).
- `docs_search` acepta un `query` (una pregunta, palabras clave o un código de error, en portugués o inglés) y un `limit` opcional (de 3 a 5, por defecto 5), y devuelve `{ query, results, source }`: las 3 a 5 páginas más relevantes de esta documentación, cada una con `title`, `url` y `description` (no el contenido de la página). Lee el índice público de la documentación (`llms.txt` y su subíndice pt-BR; las páginas del Playground quedan fuera), no llama a ningún endpoint `/v1` y no necesita permiso, alcance de clave ni `whatsappNumberId`, así que cualquier rol puede usarla y el agente de la app la ejecuta sin pedir confirmación. `source` es `live`, o `fallback` cuando no se pudo obtener el índice y respondió una copia integrada; el índice se guarda en caché por 6 horas. Úsala cuando el usuario pregunte cómo hacer algo en Pilot Status, o cuando otra herramienta devuelva un código de error: busca el código (por ejemplo, `MEDIA_TRANSCODE_FAILED` lleva a [Códigos de error del log](/es/api/messages/log-error-codes)).
- `templates_delete` acepta un `force_local_delete` opcional: cuando Meta rechaza la eliminación (`409 META_TEMPLATE_DELETE_REFUSED`, nada eliminado), elimina solo la copia de Pilot Status y deja la plantilla en Meta. Úsalo solo después de que el usuario vio ese 409 y pidió una eliminación solo local.
- Tres herramientas se niegan a ejecutarse sin el booleano **`confirm: true`** (sin token, una sola llamada): `flows_publish` (publicar un Flow no se puede deshacer; de lo contrario `400 FLOW_PUBLISH_REQUIRES_CONFIRMATION`), `flows_endpoint_key_rotate` cuando el número ya tiene una clave registrada en Meta (reemplazarla rompe todos los Flows `data_exchange` del número; de lo contrario `400 FLOW_ENDPOINT_KEY_REQUIRES_CONFIRMATION`) y `subscription_extra_numbers_add` cuando la compra convierte un plan FREE a On Demand. Envíalo solo después de que el usuario dijo que sí.
- La administración de miembros necesita un **token OAuth** (no hay un usuario detrás de una clave `ps_`, así que una clave recibe `403 MACHINE_CREDENTIAL_CANNOT_MANAGE_MEMBERS`): `workspace_members_invite` y `workspace_members_resend` (ADMIN u OWNER; un ADMIN solo puede asignar AGENT o ANALYST), `workspace_members_set_numbers` (ADMIN u OWNER), `workspace_members_update` y `workspace_members_remove` (solo OWNER). `workspace_members_list` (ADMIN u OWNER) también funciona con una clave de workspace. Nadie se convierte en OWNER mediante estas herramientas: para eso está `workspace_transfer_ownership`.
- `billing_checkout` es a nivel de cuenta: necesita al OWNER del workspace y una concesión **Entire account** (una concesión OAuth por número no puede usarla).
- Las rutas basadas en token (endpoints públicos de vinculación remota, emisión de sesiones embebidas) quedan excluidas de la lista de herramientas porque usan otro flujo de autenticación.

## Secretos y API keys por OAuth

Con el conector OAuth, la app puede hacer lo mismo que el panel, incluido revelar y crear API keys y secretos, bajo estas salvaguardas:

1. **API keys: solo el Owner del workspace, verificado en cada llamada.** Revelar o crear una API key `ps_` solo funciona mientras el usuario conectado sea el **Owner** del workspace. El rol se lee del workspace en cada llamada, no del token ni del consentimiento: si el dueño entrega el workspace o es eliminado, la siguiente llamada se rechaza.
2. **Secretos de firma: la misma regla que el panel.** Los secretos de firma de webhooks (incluido `plwh_`), el secreto del endpoint de Flow y el verify token de Meta van a quien el panel permita: **Admin** u **Owner** del workspace.
3. **Log de auditoría, para todos ellos.** Cada revelación o creación de una clave o secreto hecha por OAuth queda registrada: quién (usuario), qué app (cliente OAuth), qué workspace, qué (acción y objetivo), cuándo y desde qué IP. El valor en sí nunca se registra.
4. **Advertencia en la pantalla de consentimiento.** A un dueño se le informa que la app podrá ver secretos y crear API keys; a un admin, que podrá ver secretos (las API keys siguen siendo exclusivas del dueño).

| Herramienta | Qué revela o crea | Quién, por OAuth |
| --- | --- | --- |
| `api_keys_list` | Las claves de número, en texto plano | Solo Owner; de lo contrario `403 OAUTH_SECRET_REQUIRES_OWNER` |
| `api_keys_regenerate_number` | Una nueva clave de número (`ps_number_…`) | Solo Owner; de lo contrario `403 OAUTH_SECRET_REQUIRES_OWNER` |
| `webhooks_create`, `webhooks_rotate_secret` | Un secreto de firma de webhook | Admin u Owner (`webhooks:manage`) |
| `workspace_webhooks_create`, `phone_lines_webhooks_create` | Un secreto de firma `plwh_` | Admin u Owner (`phone_lines:webhooks`) |

`POST /v1/api-keys/regenerate` (la clave principal del workspace) sigue la regla de las API keys; `PUT`/`PATCH /v1/flows/{id}/endpoint` (el secreto del endpoint de Flow) y `POST /v1/numbers/meta` (el verify token de Meta) siguen la regla del panel. Si no se puede escribir el registro de auditoría, la acción no se realiza sin registro: una revelación o rotación se rechaza con `500 OAUTH_SECRET_AUDIT_UNAVAILABLE`, y una creación igual se completa pero devuelve `secret: null` con `secretWithheld: true` (rota para obtener uno nuevo).

<Warning>
  Una clave o secreto obtenido a través del conector **sigue siendo válido después de revocar el conector**: revocarlo termina el acceso de la app, no lo que obtuvo. Para cortar eso, regenera las claves en la pantalla [API Keys](/es/dashboard/api-keys) y rota los secretos. Las claves creadas por OAuth quedan registradas como creadas por ti, así que al eliminarte del workspace se ofrece revocarlas.
</Warning>

Una clave `ps_` clásica (`x-api-key`) no se ve afectada por estas reglas. Crear workspaces y claves de workspace con nombre (`workspaces_*`) sigue requiriendo una clave de cuenta.

## Confirmación para herramientas destructivas

Algunas herramientas cambian cosas que no se pueden deshacer. Se ejecutan en **dos llamadas**, y la segunda necesita un token de la primera:

1. **Llama a la herramienta sin `confirm_token`.** No cambia nada. La respuesta es `status: "CONFIRMATION_REQUIRED"`, un `preview` de exactamente lo que pasaría y un `confirm_token` válido por **5 minutos**.
2. **Muestra la vista previa a la persona y espera un sí explícito.** Luego llama a la herramienta de nuevo con los **mismos argumentos** más `confirm_token`. Solo esta llamada ejecuta la acción.

```json Primera llamada: vista previa, nada eliminado
{
  "status": "CONFIRMATION_REQUIRED",
  "preview": {
    "dry_run": true,
    "action": "DELETE_ON_META_AND_LOCAL",
    "template": { "id": "tpl_01HZX...", "name": "promo", "meta_language": "pt_BR", "meta_status": "APPROVED" },
    "waba": { "id": "1581714517011340", "name": "Acme" },
    "via_number": { "id": "wn_01HZX...", "number": "+5511999990000" }
  },
  "confirm_token": "pct1.eyJ0Ijo...",
  "expires_at": "2026-11-10T14:05:00.000Z",
  "next_step": "Nothing was changed. Show this preview to the user. …"
}
```

- El token es de un solo uso y está ligado a la herramienta, sus argumentos y tu conexión (credencial, workspace y número). Otra herramienta, otros argumentos, otra clave u otro número no pueden usarlo.
- Rechazos: `CONFIRM_TOKEN_EXPIRED` (pide una nueva vista previa), `CONFIRM_TOKEN_MISMATCH` (repite los argumentos exactos de la vista previa), `CONFIRM_TOKEN_USED` (ya se ejecutó: no lo repitas), `CONFIRM_TOKEN_INVALID` (obtén una nueva vista previa).
- Herramientas con confirmación hoy: `templates_delete`, `workspace_archive`, `workspace_transfer_ownership` y `workspace_members_remove`. La API REST no necesita token: llama a `DELETE /v1/templates/{id}?dry_run=true` para obtener la misma vista previa de la eliminación de una plantilla.
- En [Code Mode](/es/integrations/mcp-code-mode) se aplican las mismas dos llamadas. En el agente de IA de la app, la vista previa se ejecuta sola y el agente te pide confirmar la segunda llamada.

### Agentes sin una persona supervisando (n8n, servidores)

La confirmación de arriba te protege cuando **una persona ve la vista previa**: Claude, ChatGPT y Cursor te preguntan antes de cada llamada a una herramienta que cambia algo. Un agente autónomo (el AI Agent de n8n, un cron, un servidor) no tiene esa pantalla. Recibe el `confirm_token` y puede confirmar por sí mismo, y las demás herramientas destructivas se ejecutan en la primera llamada. Un texto enviado por un cliente puede bastar para que el agente borre algo.

<Warning>
Si la conexión funciona sin una persona supervisando cada llamada, **bloquea las operaciones destructivas en su clave de API**: panel → **Configuración → API** → la clave → **Bloquear operaciones destructivas**.
</Warning>

Con el bloqueo activado, toda operación destructiva hecha con esa clave (borrar una plantilla, un webhook, un número o un miembro; desconectar; archivar; sobrescribir la configuración) responde `403 DESTRUCTIVE_OPERATIONS_BLOCKED`, sea cual sea el cliente: una herramienta del MCP, [Code Mode](/es/integrations/mcp-code-mode), n8n o una llamada REST directa. Las lecturas y el envío de mensajes siguen funcionando. Solo el dueño o un admin del workspace lo cambia, y cada cambio queda registrado. Las claves nuevas empiezan **permitidas**, así que nada cambia en una integración hasta que la bloquees.

## Errores comunes

- `401`: API key ausente o inválida, o una sesión OAuth vencida: se le pide al cliente que vuelva a iniciar sesión ([Conecta tu cliente](#conecta-tu-cliente)).
- `403`: una clave de número en una herramienta a nivel de cuenta, una herramienta fuera de una concesión por número, o un rol que no puede llamar a la herramienta. Con un token OAuth o una clave de workspace, también se rechaza una herramienta con alcance de número llamada sin `whatsappNumberId`.
- `WORKSPACE_ID_REQUIRED`: una clave de cuenta sin `x-workspace-id` ([Con una clave de cuenta](#con-una-clave-de-cuenta)).
- `503 SHUTTING_DOWN`: la réplica que tomó la solicitud se está reiniciando; reintenta.
- `400`: argumentos de herramienta inválidos (validados contra el esquema de la API subyacente).
- `400 MCP_AUDIO_URL_REQUIRED`: `messages_send` recibió un data URI (base64) para `mediaType` `audio`/`voice`, o un medio `data:audio/*`. Envía el audio como una URL http(s) pública. El mensaje es bilingüe (`English | Português`) y no se envió nada.
